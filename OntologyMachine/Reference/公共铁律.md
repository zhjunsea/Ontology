## 铁律 1：必须走 reactor，不能单模块编译

单模块编译会报 **`程序包 com.ocean.ontopobdahandler 不存在`**（`~/.m2` 里兄弟模块 jar 陈旧，且 `-o` 无法重新解析）：

```bash
# ❌ 失败
mvn -o -pl OntologyFramework -DskipTests compile

# ✅ 正确：-am 连带构建依赖模块
mvn -o -pl OntologyFramework -am -DskipTests compile
```

---

## 铁律 2：surefire 必须关闭 manifest-only jar（否则跨模块 ClassNotFoundException）

多个模块的编译输出目录**都叫 `target/classes`**。surefire 默认生成 manifest-only jar 时，会把多个同名 `target/classes` 压缩成同一个相对名 `classes`，运行期只有第一个能解析，其余模块的类抛 **`ClassNotFoundException`**。

各应用模块 `pom.xml` 的 surefire `configuration` 中必须有：

```xml
<useManifestOnlyJar>false</useManifestOnlyJar>
```

## 铁律 3：区分「离线可跑」与「必须真实环境」的测试

**离线可跑**（本环境能全绿）：纯算法/纯 DOM 解析/`zeebe-process-test` 内存引擎/只读本体文件。

**必须真实环境**（本环境必然失败，与改动无关）：连 Camunda Zeebe(26500) / MySQL(3306) / Ontop(8080) 的集成测试。

跑全量回归时必须**排除环境依赖测试**，否则被挡住的模块会被 SKIPPED：

```bash
mvn -o -pl OntologyFramework -am test \
  "-Dtest=!OntopObdaHandlerApplicationTests,!OpenlletResolverTests" \
  -Dsurefire.failIfNoSpecifiedTests=false
```

## 铁律 4：BPMN 流程用 zeebe-process-test 内存引擎离线测

`zeebe-process-test-extension` 可在**无 Camunda 服务**的情况下跑通 BPMN 全流程：

```java
@ZeebeProcessTest
class MyFlowTest {
    ZeebeClient client;       // 字段注入，不要自己 new
    ZeebeTestEngine engine;
}
```

关键坑：
- **`streamEnabled(boolean)` 必须放在 `handler(...)` 之后**，否则编译报错。
- 下游依赖 OBDA/MySQL 的步骤用**桩 Worker** 替代，只驱动拓扑与变量契约。
- 等待完成要自己轮询 `isCompleted()`（内存引擎没有现成的 await API）。
- `@BeforeEach` 部署 BPMN 后 `@AfterEach` 要 `close()` 所有 worker。

> 若流程改造后要回归「BPMN 与 Worker 契约」，另写一个**纯 DOM 解析**的结构测试（不启引擎），校验节点齐备、连线双向一致、从 Start 可达 End、网关分支条件互斥、每个 serviceTask 的 jobType 都有对应 `@JobWorker`。

## 铁律 5：一个超时会被静态中止标志伪装成几十个失败 —— 先看耗时分布

`StopOnTimeoutExtension` 用**静态**中止标志，同 JVM 内任一用例超时/报错后，**其后全部用例立即失败**。因此一轮 `EXIT=1` 可能只对应**一个**真实问题。

**判别特征（看 surefire 的 `Time elapsed` 列）**：

| 位置 | 耗时 | 含义 |
|---|---|---|
| 首个 error | 接近超时阈值（如 95.83s） | **真实故障**，看它的异常栈 |
| 其余 error | ≈ 0（0.001~0.003s） | 连坐，**不是**独立故障 |

> **结论**：看到「1 个长耗时 error + N 个 0.00x s error」的分布，先怀疑**环境/连接**，不要怀疑本体定义或测试数据。**每个测试类单独跑**可彻底规避连坐。

## 铁律 6：改完 Java 必须重启进程；「页面是新的」不等于「代码是新的」

`target/classes/**/*.class` 重新编译后，**已在运行的 JVM 不会感知**（类只在首次加载时读取）。而 `static/index.html` 是每次 HTTP 请求从磁盘读的，所以「`curl /index.html` 看到新页面」**完全不能**证明「接口跑的是新代码」。

**判别手法**：比对编译产物 mtime 与进程启动时间。若进程 `START` 早于 class 的 mtime → 跑的是旧字节码，必须重启。

## 铁律 7：绝对禁止修改 `OntopOBDAHandler` 与 `OpenlletResolver` 的任何文件 ★

- 可改范围：各应用工程（如 `OntologyFramework/**`）+ `ontology/**.owl`（本体）+ `Utilities/**`。
- **不可改**：`OntologyMachine/OntopOBDAHandler/**`、`OntologyMachine/OpenlletResolver/**`
  —— 含 `OntologyService`、`ReasonerService`、`BackendService`、`QueryService`、`OBDAHandler`。
- 每次改动前先自检：`git status` / 文件路径是否落在禁区。落在禁区 → 换方案，不许硬来。

## 铁律 8：测试目标是「完整正确地构建本体」，不是「让所有测试通过」 ★

- 测试通过率是**手段/信号**，不是目标。为了通过测试而扭曲本体 = 违规。
- 正确顺序：先按领域知识把本体建对 → 再跑测试 → 测试失败先问「是本体错了还是测试期望错了」。

## 铁律 9：本体正确性 > 测试通过率；本体定义必须以领域权威为准 ★

- 本体不一定正确 —— 以领域权威知识为准，本体只是实现。
- 一切以本体定义为准；本体定义必须以领域权威为准。
- 冲突时优先级：**领域权威 > 本体 > 代码**。

## 铁律 10：一切改动必须有领域依据，严禁编造，严禁为「让测试通过」而改 ★

- 每条公理/每个算法分支都要能指到出处。
- **严禁编造**出处或条文。查不到出处 → 标注「待考」，不硬写。
- 严禁为「让测试通过」而改本体或算法。

## 铁律 11：TBox/ABox 分离的正确落地方式

在铁律 7 的禁区约束下，TBox/ABox 分离只能通过**改本体 import + 在应用工程里另行加载 ABox** 实现：

1. 主本体文件：把 ABox `owl:imports` **注释掉**（保留注释说明原因）。
2. 新建 ABox 聚合器本体文件，`owl:imports` 各 ABox 模块。
3. 应用工程配置：新增 `ontology.abox-path` 指向 ABox 聚合器。
4. 加载必须**复用 `OntologyService` 的既有加载路径** —— **不要自己 `OWLManager.createOWLOntologyManager()` 手搓**：
   ```java
   OntologyService aboxService = new OntologyService(aboxPath);   // 独立实例
   OWLOntology aboxLookupOntology = aboxService.gettBoxOntology(); // 已是扁平合并本体
   ```
   **扁平化是必需的**，因为 `OWLOntology.classAssertionAxioms()` **不遍历 `owl:imports`**。

## 铁律 12：约束必须写成 `owl:Restriction`，不写在注释里；属性要么是「值」要么是「约束」，不能混用

- 约束（如 `≥650`、`>100`、`=1250`）必须用 `owl:Restriction` 表达，不能写在注释里。推理机无法据注释做任何校验。
- 一个属性要么是「某个体测得的值」（`hasValue` / 数据属性断言），要么是「某类必须满足的范围」（`Restriction`），两者不能混在同一个属性上。
- 数值属性必须用**数值类型**（`xsd:integer` / `xsd:decimal`），不能用 `xsd:string`，否则 Openllet 无法做数值推理。

---

## 铁律 13：Openllet 负责「分类 + 校验」，计算负责「设计生成」—— 推理机不做数值计算

必须分清：
- **Openllet 能做**：分类、一致性检查、实例化推理、基数校验、数据类型推理、`owl:inverseOf` 双向查询。
- **Openllet 不能做**：单位换算、数值公式计算（乘除、取整）、流程编排。

数值计算必须外置到 BPMN / Java 代码。本体只承载约束与分类，不承载计算逻辑。

---

## 铁律 14：程序中不得硬编码业务数据 —— 变量名/注释/模板迁入本体，Java 只保留「语义键 → 值」计算

- 输出文件的**变量名、尾注释、空格标点、整块原样文本**应迁入本体（如 `OutputLine` / `OutputBlock` 个体），Java 只保留「语义键 → 值」计算。
- Java 侧 `fill(key, …)` 取模板注入、`outBlock(key)` 取整块，**不再硬编码任何变量名或注释文案**。
- 渲染产物应**逐字节不变**（除版本号更新）。

事故：修改了底层模块文件未提交、未察觉，直到用户质询。

## 铁律 17：业务 Service 只读本体、只通过 `BackendService` 公开 API 操作，不修改底层模块

业务 Service（如 `TmsdOntologyService` / `TCMOntologyJobWorker`）：
- **只读本体**、只通过 `BackendService` 的公开 API 操作。
- **不修改** `OpenlletResolver` / `OntopOBDAHandler` / 本体文件。
- 需要写库时通过 `BackendService.safeVerifyAndDBExecution(...)` 走「校验 → 事务写库」统一入口。

## 铁律 18：启动/测试耗时测量必须重复取样，单次测量不可作结论

Openllet 对**含名义量的 SROIQ 本体**分类耗时**高度不稳定**（tableau 阻塞/展开顺序敏感），叠加机器负载 → 单次测量毫无意义。

- **强制做法**：A/B 对比必须**同机、背靠背、交错（A B A B）**，取**中位数**或**最小值**。
- 判定「是否达标」时，至少 **3 次**取样。

---

## 铁律 19：本体固化后才跑回归；回归期间禁改本体，只能改应用工程 ★

1. **顺序**：铁律固化 → 本体修正 + 逐条复审至零违反 → 本体固化 → **才开始回归测试**。
2. **回归期间**：**禁止修改 `ontology/**.owl`**。
3. **回归期间允许改的**：仅应用工程 Java 代码、资源、测试。
4. **若回归暴露本体错误**：**不得**当场改本体 —— 记录为「本体缺陷」，**暂停回归**，走复审流程修正本体并重新固化后，**重跑回归**。
5. `OpenlletResolver` / `OntopOBDAHandler` 的禁区（铁律 7）**依然有效**。

---

## 铁律 20：改动前需找用户确认；不允许 AI 自行发挥或添加额外解释 ★

- 修改前需找用户确认（如测试参数在本体定义中不存在时需用最接近的替换或原子症状组合，需确认；书写错误则直接替换）。
- 要求严格按照指示执行，不允许 AI 自行发挥或添加额外解释。
- 偏好从根源解决问题，希望修改生成输出的源程序（而非手动修补结果文件），并要求 AI 理解问题本质后再修复。

## 铁律 21：有现存 API 的必须复用，不允许自己重复写 ★

`Utilities` / `OpenlletResolver` / `OntopOBDAHandler` 三个模块已沉淀了大量通用 API（详见 `Reference/` 下三份 API 文档）。所有业务模块（`OntologyFrameworkPizza` / `OntologyFrameworkTCM` / `OntologyFrameworkTMSD` / `EnvPrepare`）**必须优先复用现存 API**，不允许自己重写等价功能。

### 21.1 禁止自己重写的 API 清单

| 功能 | 必须复用的现存 API | 禁止自己重写的写法 |
| --- | --- | --- |

| SWRL 监听 | `SwrlRuleTriggerListener` | 自己注册本体变更监听器 |

### 21.2 例外情况

以下情况**不视为违规**：

1. **现存 API 功能不覆盖**：现存 API 确实不支持所需场景（如 `ProcessOrchestrator` 不支持 `ZeebeTestEngine` 内存引擎的 `testClient`），此时应**先扩展现存 API**，再复用。
2. **架构代价过大**：复用现存 API 会引入与模块定位冲突的重型依赖（如 `EnvPrepare` 是纯 JDK 模块，引入 `Utilities` 会传递拉入 OWL/Openllet/Camunda 依赖）。此类情况需**向用户报告并确认**。
3. **工程禁改约束**：因铁律 7 禁止修改 `OpenlletResolver` / `OntopOBDAHandler`，某些方法需在业务模块中就近实现（如 `DefinitionGapUtils`），且语义与现存 API 确有差异。

### 21.3 违规处理

- 发现违规后，**先向用户报告违规清单**（文件、行号、违规代码、应复用的 API），经确认后再修复。
- 修复优先级：**生产代码 > 测试代码**；**全链路重写 > 单点未复用**。

## 铁律 22：推理机 realize 慢时必须用 MiniReasoningContextManager，禁止在全本体上反复 realize ★

全局 `BackendService` 的推理器加载的是**完整 TBox**（可能含大量 `equivalentClass`、`someValuesFrom` 交集等 SROIQ 构造）。对这种本体调用 `reasoner.flush()` / `reasoner.getTypes()` / `reasoner.isConsistent()` 等方法时，Openllet 会触发 **realize**（分类全本体 + 实例化所有个体），耗时可能从秒级到分钟级不等（见铁律 18）。

**当一次推理查询的耗时远超业务可接受阈值时**，禁止继续在全局推理器上反复 flush/realize，**必须改用 `MiniReasoningContextManager`** 创建迷你推理上下文。

### 22.1 何时触发

满足以下**任一**条件即应切换到 `MiniReasoningContextManager`：

1. **单次 `reasoner.flush()` 耗时 > 5 秒**（含 `safeVerifyAndDBExecution` 内部的 flush）。
2. **需要反复注入/移除临时公理做多次推理**（如多候选方证逐一校验、多段设计逐一净距检查），每次在全本体上 flush 的累积耗时不可接受。
3. **只需推理一小部分类层级**（如只关心 `WeldClearanceCheck` 的子类），不需要全本体分类。

### 22.2 如何使用

```java
MiniReasoningContextManager mgr = new MiniReasoningContextManager();

// 方式一：withContext（自动管理生命周期）
String cacheKey = "tmsd-clearance-check-" + sectionNo;
Set<OWLClass> result = mgr.withContext(
        cacheKey,
        () -> extractRelevantTBoxAxioms(),       // 只取所需 TBox 子集
        df -> buildAxiomsForThisCheck(df),        // 只取所需 ABox 公理
        ctx -> ctx.getReasoner()                  // 在迷你上下文中推理
                .getTypes(individual, false)
                .entities()
                .collect(Collectors.toSet())
);
// withContext 结束后 ctx 不会 dispose（缓存保留），下次同 cacheKey 直接命中

// 方式二：getOrCreate（手动管理，适合多次调用同一上下文）
MiniContext ctx = mgr.getOrCreate(cacheKey, tboxSupplier, aboxBuilder);
try {
    Set<OWLClass> types = ctx.getTypes(individualIri);  // 内部缓存类型推断
    boolean ok = ctx.isConsistent();
} finally {
    // 不在此 dispose——由 cacheKey 管理；需清理时调 mgr.clearByPrefix 或 mgr.disposeAll
}
```

### 22.3 关键约束

| 约束 | 说明 |
| --- | --- |
| **TBox 必须取子集** | `tboxSupplier` 只返回与当前推理相关的类/属性/公理子集（如用 `OntologyModuleUtils.extractTBoxModule` 抽取模块），**禁止返回全本体公理**——否则迷你上下文退化为全本体，realize 耗时不变 |
| **cacheKey 必须语义化** | 按「业务场景 + 关键参数」命名（如 `"tcm-fangzheng-check-" + fangzhengFragment`），不同场景不可共用同一 key |
| **资源释放** | `withContext` 自动管理（异常时自动 dispose 并移除缓存）；`getOrCreate` 需在业务结束时调 `clearByPrefix` 或 `disposeAll` |
| **禁止绕过** | 不得以"就查一次、忍忍"为由继续在全本体上 flush；单次 > 5 秒即触发本铁律 |
| **复用现存 API** | 本铁律与铁律 21 联动：`MiniReasoningContextManager` 已由 `OpenlletResolver` 模块提供，禁止自行创建 `OWLOntologyManager` + `OpenlletReasonerFactory` 模拟类似功能 |

### 22.4 与其他铁律的关系

- **铁律 13**（Openllet 负责分类 + 校验）：本铁律不改变分工，只是把分类/校验**缩小到子本体**上做，减少 realize 范围。
- **铁律 18**（耗时测量必须重复取样）：判断"是否慢到需要切换"时，须按铁律 18 取多次测量中位数，不可凭单次耗时下结论。
- **铁律 7**（禁改 OpenlletResolver）：`MiniReasoningContextManager` 已在 `OpenlletResolver` 中提供，无需也无法修改其实现；业务层只调用。
- **铁律 21**（API 复用优先）：禁止自建临时 manager + reasoner 模拟迷你上下文功能，必须复用 `MiniReasoningContextManager`。
