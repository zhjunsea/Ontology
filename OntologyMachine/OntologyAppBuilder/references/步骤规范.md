# 步骤规范（14 步 · 输入/动作/产出/验收）

> 与 `SKILL.md` §3 配套的**深度规范**。每步给出：输入 → 动作清单 → 产出 → 验收判据 → 关联铁律。
> 通用红线：**完全按业务、不编造**；产出参考 `Example-文件映射.md`。

---

## 第 1 步　明确业务场景与目标范围
- **输入**：业务场景描述（用户提供）。
- **动作**：① 提炼目标；② 划定范围与**不在范围**项；③ 识别角色/关键对象/关键约束；④ 无法确认处标「待业务确认」。
- **产出**：`design/<Xxx>应用-顶层设计.md` §概述与定位、§范围。
- **验收**：场景每个业务名词在后续有落点或显式声明不建模；「待确认」项已登记。
- **铁律**：★10（有依据）、★20（待确认项带入闸门）。

## 第 2 步　流程设计【闸门①】
- **输入**：第 1 步范围。
- **动作**：拆「环节 → 输入 → 处理 → 输出 → 分支」；纯业务语言；标注待业务裁定的分支/边界。**产出初稿后交客户审阅，根据客户反馈反复修订打磨，直至客户明确同意流程设计定稿**——此过程可能多轮往返，每轮修订后须重新交客户确认。
- **产出**：`design/<Xxx>应用-流程设计.md`。
- **验收**：每环节输入/输出明确；每个排他分支条件**互斥且完备**；**客户已明确同意流程设计**（非仅 AI 单方面定稿）。
- **铁律**：★10、★20。

## 第 3 步　本体顶层设计【闸门②】
- **输入**：第 1/2 步。
- **动作**：界定本体设计理念与范围；规划 TBox/ABox 分层与资产组织；定义命名空间与 `owl:imports` 拓扑；勾出**顶层类层级框架**（根类/主干）；每项决策标出处。**产出初稿后交客户审阅，根据客户反馈反复修订打磨，直至客户明确同意本体顶层设计为止**——此过程可能多轮往返，每轮修订后须重新交客户确认。
- **产出**：`design/<Xxx>应用-本体顶层设计.md`。
- **验收**：顶层类框架覆盖流程设计的每个业务概念域；命名空间/import 闭合；无硬编码业务数据；**客户已明确同意本体顶层设计**（非仅 AI 单方面定稿）。
- **铁律**：★8/9/10、★20。

## 第 4 步　本体核心类、属性与关系设计【闸门③】
- **输入**：第 3 步已确认的顶层设计。
- **动作**：设计类层级明细、对象属性（`inverseOf`、定义域/值域）、数据属性（数值用数值类型）、约束（`owl:Restriction`）、SWRL 规则；每条约束标出处；区分 TBox/ABox。**产出初稿后交客户审阅，根据客户反馈反复修订打磨，直至客户明确同意核心设计为止**——此过程可能多轮往返，每轮修订后须重新交客户确认。
- **产出**：`design/<Xxx>应用-本体核心设计.md`。
- **验收**：类/属性覆盖流程每个业务概念；约束用 `Restriction`；数值属性为数值类型；**客户已明确同意核心设计**（非仅 AI 单方面定稿）。
- **铁律**：★8/9/10、12、14、★20。

## 第 5 步　生成 BPMN（含 UI）
- **输入**：定稿流程设计。
- **动作**：环节→`serviceTask`（jobType 字面量）；分支→排他网关（条件互斥完备）；产出 REST + 前端页面；补 BPMNDI。**生成过程中若发现需要修改流程设计或本体设计，须找客户确认**（见 SKILL.md §3.2）——既可以修改程序也可以修改本体解决时，**优先修改程序**；所有约束、数据外置于本体；简单判定和分类规则尽量利用 SWRL；程序只处理复杂的逻辑和计算。
- **产出**：`ontology/bpmn/<xxx>Process.bpmn` + UI（`static/index.html` + `web/<Xxx>Controller`）。
- **验收**：节点齐备、连线双向一致、Start→End 可达、网关条件互斥、每个 serviceTask 的 jobType 有 Worker 承接；**若有流程/本体修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：4（结构校验）、★20。

## 第 6 步　生成单文件本体（含典型 ABox 数据）【闸门⑦】
- **输入**：已确认的本体顶层 + 核心设计。
- **动作**：生成**单文件** `<xxx>-all.owl`（TBox + 典型 ABox）；写 `catalog-v001.xml`；数值属性用数值类型；**本步不拆分**；生成后把**典型 ABox 数据**（个体集/类型/关键断言/代表性）交业务确认（闸门⑦）。**生成过程中若发现需要修改流程设计或本体设计，须找客户确认**（见 SKILL.md §3.2）——既可以修改程序也可以修改本体解决时，**优先修改程序**；所有约束、数据外置于本体；简单判定和分类规则尽量利用 SWRL；程序只处理复杂的逻辑和计算。
- **产出**：`ontology/<xxx>-all.owl` + `catalog-v001.xml`；典型 ABox 确认留痕于《<Xxx>应用-本体核心设计》§ABox 典型个体设计。
- **验收**：Openllet 一致性通过；imports 闭合；`Restriction` 与设计表逐条对应；典型 ABox 可加载推理，且已获**闸门⑦**确认；**若有流程/本体修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：12、9/10、★20。

## 第 7 步　应用架构设计与 JobWorker【闸门④】
- **输入**：第 2/3/4/5 步。
- **动作**：① 产出应用架构设计；② **逐节点**与业务确认**实现方法与算法**（闸门④）——**实现方法载体不限**（一段自然语言描述 / 一段程序 / 一个外部调用等），并说明业务规则与算法口径；③ 实现 `<Xxx>OntologyJobWorker`/`<Xxx>Application`/`web/<Xxx>Controller`/`application.yaml`；④ 逻辑走现存 API；⑤ 新建 IDEA Run Configuration（主类 `<Xxx>Application`，启动应用即注册并运行 `<Xxx>OntologyJobWorker` 全部 `@JobWorker`），**须落工作区根（IDEA 工程根）的 `.idea/runConfigurations/`（非模块内，否则聚合工程下不可见）**，**`Working directory` = `$MODULE_WORKING_DIR$`**（相对路径与 EnvPrepare 向上查找均以模块根为基准）；⑥ **照 `OntologyFrameworkExample/start-env.cmd` 生成配套环境启停脚本** `<模块根>/start-env.cmd`（一键 `createdb`→`start`(新窗口常驻)→`create-rabbitmq`，`%~dp0` 定位、`chcp 936`、渐次 errorlevel 校验；停止=关闭常驻窗口；**须 GBK + CRLF**）；⑦ **把 `EnvPrepare-<version>.jar`（可执行 fat jar）复制到模块根**（与 `start-env.cmd` 同目录，脚本以 `%~dp0` 定位它，**缺失则运行即报「未找到 EnvPrepare 可执行 jar」而失败**；来源 `OntologyMachine/build/EnvPrepare-<version>.jar`，或 `OntologyFrameworkExample-*-project.zip` 内已注入的同名 jar）；⑧ **照 `OntologyFrameworkExample/README.md` 的形态在模块根生成 `README.md`**（模板 `templates/应用README模板.md`：工程说明 + 打包/发布/运行）；⑨ **`pom.xml` 含打包配置**（照 Example：`spring-boot-maven-plugin` / `maven-surefire-plugin(useManifestOnlyJar=false)` / `maven-source-plugin(jar-no-fork)`）；⑩ **把新模块登记进工作区根聚合 `pom.xml` 的 `<modules>`**（新增 `<module>OntologyFrameworkXxx</module>`，与 `<module>OntologyFrameworkExample</module>` 并列；**未登记则 IDEA 打开工作区看不到该模块、`$MODULE_WORKING_DIR$` 亦无法解析**；登记后重载 Maven 工程即可见）。
- **产出**：`design/<Xxx>应用-应用架构设计.md` + 主代码三件套 + 配置 + `pom.xml`（含打包插件）+ **`README.md`（工程说明 + 打包/发布/运行）** + **`<工作区根>/.idea/runConfigurations/<Xxx>Application.xml`（IDEA 运行配置，须落工作区根/工程根）** + **`start-env.cmd`（环境启停脚本）** + **`EnvPrepare-<version>.jar`（环境启动器可执行 jar，置于模块根）** + **工作区根聚合 `pom.xml` 的 `<modules>` 新增 `<module>OntologyFrameworkXxx</module>`**。
- **验收**：BPMN `serviceTask` ⇄ `@JobWorker(type)` 一一对应；每 Worker 的**实现方法与算法**可指确认记录；无硬编码业务数据；realize 慢时用迷你推理上下文；**IDEA 运行配置已落工作区根（工程根）`.idea/runConfigurations/`、非模块内**，其 `Working directory` = `$MODULE_WORKING_DIR$`；**`start-env.cmd` 已生成于模块根、为 GBK + CRLF、含三步（照 Example 形态）**；**模块根含 `EnvPrepare-<version>.jar`（可执行）且与 `start-env.cmd` 同目录**；**模块根含 `README.md`（照 Example 形态）**；**`pom.xml` 含三插件打包配置**；**工作区根聚合 `pom.xml` 的 `<modules>` 已含 `<module>OntologyFrameworkXxx</module>`（与 `OntologyFrameworkExample` 并列）**；**若有流程/本体修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：★20、14、17、★21、★22、13。

## 第 8 步　测试设计与用例【闸门⑤】
- **输入**：第 2–7 步。
- **动作**：① 测试设计文档（分层/环境/数据/用例清单/覆盖矩阵）；② 实现测试类（BPMN 端到端、SWRL+消息、本体合规、SKOS）；③ 聚合入口 `All<Xxx>SuiteTest`；④ 正向+边界+负向齐备，BPMN 用生产 Worker 消费。⑤ **本步起本体和程序已固定**：测试中发现的问题，**优先修改测试程序**；**如果需要修改本体或本体应用（JobWorker/Controller 等），须找客户确认**后方可修改，并同步所有设计文档（见 SKILL.md §3.2）。
- **产出**：`design/<Xxx>应用-测试设计文档.md` + `src/test/java/.../*`。
- **验收**：每节点/每约束有用例；边界场景列示；可驱动 BPMN 走完拓扑；**本步完成后进行回归测试，确保回归全对后才进行第 9 步**；**若有本体/本体应用修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：4、2、3、★8、★20。

## 第 9 步　TBox/ABox 分离为两个 owl 文件【闸门⑧】
- **触发**：ABox 不参与推理且量大（>200）。
- **动作**：⓪ **执行前**与业务确认**是否进行 TBox/ABox 分离**（闸门⑧）——**不分离则跳过本步**（保持单文件）；① 拆分出 `<xxx>-tbox.owl` 与 `<xxx>-abox.owl`（**两个独立 owl 文件**）；② 主入口 `<xxx>-all.owl` 对 ABox 的 `owl:imports` **注释掉**（★55）；③ 更新 `catalog-v001.xml`。**ABox 不进数据库**（入库属第 11 步）。
- **产出**：`ontology/<xxx>-tbox.owl` + `ontology/<xxx>-abox.owl`（+ 更新 all/catalog）；分离决策留痕于《<Xxx>应用-本体顶层设计》§TBox/ABox 分层策略。
- **验收**：TBox 独立可推理；两文件各自可解析；主本体一致性不破（★55：ABox 只搬不删）；已获**闸门⑧**确认（或留痕「不分离」）；**本步完成后进行回归测试，确保回归全对后才进行第 10 步**；**若有本体/流程修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：★20、11、★55、56。

## 第 10 步　TBox 拆分（条件）【闸门⑨】
- **触发**：TBox 较大。
- **动作**：**和第 2~4 步一样反复打磨，找客户确认后进行下一步**——先与客户确认**是否进行 TBox 拆分**及**拆分粒度**（闸门⑨，不拆分则跳过），产出初稿后交客户审阅，根据客户反馈反复修订打磨，**直到客户明确同意为止**；确认拆分后，按业务域切分子本体；`owl:imports` + `catalog-v001.xml` 组织；内聚/低耦合。
- **产出**：拆分后的 `ontology/<xxx>-*.owl` + 更新 `catalog-v001.xml`；拆分决策留痕于《<Xxx>应用-本体顶层设计》§TBox/ABox 分层策略。
- **验收**：语义不变；子模块可单独校验；imports 无循环；已获**闸门⑨**确认（或留痕「不拆分」）；**客户已明确同意拆分方案**；**本步完成后进行回归测试，确保回归全对后才进行第 11 步**；**若有本体/流程修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：★20。

## 第 11 步　典型 ABox 数据导入数据库（库环境 + OBDA）【闸门⑩】
- **动作**：⓪ **执行前找客户确认数据库信息**（闸门⑩）——确认**是否使用数据库**（**不使用则跳过本步**，ABox 仍以 owl 承载）；若使用，确认**库表结构来源**（①客户提供现成库表结构 / ②按本体**新建**库表 / ③**导入已有**数据库表结构），**客户提供的须以其实际给出为准，不得臆造**；① 生成 `createdb_tables.ddl` + `data.sql`（典型 ABox 入库）；② 生成 `<xxx>.obda` + `<xxx>.properties`；③ 配置补 `ontology.obda-path`/`obda-properties-path`，复用 `OntologyService`；④ `EnvPrepare createdb` 建库灌数、`EnvPrepare start` 拉起环境。
- **产出**：`ontology/database/{createdb_tables.ddl, data.sql, <xxx>.obda, <xxx>.properties}`；用库决策与库表来源留痕于《<Xxx>应用-应用架构设计》。
- **验收**：库建成、典型数据入库；经 OBDA 可 SPARQL 访问；映射与本体 IRI 一致；已获**闸门⑩**确认（或留痕「不用库」）；**本步完成后进行回归测试，确保回归全对后才进行第 12 步**；**若有本体/流程修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：★8、★10、★20、11、★21（复用加载）、★1/2/19（环境构建）。
