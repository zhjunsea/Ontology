# 步骤规范（14 步 · 输入/动作/产出/验收）

> 与 `SKILL.md` §3 配套的**深度规范**。每步给出：输入 → 动作清单 → 产出 → 验收判据 → 关联铁律。
> 通用红线：**完全按业务、不编造**；产出参考 `Example-文件映射.md`。
> **闸门执行口径（对齐 `SKILL.md` §0.5 闸门策略）**：各步 `【闸门X】` 默认「确认」；开工前由客户一次性逐项选择每个闸门「跳过/确认」形成《闸门策略表》后，**严格按此执行**——「跳过」的闸门产出后直接推进并留痕「按策略跳过」，「确认」的闸门停下→展示产出→请求确认→等回复；未在策略中授权跳过的闸门一律按「确认」处理，AI 不得擅自跳过、不得批量确认、不得替代业务裁定（★铁律20）。

---

## 第 1 步　明确业务场景与目标范围
- **输入**：业务场景描述（用户提供）；如给出领域黄金标准/语料位置，一并作为输入。
- **动作**：
  1. 提炼目标；
  2. 划定范围与**不在范围**项；
  3. 识别角色/关键对象/关键约束；
  4. 无法确认处标「待业务确认」，**不得臆造**；
  5. **★黄金标准逐章逐字解析（输入指定了领域黄金标准/语料位置时必做）**：解析并理解该黄金标准/语料——**指定了具体章节则读指定章节，未指定则一章一章依次读取**，不得跳章；**逐字逐句**完整理解并抽取，**不得仅读目录或框架**；每抽取完一章**须再次读取提取核查缺失，有缺失则补充修复，循环往复直至该章完全读取**方可进入下一章；直到**所有标准读取完毕**；重点抽取与**场景、目标相关**的内容；**全过程不编造、每条有依据**。抽取结果作为第 2 步流程设计与第 3/4 步本体设计的依据。
- **产出**：`design/<Xxx>应用-顶层设计.md` §概述与定位、§范围；若输入指定了黄金标准/语料，另附「黄金标准解析与依据」节承载逐章抽取结果。
- **验收**：场景每个业务名词在后续有落点或显式声明不建模；「待确认」项已登记；若输入指定了黄金标准/语料，其解析与抽取已**逐章逐字完成、迭代至无缺失且每条有依据**。
- **铁律**：★10（有依据）、★20（待确认项带入闸门）。

## 第 2 步　流程设计【闸门①】
- **输入**：第 1 步范围。
- **动作**：拆「环节 → 输入 → 处理 → 输出 → 分支」；纯业务语言；标注待业务裁定的分支/边界。**产出初稿后交客户审阅，根据客户反馈反复修订打磨，直至客户明确同意流程设计定稿**——此过程可能多轮往返，每轮修订后须重新交客户确认。
- **产出**：`design/<Xxx>应用-流程设计.md`。
- **验收**：每环节输入/输出明确；每个排他分支条件**互斥且完备**；**客户已明确同意流程设计**（非仅 AI 单方面定稿）。
- **铁律**：★10、★20。

## 第 3 步　数据层（Data）设计【闸门②】
- **输入**：第 1/2 步；方法依据 `references/本体构建方法论-业务对象识别驱动法.md`（业务对象四原则）。
- **动作**：① 界定范围（L1 主题域分组 / L2 主题域**只作治理分类**——命名空间 + `AnnotationProperty`，不建 `owl:Class` 逻辑）；② **从「业务视角」识别业务对象（L3）**——业务对象是业务人员关心的重要人/事/物（业务概念），**禁止用「IT 视角」**（数据库表、系统模块、界面字段、DTO/接口/服务、代码类、技术组件等 IT 实现对象）替代；再按四原则（见方法论第 3 章，须逐条校验：①不可或缺且有唯一数据 Owner；②全企业唯一身份标识；③相对独立并有属性描述、无包含从属；④可实例化）过滤（不符合「唯一标识 + 独立生命周期」者归为组成类或属性）→ `owl:Class` + `owl:hasKey`（唯一标识）；③ 识别属性与关系（L5）：`owl:DatatypeProperty`（数值用数值类型）/ `owl:ObjectProperty`（`inverseOf`、定义域/值域）/ `owl:AnnotationProperty`（治理元数据）**三类分清**；④ 一对多明细按 **`hasPart` 组成类方案**（部分类复合 `owl:hasKey`、`部分 ⊑ ∃isPartOf.整体`、`hasPart`/`isPartOf` 互逆，见方法论第 7 章）；⑤ L4 逻辑数据实体**不建类**；登记「业务对象↔逻辑数据实体(1:N)↔物理表/视图(一对一，含 一对一/主从/主扩；3NF；关系可单独成关系型实体)」映射供第 11 步 OBDA（一个类可多 `mappingId`/视图，不得压成"业务对象=一张表"）；⑥ 规划 TBox/ABox 分层与资产组织、命名空间与 `owl:imports` 拓扑、勾出顶层类层级框架；⑦ 每项决策标出处（**可选增强**：识别前可先按方法论第 16 章「29 句话」/第 15 章「7+1」结构化采集，见方法论第 5 章 v1.1 补充）。**产出初稿后交客户审阅，根据客户反馈反复修订打磨，直至客户明确同意数据层设计为止**——此过程可能多轮往返，每轮修订后须重新交客户确认。
- **产出**：`design/<Xxx>应用-数据层设计.md`。
- **验收**：流程设计的每个业务概念均有落点（业务对象类或显式声明不建模）；每个业务对象满足四原则且设 `owl:hasKey`；属性三类分清（治理 annotation 与逻辑属性不混）；L4 未错误建类；命名空间/import 闭合；无硬编码业务数据；**客户已明确同意数据层设计**（非仅 AI 单方面定稿）。
- **铁律**：★8/9/10、12、14、★20。

## 第 4 步　逻辑层（Logic）+ 行动层（Action）设计【闸门③】
- **输入**：第 2 步流程设计（提供动作与数据来源）+ 第 3 步已确认的数据层设计 + 第 1 步登记的经典/黄金标准（提供「经典对象规则」）。
- **动作**：① **逻辑层（Logic）＝OWL 公理/规则/事理（≈新书『事理层』，≠华为『逻辑数据模型』）**：逐业务对象/关系设计约束——`owl:Restriction`（基数/值域/受限存在）、类公理（`owl:disjointWith`/`complementOf`/必要时 `equivalentClass`）、`owl:propertyChainAxiom`、SWRL 规则（简单判定/分类用 SWRL、复杂逻辑留给程序；编写须避开易错点，见《逻辑与行动层设计模板》§5「SWRL 编写要点」）、SHACL 校验形状；每条标出处；② **行动层（Action）｜仅对需本体推理/约束的动作建过程类，纯编排交 BPMN**：把**需要本体约束**的业务动作建模为**动作（过程）类**，定义输入/输出、前置/后置条件及对业务对象的操作（产生/修改/消耗/查询，用 `owl:ObjectProperty` 关联），形成过程子本体 `{app}-processes.owl`，产出「动作↔流程节点对照表」（依据《华为数据之道》4.4「对象/过程/规则数字化」与新书 4.1.2「事实–事理–行动」）；③ 打通两层耦合（动作前/后置条件引用逻辑层约束/SWRL），**仅做语义建模、不做流程编排、不写代码**（编排属第 5 步 BPMN、代码属第 7 步 JobWorker）；④ 区分 TBox（逻辑/动作定义）与 ABox（过程实例，实例化留第 6 步）。**产出初稿后交客户审阅，根据客户反馈反复修订打磨，直至客户明确同意逻辑层 + 行动层设计为止**——此过程可能多轮往返，每轮修订后须重新交客户确认。
- **产出**：`design/<Xxx>应用-逻辑与行动层设计.md`。
- **验收**：约束用 `owl:Restriction`（非注释）；数值属性为数值类型；SWRL 遵循易错清单；**流程每个动作环节都有对应动作类且输入/输出/前置/后置条件齐全、可追溯流程与经典**；行动层仅语义、不含流程编排或代码；无硬编码业务数据；**客户已明确同意逻辑层 + 行动层设计**（非仅 AI 单方面定稿）。
- **铁律**：★8/9/10、12、14、★20。

## 第 5 步　生成 BPMN（含 UI）
- **输入**：定稿流程设计。
- **动作**：环节→`serviceTask`（jobType 字面量）；分支→排他网关（条件互斥完备）；产出 REST + 前端页面；补 BPMNDI。**生成过程中若发现需要修改流程设计或本体设计，须找客户确认**（见 SKILL.md §3.2）——既可以修改程序也可以修改本体解决时，**优先修改程序**；所有约束、数据外置于本体；简单判定和分类规则尽量利用 SWRL；程序只处理复杂的逻辑和计算。
- **产出**：`ontology/bpmn/<xxx>Process.bpmn` + UI（`static/index.html` + `web/<Xxx>Controller`）。
- **验收**：节点齐备、连线双向一致、Start→End 可达、网关条件互斥、每个 serviceTask 的 jobType 有 Worker 承接；**若有流程/本体修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：4（结构校验）、★20。

## 第 6 步　生成单文件本体（含典型 ABox 数据）【闸门⑦】
- **输入**：已确认的数据层 + 逻辑与行动层设计。
- **动作**：生成**单文件** `<xxx>-all.owl`（TBox + 典型 ABox）；写 `catalog-v001.xml`；数值属性用数值类型；**SWRL 字面量用 property-element 序列化、`owl:withRestrictions` 的 facet 须为合法 RDF 列表**（否则报 `malformed list` 且 facet 丢失），避开 Openllet 易错点（见《逻辑与行动层设计模板》§5）；**本步不拆分**；生成后把**典型 ABox 数据**（个体集/类型/关键断言/代表性）交业务确认（闸门⑦）。**生成过程中若发现需要修改流程设计或本体设计，须找客户确认**（见 SKILL.md §3.2）——既可以修改程序也可以修改本体解决时，**优先修改程序**；所有约束、数据外置于本体；简单判定和分类规则尽量利用 SWRL；程序只处理复杂的逻辑和计算。
- **产出**：`ontology/<xxx>-all.owl` + `catalog-v001.xml`；典型 ABox 确认留痕于《<Xxx>应用-逻辑与行动层设计》§ABox 典型个体设计。
- **验收**：Openllet 一致性通过；imports 闭合；`Restriction` 与设计表逐条对应；典型 ABox 可加载推理，且已获**闸门⑦**确认；**若有流程/本体修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：12、9/10、★20。

## 第 7 步　应用架构设计与 JobWorker【闸门④】
- **输入**：第 2/3/4/5 步。
- **动作**：① 产出应用架构设计；② **逐节点**与业务确认**实现方法与算法**（闸门④）——**实现方法载体不限**（一段自然语言描述 / 一段程序 / 一个外部调用等），并说明业务规则与算法口径；③ 实现 `<Xxx>OntologyJobWorker`/`<Xxx>Application`/`web/<Xxx>Controller`/`application.yaml`；④ 逻辑走现存 API；⑤ 新建 IDEA Run Configuration（主类 `<Xxx>Application`，启动应用即注册并运行 `<Xxx>OntologyJobWorker` 全部 `@JobWorker`），**须落工作区根（IDEA 工程根）的 `.idea/runConfigurations/`（非模块内，否则聚合工程下不可见）**，**`Working directory` = `$MODULE_WORKING_DIR$`**（相对路径与 EnvPrepare 向上查找均以模块根为基准），且 **Shorten command line = `ARGS_FILE`**（Spring Boot 类型字段名 `<option name="SHORTEN_COMMAND_LINE" value="ARGS_FILE" />`；JUnit 套件用 `shortenClasspath`，见第 8 步，二者不可混用）；⑥ **照 `OntologyFrameworkExample/start-env.cmd` 生成配套环境启停脚本** `<模块根>/start-env.cmd`（默认 `start`（新窗口常驻、并确保已声明的持久化服务（MySQL 库 / RabbitMQ 资源）存在——缺则建、有则留），并交互式询问是否「重建环境」→ 选是则 `init`（清空重建已声明的持久化服务）后启动，`%~dp0` 定位、`chcp 936`、errorlevel 校验；停止=关闭常驻窗口；**须 GBK + CRLF**）；⑦ **把 `EnvPrepare-<version>.jar`（可执行 fat jar）复制到模块根**（与 `start-env.cmd` 同目录，脚本以 `%~dp0` 定位它，**缺失则运行即报「未找到 EnvPrepare 可执行 jar」而失败**；来源 `OntologyMachine/build/EnvPrepare-<version>.jar`，或 `OntologyFrameworkExample-*-project.zip` 内已注入的同名 jar）；⑧ **照 `OntologyFrameworkExample/README.md` 的形态在模块根生成 `README.md`**（模板 `templates/应用README模板.md`：工程说明 + 打包/发布/运行）；⑨ **`pom.xml` 含打包配置**（照 Example：`spring-boot-maven-plugin` / `maven-surefire-plugin(useManifestOnlyJar=false)` / `maven-source-plugin(jar-no-fork)`）；⑩ **把新模块登记进工作区根聚合 `pom.xml` 的 `<modules>`**（新增 `<module>OntologyFrameworkXxx</module>`，与 `<module>OntologyFrameworkExample</module>` 并列；**未登记则 IDEA 打开工作区看不到该模块、`$MODULE_WORKING_DIR$` 亦无法解析**；登记后重载 Maven 工程即可见）。
- **产出**：`design/<Xxx>应用-应用架构设计.md` + 主代码三件套 + 配置 + `pom.xml`（含打包插件）+ **`README.md`（工程说明 + 打包/发布/运行）** + **`<工作区根>/.idea/runConfigurations/<Xxx>Application.xml`（IDEA 运行配置，须落工作区根/工程根）** + **`start-env.cmd`（环境启停脚本）** + **`EnvPrepare-<version>.jar`（环境启动器可执行 jar，置于模块根）** + **工作区根聚合 `pom.xml` 的 `<modules>` 新增 `<module>OntologyFrameworkXxx</module>`**。
- **验收**：BPMN `serviceTask` ⇄ `@JobWorker(type)` 一一对应；每 Worker 的**实现方法与算法**可指确认记录；无硬编码业务数据；realize 慢时用迷你推理上下文；**IDEA 运行配置已落工作区根（工程根）`.idea/runConfigurations/`、非模块内**，其 `Working directory` = `$MODULE_WORKING_DIR$`；**`start-env.cmd` 已生成于模块根、为 GBK + CRLF、按 Example 形态以 `start`/`init` 分支启动（含交互式「重建」询问）**；**模块根含 `EnvPrepare-<version>.jar`（可执行）且与 `start-env.cmd` 同目录**；**模块根含 `README.md`（照 Example 形态）**；**`pom.xml` 含三插件打包配置**；**工作区根聚合 `pom.xml` 的 `<modules>` 已含 `<module>OntologyFrameworkXxx</module>`（与 `OntologyFrameworkExample` 并列）**；**若有流程/本体修改，已获客户确认且设计文档已同步**（见 SKILL.md §3.2）。
- **铁律**：★20、14、17、★21、★22、13。

## 第 8 步　测试设计与用例【闸门⑤】
- **输入**：第 2–7 步（含第 1 步登记的经典/黄金标准）。
