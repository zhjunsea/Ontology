## 铁律 4：javac/java 用 @argfile，路径写正斜杠

classpath 太长会 `WinError 206 文件名或扩展名太长`。且 **@argfile 里反斜杠是转义符**，必须换成 `/`：

```python
def fwd(p): return p.replace("\\", "/")
with open(argfile, "w", encoding="utf-8") as f:
    f.write('-cp\n"%s"\n-d\n"%s"\n"%s"\n' % (fwd(full_cp), fwd(outdir), fwd(src)))
subprocess.run([JAVAC, "@" + argfile], ...)
```

生成 classpath：
```powershell
mvn -o -q -pl OntologyFramework dependency:build-classpath "-Dmdep.outputFile=cp.txt"
```
运行 harness 时，**把三个子模块的 `target/classes` 前置**到 classpath（`~/.m2` 的 jar 可能陈旧）：
`OntologyFramework/target/classes` + `OntopOBDAHandler/target/classes` + `OpenlletResolver/target/classes` + cp.txt

## 铁律 6：surefire 必须关闭 manifest-only jar（否则跨模块 ClassNotFoundException）

`OntologyFramework` / `OntopOBDAHandler` / `OpenlletResolver` 三个模块的编译输出目录**都叫 `target/classes`**。
surefire 默认生成 manifest-only jar 时，会把多个同名 `target/classes` 压缩成同一个相对名 `classes`，
运行期只有第一个能解析，其余模块的类抛 **`ClassNotFoundException: com.ocean.ontopobdahandler.ObdaQueryUtils`**。

`OntologyFramework/pom.xml` 的 surefire `configuration` 中必须有：

```xml
<useManifestOnlyJar>false</useManifestOnlyJar>
```

> 症状很有迷惑性：报的是「兄弟模块的类找不到」，容易误判为依赖没装好。实际是 surefire 打包机制问题。

## 铁律 7：BPMN 流程用 zeebe-process-test 内存引擎离线测

`zeebe-process-test-extension` 8.9.6 可在**无 Camunda 服务**的情况下跑通 BPMN 全流程：

```java
@ZeebeProcessTest
class MyFlowTest {
    ZeebeClient client;       // 字段注入，不要自己 new
    ZeebeTestEngine engine;

    private void worker(String jobType, Handler h) {
        client.newWorker()
              .jobType(jobType)
              .handler(h::handle)
              .streamEnabled(false)          // 内存引擎用轮询，必须关流式
              .pollInterval(Duration.ofMillis(50))
              .open();
    }
}
```

关键坑：

- **`streamEnabled(boolean)` 在 `JobWorkerBuilderStep3`**，必须放在 `handler(...)` **之后**，否则编译报错。
- **`<userTask>` 未声明 `zeebe:userTask` 时**，`UserTaskTransformer` 会自动套内置 jobType
  `io.camunda.zeebe:userTask`（常量 `Protocol.USER_TASK_JOB_TYPE`），因此可用普通 Worker 完成，
  **不需要 Tasklist**。
- 断言用 `BpmnAssert.assertThat(instance)`：`isCompleted()` / `hasNoIncidents()` /
  `hasPassedElement(id[,times])` / `hasNotPassedElement(id)` / `hasPassedElementsInOrder(ids...)` /
  `hasVariableWithValue(name,value)`。
- 下游依赖 OBDA/MySQL 的步骤（八纲/六经/方证/方剂…）用**桩 Worker** 替代，只驱动拓扑与变量契约。
- 等待完成要自己轮询 `isCompleted()`（内存引擎没有现成的 await API）。
- `@BeforeEach` 部署 BPMN 后 `@AfterEach` 要 `close()` 所有 worker。

> 若流程改造后要回归「BPMN 与 Worker 契约」，另写一个**纯 DOM 解析**的结构测试（不启引擎），
> 校验：节点齐备、`sequenceFlow` 的 sourceRef/targetRef 可解析、节点 incoming/outgoing 双向一致、
> 从 Start 可达 End 且途经新增节点、网关分支条件互斥、每个 serviceTask 的 jobType 都有对应 `@JobWorker`、
> 每个流节点有 `BPMNShape`、每条连线有 `BPMNEdge`、两份 BPMN 副本字节一致。

## 铁律 8：聚合套件与全部 TCM 测试类同包（`com.ocean.ontologyframework.tcm`）

本工程有**两个等价的总入口**，改一个要同步改另一个：

| 入口 | 位置 | 形式 |
|---|---|---|
| `AllFangzhengSuiteTest` | `com.ocean.ontologyframework.tcm` | JUnit 5 `@Suite` + `@SelectClasses`，IDEA 右键 Run / `-Dtest=AllFangzhengSuiteTest` |
| `FangzhengSuiteRunner` | 同上 | `main` 程序，`DEFAULT_CLASSES` 常量；被 `OntologyMachine/run_all_fangzheng_tests.ps1` 调用 |

两者都已在 `OntologyFramework/pom.xml` 的 surefire `<excludes>` 中排除（`**/AllFangzhengSuiteTest.java`），
否则 `mvn test` 会「套件跑一遍 + 各类再跑一遍」重复执行。`FangzhengSuiteRunner` 不以 `Test` 结尾，surefire 本就不认。

**测试类统一放在 `tcm` 包**（含 `HerbRuleEngineTest`、`SizhenToHerbModificationFlowTest`）：
`src/test/java/com/ocean/ontologyframework/tcm/`。这样套件用**短名**即可引用，`FangzhengSuiteRunner.fqcn()`
只给不含 `.` 的短名补 `com.ocean.ontologyframework.tcm.` 前缀，无需再写全限定名。

**跨包访问生产测试钩子需 `public`**：`TCMOntologyJobWorker` 在 `com.ocean.ontologyframework`（父包），
其 `loadHerbRulesForTest(...)` / `deriveFormulaForTest(...)` 原为**包私有**，测试类一旦移入 `tcm` 子包就会编译失败
（`is not public in com.ocean.ontologyframework.TCMOntologyJobWorker; cannot be accessed from outside package`）。
故这两个钩子必须是 `public`。反之，若把测试类放回父包，则套件（在 `tcm` 包）写 `HerbRuleEngineTest.class` 会失败，
被纳入的测试类本身也必须 `public`（顶层类不加 `public` 即包私有）。

`AbstractJingfangDiagnosisTest` 上的 `StopOnTimeoutExtension` 用**静态**中止标志，同 JVM 内任一用例超时
会连坐跳过其后所有用例；离线测试排最前，环境未就绪时也能先拿到结果。

## 铁律 9：离线 Openllet 回归测试必须「多场景合并进同一本体、只 realize 一次」

Openllet 对**完整 TBox**（`tcm-all.owl`）做一次分类约需 **4 分钟**（CPU 满载、单线程）。
若每个用例各建一个 reasoner（`new OpenlletReasonerFactory().createReasoner(ont)` +
`precomputeInferences(CLASS_ASSERTIONS)`），耗时按用例数线性放大：

> 实测：5 个场景 × 各自建 reasoner = **1217s（20 分钟）**；合并后只需 1 次分类。

**正确写法**：在 `@BeforeAll` 里把 N 个场景建成同一本体中的 N 个患者个体，建**一个** reasoner、
realize 一次，各 `@Test` 只做 `reasoner.getTypes(patient, false)` 查询。

```java
@BeforeAll static void setUp() throws Exception {
    OntologyService os = new OntologyService(readMainPath());
    tbox = os.gettBoxOntology();
    df = tbox.getOWLOntologyManager().getOWLDataFactory();

    Set<OWLAxiom> abox = new HashSet<>();
    addPatient(abox, "scenarioA", syms, pulses, tongues, fuzhengs);   // 场景 1
    addPatient(abox, "scenarioB", syms, pulses, tongues, fuzhengs);   // 场景 2 …

    mgr = OWLManager.createOWLOntologyManager();
    ont = mgr.createOntology(IRI.create("urn:verify:xxx"));
    mgr.addAxioms(ont, tbox.axioms());
    mgr.addAxioms(ont, abox);
    reasoner = new OpenlletReasonerFactory().createReasoner(ont);
    reasoner.precomputeInferences(InferenceType.CLASS_ASSERTIONS);   // 只此一次
}
@AfterAll static void tearDown() { reasoner.dispose(); mgr.removeOntology(ont); }
```

患者 ABox 的构造复刻 `TCMOntologyJobWorker.buildPatientAxioms` 的最小形式：
`Huanzhe` 类型断言 + `you_zhengzhuang` / `you_maixiang` / `you_shexiang` / `you_fuzheng`
四条对象属性断言，且**必须**用

## 铁律 10：一个超时会被静态中止标志伪装成几十个失败 —— 先看耗时分布

`AbstractJingfangDiagnosisTest` 上的 `StopOnTimeoutExtension` 用**静态**中止标志，
同 JVM 内任一用例超时/报错后，**其后全部用例立即失败**。因此一轮 `EXIT=1` 可能只对应**一个**真实问题。

**判别特征（看 surefire 的 `Time elapsed` 列）**：

| 位置 | 耗时 | 含义 |
|---|---|---|
| 首个 error | 接近 100s（如 95.83s） | **真实故障**，看它的异常栈 |
| 其余 error | ≈ 0（0.001~0.003s） | 连坐，**不是**独立故障 |

实测：`TaiyangFangzhengTest` 报 13 errors、`ZabingFangzhengTest` 报 62 errors，
真实原因只有 1 个 —— `t_gegenqinliantang` 的
`io.grpc UNAVAILABLE: io exception` / `java.net.SocketException: Connection reset`，
即 **Camunda/Ontop 在测试运行途中被重启**。单独重跑后 40/40、62/62 全绿。

> **结论**：看到「1 个长耗时 error + N 个 0.00x s error」的分布，
> 先怀疑**环境/连接**（Zeebe 26500 被重启、Worker 未就绪、MySQL 抖动），
> 不要怀疑本体定义或测试数据。**每个测试类单独跑**可彻底规避连坐。

**跑全栈方证套件的正确姿势**：逐类单独 `mvn ... -Dtest=<单个类>`。
8 个类合计 271 个用例，逐类跑约 6 分钟，远优于被连坐后反复排查。

## 铁律 14：改完 Java 必须重启进程；「页面是新的」不等于「代码是新的」

## 铁律 15：「未定」占位符绝不能进候选列表 —— 否则零匹配输入被误判为诊断成功

## 铁律 16：结果形态三态化 —— 只有「完全 realize」才算诊断结论

方证分类必须区分两种来源，**不能混为一谈**：

- **完全 realize**：Openllet 推理把患者个体归入该方证类（`realizedMatches` 非空）→ 这才是**确定性结论**；
- **仅候选**：只是 Jaccard 打分排出来的候选项 → 只能作为**候选**展示，不得冒充结论。

流程与代码的三态映射（v1.4 起）：

| 形态 | BPMN 终止事件 | 网关条件 | `outcome` |
| --- | --- | --- | --- |
| 完全 realize | `EndEvent_Success` | `=fangzhengRealized = true` | `DIAGNOSED` |
| 有候选未 realize | `EndEvent_Candidates` | `=fangzhengRealized = false and fangzhengCandidates != null and fangzhengCandidates != []` | `CANDIDATES` |
| 无候选 | `EndEvent_NoResult` | `=fangzhengRealized = false and (fangzhengCandidates = null or fangzhengCandidates = [])` | `NO_RESULT` |

要点：
1. `Gateway_HasRecommendation` 是**三分支**互斥网关，三条 FEEL 条件必须覆盖且互斥（结构测试
   `outcomeGatewayThreeWayConditions` 守护）。
2. worker 输出 `fangzhengRealized`（boolean）+ `fangzhengCandidates` / `fangzhengCandidatesCn` /
   `fangzhengCandidateDetails`；`fangzhengCandidateDetails[i].hitSymptoms` 是该候选**命中的症状**
   （元素 `{fragment, label}`），供前端逐条展示。
3. `TCMDiagnosisService.outcomeOf` 的判定顺序：`fangzhengRealized=true` → DIAGNOSED；
   `fangzhengCandidates` 非空 → CANDIDATES；旧 fallback → DIAGNOSED；否则 NO_RESULT。
4. 新增终止事件后，**务必同步补 BPMNDI**（`EndEvent_Candidates_di` + `Flow_HasRecommendation_Candidates_di`），
   否则结构测试的「图形信息完整」断言会失败。
5. 验证同样要落到「实际经过哪个终止事件」（见铁律 15 的 element-instances 查询）。

## 铁律 18：候选排序「小定义方证胜出」是 Jaccard 分母被六经症状池灌大的结果

**症状**：临床直觉上该排第一的方证（如 白头翁汤证）排在某个「后世小方」之后（如 温胆汤证）。

**排查三步**（照此顺序，别乱猜）：
1. 看 `fangzhengCandidateDetails` 的 `hits` / `required` / `jaccard` / `hitSymptoms`。
2. 打开本体看该方证的 `equivalentClass`，**特别注意它是否以某个六经类（如 `Jueyinbing`）为合取项**。
3. 看那个六经类的 `equivalentClass` 是否要求多个支路同时成立。

**机制**：`ScoredFangzheng.jaccard() = hits / (patientSize + required - hits)`，而
`required` 由 `OntologyModuleUtils.collectRestrictionFillers` 计算，它会
**递归继承父类/合取类的限制**（`subClassAxiomsForSubClass` + 递归进 named class）。
所以「⊑ 某六经病」的方证，其 `required` 会把**整个六经病的症状池**算进分母：

- 白头翁汤证 ≡ `厥阴病 ∧ 下利 ∧ 里急后重`；厥阴病要求「上热（消渴/气上撞心/心中疼热）**且** 下寒（手足冷/下利/沉微/饥不欲食/吐蛔）」→ required=11。
- 温胆汤证 ≡ `心烦 ∧ 不得眠` → required=2。
- 患者「下利，里急后重，脉大，苔黄，不得眠」（5 症）：
  温胆汤证 1/2 → 1/(5+2-1)=**0.167**；白头翁汤证 2/11 → 2/(5+11-2)=**0.143** → 小定义方证胜。

**关键推论**：这类方证**永远不会 realize**，因为它的 `equivalentClass` 含六经合取项，
而六经定义若太窄（如厥阴病要求上热下寒俱全），纯「热利下重」患者推不出厥阴病。
**验证手法**：补上该六经病的完整证候再跑一次——若立刻 realize 并给出正确方证，
就证明是「六经定义过窄」而非「方证定义错误」。
（实测：`消渴，气上撞心，心中疼热，下利，里急后重` → DIAGNOSED / 厥阴病 / 白头翁汤证。）

**修复方向（择一，需医学判断，勿擅自改本体）**：
- 本体侧：该方证不以六经类为必要条件；或放宽六经定义；或给方证独立充分条件。
- 打分侧：`required` 不计继承来的六经级症状池；或改用「本方证自身鉴别症状覆盖率」；
  或对高特异性症状（里急后重/下利）加权。

## 铁律 19：区分「呈现语义」与「排序语义」——改前者不要声称修了后者

排查「为什么给出 X 方证」时，先 `git log` / `git diff` 确认**当前改动到底动了什么**。
本工程曾出现：未 realize 时旧代码 `fangzheng = displayScored.get(0).fragment()`
**直接把 Jaccard Top1 候选当成方证**（仅服务端 `log.warn`，用户不可见）；

## 铁律 20：扫描本体 OWL 源文件时，必须正确识别自闭合标签

用 Python 正则/深度计数扫 `<owl:Class rdf:about="#X">…</owl:Class>` 块时，
**`<owl:Class rdf:about="#Y"/>`（自闭合）大量出现在 `owl:intersectionOf` / `owl:unionOf` 内部**。
若只按「找到 `<owl:Class` 就 depth+1」计数，这些自闭合标签会让 depth 永不归零 →
**一个「块」吞掉整个文件** → 后续所有统计全错。

**症状**：统计出「每个症状都被 6 个经病全覆盖」这类荒谬结果（第一版扫描的假结果）。

**正确做法**：`find('>')` 后检查**前一个字符**是否为 `/`：

```python
def extract_blocks(text, tag="owl:Class"):
    out, key = [], "<" + tag
    i = 0
    while True:
        s = text.find(key, i)
        if s < 0: break
        te = text.find(">", s)
        if te < 0: break
        if text[te-1] == "/":            # ← 自闭合，直接收下，不进深度计数
            out.append(text[s:te+1]); i = te + 1; continue
        close = "</" + tag + ">"; depth = 1; j = te + 1
        while depth > 0:
            nxt_o = text.find(key, j); nxt_c = text.find(close, j)
            if nxt_c < 0: break
            if 0 <= nxt_o < nxt_c:
                te2 = text.find(">", nxt_o)
                if te2 > 0 and text[te2-1] != "/": depth += 1
                j = te2 + 1
            else:
                depth -= 1; j = nxt_c + len(close)
        out.append(text[s:j]); i = j
    return out
```

**自检**：`len(extract_blocks(open(f).read()))` 应等于该文件的类数
（`tcm-zhengzhuang.owl` = 576、`tcm-maixiang.owl` = 68、`tcm-shexiang.owl` = 71）。
若远大于此，说明深度计数坏了。

## 铁律 21：三个「象」文件的层级状况完全不同 —— 症状是扁平的

做任何「按症状/脉/舌归类」的统计或推理前，先知道这个事实：

| 文件 | 类数 | 层级 | 证据 |
|---|---|---|---|
| `tcm-maixiang.owl`（脉象） | 68 | ✅ **已分层 + 已有组合层** | 38 个复合脉用**多重 `subClassOf` + `equivalentClass` 交**：`Fujinmai 浮紧脉 ⊑ Maixiang, Fumai, Jinmai` |
| `tcm-shexiang.owl`（舌象） | 71 | ⚠️ **有分类树，但无组合层** | 7 个维度（舌质颜色/舌苔/舌形/舌态/舌下络脉/舌面润燥/苔色苔质），**`equivalentClass` 0 处、`intersectionOf` 0 处** |
| `tcm-zhengzhuang.owl`（症状） | 576 | ❌ **扁平** | **563/576（97.7%）** 直接 `subClassOf Zhengzhuang`，仅 ~13 个有其它父类 |

**量化对比（判断「有没有组合层」的快捷手法）**：

```python
t.count('equivalentClass'), t.count('intersectionOf')
# tcm-maixiang.owl → 78, 76   ← 有组合层
# tcm-shexiang.owl →  0,  0   ← 无组合层（红舌与黄苔在两条互不相干的支路上）
```

**复合脉的现成模板**（舌象/症状要建组合层时照抄）：

```owl
<owl:Class rdf:about="#Fujinmai">
    <rdfs:subClassOf rdf:resource="#Maixiang"/>   <!-- 根 -->
    <rdfs:subClassOf rdf:resource="#Fumai"/>      <!-- 原子 1 -->
    <rdfs:subClassOf rdf:resource="#Jinmai"/>     <!-- 原子 2 -->
    <rdfs:label xml:lang="zh">浮紧脉</rdfs:label>
    <rdfs:comment xml:lang="zh">《伤寒论》3条、35条：伤寒，麻黄汤证核心脉。</rdfs:comment>
    <owl:equivalentClass><owl:Class><owl:intersectionOf rdf:parseType="Collection">
        <owl:Class rdf:about="#Fumai"/><owl:Class rdf:about="#Jinmai"/>
    </owl:intersectionOf></owl:Class></owl:equivalentClass>
</owl:Class>
```

模式 = **多重 `subClassOf`（供归类）+ `equivalentClass` 交（供定义）+ `rdfs:comment` 引条文**。

**推论（很重要）**：
- 「脉舌能归类、症状不能归类」的根因是**结构问题，不是医学问题**。
- `干呕` / `呕` / `吐` / `哕` / `噫气` 在症状本体里是**平级兄弟类**，本体不知道它们相关。

## 铁律 22：`belongsToLiujing` 是「篇章归属」，不是「八纲归属」

`belongsToLiujing` 记录的是方证在《伤寒论》**篇章中的位置**，与胡希恕体系的八纲归属**不一致**。

**铁证**：`shaoyin_taiyin.owl` 的 `Sinitangzheng`（四逆汤证）：
```
belongsToLiujing = 少阴病
you_zhengzhuang  = 手足冷、下利清谷     ← 两个都是「里寒」症状
```
- 本体：四逆汤证 → 少阴病（少阴病篇位置）
- 胡希恕：四逆汤证 → **太阴病（里阴证）**；少阴病是**表阴证**（麻黄附子细辛汤类）

**后果**：拿 `belongsToLiujing` 推病位，`下利清谷` 会被算成「表」，与医理「里」直接冲突；
大量「里」症状因挂在少阴/厥阴方证下被算成「表/半表半里」→ **普遍多值**。

**用法约束**：
- ❌ 不要用它推导八纲（病位/病性）。
- ✅ 只用于**校验/展示**（辨出的六经 vs 方证归属，不符则报警）。
- 统计判据资格时，**合病方证（`belongsToLiujing` 多值）必须排除**，否则症状分布被「灌宽」
  （例：呕吐 全口径=表,里；仅单经方证=**里**）。

## 铁律 23：八纲判据的准入标准 —— 必须能定八纲；定不了的**不是「低级别」，而是「不在这张表里」**

给八纲写判据时的**准入标准**（用户定）：**每条判据必须能定八纲**。

**⚠️ 已废弃的四级模型（v2/v3 的 A/B/C/D）**：曾把「定不了八纲、只定证素」的舌象列为 **D 级**。
**用户裁定这是概念错误**：「定不了八纲感觉没有意义，为啥要建 D 级？」
→ **D 级取消**。定不了八纲的舌象**不是判据的低级别**，而是**证候组合层的成员**（见铁律 24）。

**现行模型（v4）：两层分离**

| 层 | 目标 | 舌象成员 | 落点 |
|---|---|---|---|
| **八纲判据层** | **八纲** | **A 级**（单象定）：淡白舌→`Han`+`Xu`、红舌→`Re`、绛舌→`Re`、黄苔→`Re`<br>**B 级**（组合才定）：黑燥苔→`Re`、黑滑苔→`Han`、灰燥苔→`Re`、灰滑苔→`Han` | 挂**具体**的 `Han`/`Re`/`Xu`/`Shi`（阴阳靠 4 条 axiom 上溯）；病位判据挂 `Biao`/`Li`/`Banbiaobanli` |
| **证候组合层** | **证候/证素** | Z-1 瘦薄舌⊓淡白舌→气血两虚；Z-2 瘦薄舌⊓红绛舌→阴虚火旺；Z-3 点刺舌⊓大热→脏腑热盛；Z-4 灰腻苔→湿浊<br>单象→证素：紫舌/青舌→血瘀、胖大/齿痕→水湿、裂纹→津伤、腻/腐→湿浊、剥/镜面/无苔→胃气伤、舌下络脉→血瘀、白苔→表/寒/湿、薄/厚→病位、润/滑/燥/糙→津液 | `⊑ ZhengHouZuhe`，再由证候→八纲 |

**组合必要性判据（用户铁律 5）**：**能单独定的就直接定，不加组合**（加组合是冗余）；
**组合只在「单个不能定」时才需要**。

| 组合 | 八纲层 | 证候层 |
|---|---|---|
| 淡白舌⊓白苔 | ❌ 冗余（淡白舌已定阴） | ❌ 也冗余（白苔不带新证素） |
| 紫舌⊓畏寒 | ❌ 冗余（畏寒已定阴） | ✅ 可留（寒凝血瘀是证候） |
| 瘦薄舌⊓舌色 | ❌ 冗余（舌色已定阴阳） | ✅ 进（气血两虚 / 阴虚火旺） |
| 点刺舌⊓大热 | ❌ 冗余（大热已定阳） | ✅ 进（脏腑热盛） |
| 灰腻苔 | 本就不定八纲 | ✅ 进（湿浊证素） |

→ **八纲判据层里真正需要组合的只有灰黑苔 4 个**（单看苔色定不了寒热）。

**两条关键医理（有医书依据，勿凭直觉改）**：

1. **舌象不能单独定病位**。依据《医门棒喝》：**「望舌不过察病之标，必合脉症方得其本。」**
   表证舌象基本正常（淡红舌薄白苔，正常人也如此）→ 无特异性；少阳舌象也无特异性。
   → 「薄苔→表」「厚苔→里」**不能作独立判据**，只能作弱佐证。
2. **黑苔判寒热靠「苔色 + 苔质润燥」组合，不是靠颜色**。
   - 国家中医药管理局《中医基础术语》：「黑苔……主里证，或为热极，或为寒盛。苔黑而**燥裂**……**热极津枯**；苔黑而**滑润**……**寒盛阳衰**」
   - 《伤寒金镜录》：「舌内有黑形如小舌者，乃**邪热结于里**也」
   - 《舌鉴辨证》（寒极）：「**虚寒而舌黑者，则必湿滑无苔，多津，口不苦，唇不燥，无朱点，无芒刺，无罅裂，刮之明净，如水浸猪腰**……是**脏腑极寒**之舌也」
   - **灰苔同理**：《辨舌指南》「**灰色苔者，即黑苔之轻也**……**当与黑苔同治**」→ 灰燥苔→阳、灰滑苔→阴。
   → 该书区分寒热**列了 7 个指征**，不是只看颜色。

**推论：凡「双向」的舌象/症状都不能单独定八纲**，必须与其他证据组合。
- **紫舌/青舌**：既主寒凝血瘀又主热盛血瘀 → 不能单独定病性，更不能靠苔色定，须配症状。
- **白苔**：主表（阳）/寒（阴）/湿 → 双向，不定病性。
- **黑苔、灰苔**：双向，须配苔质润燥。
- **瘦薄舌**：瘦薄而色淡→气血两虚(阴)；瘦薄而色红绛干燥→阴虚火旺(阳) → 双向，靠舌色。
- **点刺舌**：主热盛但特异性不足（正常人舌尖可见）→ 须配大热。
- **积粉苔**：主流主热毒(阳)，但许公岩主「脾胃寒湿之极」(阴) → **有争议，不列 A 级**。

## 铁律 24：两层分离 —— 「八纲判据层」与「证候组合层」是两张表，不是一张表的两个级别

**用户裁定**：「定成 D 级感觉没有意义，为啥要建 D 级？」

**核心**：一个舌象/症状**定不了八纲 ≠ 它是判据的低级别**，而是它**根本不是八纲判据**。

| | 八纲判据层 | 证候组合层（`ZhengHouZuhe`） |
|---|---|---|
| 目标 | **八纲** | **证候 / 证素** |
| 判据资格 | 必须能定八纲 | 不要求定八纲 |
| 组合必要性 | 组合**才**定出八纲 | 组合**坐实**证候 |
| 落点 | `⊑ Han/Re/Xu/Shi`（阴阳靠 axiom 上溯）/ `Biao`/`Li`/`Banbiaobanli` | `⊑ ZhengHouZuhe`，再由证候→八纲 |

**证候组合层允许跨证据层**（舌 ⊓ 症 ⊓ 脉）：如 Z-3「点刺舌 ⊓ 大热」是舌象⊓症状。
这与用户「青紫舌应与其他**症状**组合」的裁定一致。

**OWL 要点**：证候组合类**不写** `⊑ Yin`/`⊑ Yang`（八纲由组合中的舌色/大热成分定，
或本就不定八纲），只写 `⊑ ZhengHouZuhe` + `equivalentClass` 交。

**⚠️ 证候不设「阴阳归属」**（用户裁定：「**阴虚火旺为啥一定要有阴阳归属？这个单一[证候]不能归属，就用组合症状。**」）：

- **证候不是八纲判据，不该有阴阳归属**。问「阴虚火旺属阴还是属阳」是**层次错位** ——
  证候组合层的产物是**证候**，阴阳是**八纲判据层**的事。
- 阴阳由**组合成分**提供（红绛舌→`Re`→阳、淡白舌→`Han`+`Xu`→阴、大热→阳）。
- **不要**在文档/表格里给证候设「证候→八纲」列，也**不要**在 `rdfs:comment` 写「证候→八纲：X」。
- 这正是铁律 5「单个不能定就用组合」的体现：**组合的产物是证候，阴阳来自成分**。

## 铁律 26：**本体不一定正确 —— 以医理和医书为准，本体只是实现**

**用户裁定（原话）**：**「本体不一定正确，要严格按照医理和医书来。」**

设计判据、写 OWL、下结论时，**权威顺序**是：

```
医书 / 医理  >  本体现状
```

**本体只是实现，不是权威**。发现「本体写法」与「医理」冲突时，**以医理为准**，
并把本体视为**待修正的缺陷**（记入待补清单），**不要反过来用本体去否定医理**。

**典型翻车案例（务必记住）**：

| 现象 | 错误做法（拿本体当权威） | 正确做法（以医理为准） |
|---|---|---|
| 本体里 `Danyumei ⊑ {Xu, Yin}` 是**并列** | 断言「`Xu`/`Shi` 不能 ⊑ `Yin`/`Yang`」 | 医理「虚、寒属阴；实、热属阳」→ `Xu ⊑ Yin`、`Shi ⊑ Yang` **是对的**；本体并列 = **缺 axiom** |
| 本体八纲 9 子类**零 axiom** | 认为「八纲就该平级」 | 医理「**阴阳是总纲**，表里寒热虚实为六变」→ 必须补 `Re/Shi ⊑ Yang`、`Han/Xu ⊑ Yin` |
| 本体舌象**零八纲挂载** | 认为「舌象不能定八纲」 | 医理「淡白舌主虚寒、红舌主热」→ A 级 4 个**能定**，本体是**漏挂** |

**医理依据（八纲结构，写判据前先读）**：

- 《医学六要》：「治病大法有八，曰阴、曰阳、曰表、曰里、曰寒、曰热、曰虚、曰实」
- 《景岳全书·传忠录》：「**必须先审阴阳，乃为医道之纲领**」「六变者，**表里寒热虚实**也」
- 《中医诊断学》：「八类证候之间的关系，**并非是彼此平行的**……表、热、实隶属于阳；里、寒、虚统属于阴」
- 胡希恕：「**表里为病位，阴阳为总的病性**」「**表证有阴阳**」「**实、热属阳，虚、寒属阴**」

**推论（判据挂载规则）**：
- 判据挂**最具体**的 `Han`/`Re`/`Xu`/`Shi`（不直接挂 `Yin`/`Yang`），阴阳靠 4 条 axiom 上溯。
- 表/里/半表半里 **不挂阴阳**（胡希恕「表证有阴阳」→ 太阳＝表阳、少阴＝表阴）。
- 六经 `equivalentClass` 只用阴阳 → 补 axiom 后判据可自动推六经。

## 铁律 27：胡希恕「**寒热有常，而虚实无常**」—— 判「虚＋热」类证候阴阳归属的终极依据

**问题**：`阴虚火旺`（虚＋热）到底属阴还是属阳？三种说法都"有道理"：
① 虚属阴→阴；② 热属阳→阳；③ 阴阳俱见。

**答案（胡希恕，冯世纶整理，北京市中医药管理局官网刊载）**：

> 「**寒者必阴，热者必阳，在任何情况下永无变异**。但虚实则不然，当其与寒热交错互见时，反其阴阳，
> 即如虚而寒者，当然为阴，但**虚而热者，反而为阳**。」

**规则**（判定阴阳的优先级）：

| 情形 | 阴阳 | 依据 |
|---|---|---|
| 有**寒**（不论虚实） | **阴** | 寒者必阴（**有常**） |
| 有**热**（含**虚热**） | **阳** | 热者必阳（**有常**） |
| **不寒不热** | 实→阳、虚→阴 | 虚实定阴阳（**无常**，仅在无寒热时生效） |

**关键**：**寒热是「有常」的（决定阴阳，永不反转）；虚实是「无常」的（会被寒热反转）**。
所以「虚属阴」只是**总纲层面的泛言**（胡希恕：「泛言阴，则不定必寒」），
一旦与「热」并见，就被反转。

**推论（写判据/证候→八纲映射时直接用）**：

| 证候 | 组成 | 阴阳 |
|---|---|---|
| 气血两虚 | 虚＋**无热** | **阴** |
| **阴虚火旺** | 虚＋**热**（虚热） | **阳** |
| 阳虚（虚寒） | 虚＋寒 | 阴 |
| 实热 | 实＋热 | 阳 |
| 实寒 | 实＋寒 | 阴 |

→ **同为虚证，因寒热不同而分属阴阳**。这就是「虚实无常」的落地。

**「阴阳俱见」的适用边界**：胡希恕的「阴阳俱见」指**寒热并见**（上热下寒之类 → 厥阴病）。
**只有热、没有寒**的证候（如阴虚火旺）**不是**阴阳俱见，不能套用。

**出处权威性排序**（本项目采用）：
1. 胡希恕「寒热有常，虚实无常」（**判定规则**，专门解决此问题）← **取这个**
2. 《中医诊断学》「表、热、实隶属于阳；里、寒、虚统属于阴」（**总纲概括**）
3. 一般「寒热错杂」套用（**边界不符**，阴虚火旺无寒）

**⚠️ 适用范围（重要，勿越界）**：本原则用于**八纲判据层** ——
当某条**判据**（如复合脉「细数脉」= 虚＋热）同时含虚与热时，用它定阴阳（**虚＋热→阳**）。
**不用于**给**证候组合层**的证候（阴虚火旺等）贴阴阳标签 —— **证候不挂八纲**（见铁律 24）。
「阴虚火旺属阴还是属阳」是**层次错位**的提问，正确做法是**由组合成分提供阴阳**。

## 铁律 28：4 条八纲 axiom —— `Re/Han` 是**硬约束**，`Xu/Shi` 是**可反转默认值**（写本体时勿写死）

**背景**：本体 `Bagang` 下 9 个子类**彼此平级、零 axiom**。依医理（铁律 26）应补 4 条：

```owl
<owl:Class rdf:about="#Re"><rdfs:subClassOf rdf:resource="#Yang"/></owl:Class>
<owl:Class rdf:about="#Shi"><rdfs:subClassOf rdf:resource="#Yang"/></owl:Class>
<owl:Class rdf:about="#Han"><rdfs:subClassOf rdf:resource="#Yin"/></owl:Class>
<owl:Class rdf:about="#Xu"><rdfs:subClassOf rdf:resource="#Yin"/></owl:Class>
```

**⚠️ 但 4 条的性质不同**（依胡希恕「寒热有常，虚实无常」，铁律 27）：

| axiom | 性质 | 理由 |
|---|---|---|
| `Re ⊑ Yang`、`Han ⊑ Yin` | **硬约束**（可放心写死） | 「寒者必阴，热者必阳，**永无变异**」 |
| `Xu ⊑ Yin`、`Shi ⊑ Yang` | **默认值**（**遇寒热反转时失效**） | 「虚而**热**者反而为**阳**；实而**寒**者反而为**阴**」 |

**实施坑（必看）**：若把 `Xu ⊑ Yin` 当硬约束写死，则
**「阴虚火旺」= 虚 + 热 → 会被推理机判成阴证**（错，应为阳证 / 阳虚热证）。
同理 `Shi ⊑ Yang` 写死会把**寒实结胸（实 + 寒）判成阳证**（错，应为阴证）。

**正确做法**：把 `Xu`/`Shi` 的阴阳归属**交给含寒热的复合判据去定** ——
即判据挂 `Han`/`Re`（硬）或挂含寒热的具体组合，**不要**单靠 `Xu`/`Shi` 上溯阴阳。

**实施现状（v4.6，用户确认 ② 后落地）**：4 条 axiom **全部**以 `rdfs:subClassOf` 写入
`tcm-core.owl`（`Han/Re/Xu/Shi` 各加一条 `subClassOf #Yin`/`#Yang`），并各附 `rdfs:comment`
标注「有常/无常」。Openllet 实测：`PaleWhiteTongue → {Han, Xu, Yin}` ✅、`RedTongue → {Re, Yang}` ✅。

> **遗留风险（v4.8 已裁定，方案 A）**：`Xu ⊑ Yin` 写死后，一个同时 ⊑ `Xu` 与 ⊑ `Re` 的类
> （如「阴虚火旺」型判据）会被推断为 **`Yin` 与 `Yang` 并见**（= 寒热错杂 / 阴阳俱见）。
> 这**未必是错**（胡希恕「阴阳俱见 → 厥阴病」）—— **用户已裁定「同时为阴阳也可以，不是问题」**，
> 故**保留硬 ⊑**（方案 A）。**实测（2026-09-18）当前本体无任何实体同时挂「虚+热」或「实+寒」**，
> 硬 ⊑ **暂不产生矛盾**（关键：`ThinTongue` 瘦薄舌**不挂** `Xu`，故 Z-2 阴虚火旺只从红绛舌得阳）。
>
> **医理裁定（v4.8，务必记住）**：`Xu ⊑ Yin`/`Shi ⊑ Yang` **作为「默认值（多属）」医理成立，
> 作为「硬约束（必属）」医理不严谨** —— 医书用「**多属**」（《中医诊断学》「里、寒、虚多属阴」），
> 胡希恕用「**无常**」。故本体写成硬 ⊑ 是**有意的工程妥协**（OWL 无默认值语义），
> **必须用 `rdfs:comment` 标注「默认，非必属」**，并在推理层遵守「**有寒热则从寒热**」。
>
> **未来风险（实施 ⑤/⑥ 前须裁定）**：一旦新增「虚+热」判据（细数脉、虚热证）或「实+寒」判据
> （寒实结胸），该实体将同时 ⊑ `Yin` 与 ⊑ `Yang` → 六经 `equivalentClass`
> （`Yangmingbing = Li ⊓ Yang`、太阴病 `= Li ⊓ Yin`）可能**同时推出阳明病与太阴病**。
> 备选：**方案 B**（`Xu`/`Shi` 不挂阴阳，全由 `Han`/`Re` 提供；代价：纯虚证失去阴阳）、
> **方案 C**（硬 ⊑ + 推理层覆盖）。详见 `判定依据.md` §8.6。

## 铁律 29：验证 TBox 判据的 Openllet harness —— 只加载 TBox 模块，且必须离线解析 imports

**场景**：改完 `tcm-core.owl` / `tcm-shexiang.owl` 的 `subClassOf`/`equivalentClass` 后，
要**用真实推理机**验证「某类是否被正确推断出八纲」。此时写一个独立 `main`（不启动 Spring）。

### 四条硬约束（都踩过）

| # | 约束 | 症状 / 原因 |
|---|---|---|
| 1 | **只加载 TBox 模块**（如 `tcm-shexiang.owl`，它会自动 import `tcm-core.owl`），**绝不要加载 `tcm-all.owl`** | `tcm-all.owl` 含 ABox/方证模块 → Openllet **跑 >11 分钟无结果**（被迫 kill）。TBox 判据验证加载 `tcm-shexiang.owl` → **秒级**（327 公理） |
| 2 | **必须加 `AutoIRIMapper` 离线映射** | 否则 `UnknownHostException: www.tcm-classics.org`（`owl:imports` 试图联网） |
| 3 | **`Node<OWLClass>` 没有 `getFlattened()`**（OWLAPI v5 已移除） | 用 `.getEntities()` 代替 |
| 4 | **java/javac 命令行过长 → `WinError 206`** | 用 `@argfile`；且 **argfile 里反斜杠是转义符 → classpath 必须写正斜杠**，否则 `NoClassDefFoundError` |
| 5 | **`OpenlletReasonerFactory` 没有 `createReasoner(Set<OWLOntology>)`** | 本 OWLAPI 版本只有 `createReasoner(OWLOntology)`。想同时推理多个模块**不能**传 Set |
| 6 | **`createOntology` + `AddImport` 不会自动加载 imports** | 闭包公理数 = **0**，所有查询返回空（**静默失败，最坑**）。必须**先 `m.loadOntology(IRI)` 显式加载**各模块 |
| 7 | **`OWLReasoner.getTypes()` 只接受 `OWLNamedIndividual`** | 传 `OWLClass` 编译报错 → 用 `getSuperClasses()` |

### 多模块 TBox 的正确加载姿势（约束 5+6 的解法）

```java
OWLOntologyManager m = OWLManager.createOWLOntologyManager();
m.getIRIMappers().add(new AutoIRIMapper(ontologyDir, true));   // IRI → 本地文件
// ① 先按 IRI 显式加载每个需要的模块（这一步不能省！）
for (String mod : new String[]{"core", "zhengzhuang", "shexiang"})
    m.loadOntology(IRI.create("http://www.tcm-classics.org/jingfang/" + mod));
// ② 建内存探针本体，加 imports
OWLOntology probe = m.createOntology(IRI.create("http://www.tcm-classics.org/jingfang#_probe"));
for (String mod : ...) m.applyChange(new AddImport(probe, df.getOWLImportsDeclaration(IRI.create(...))));
// ③ 此时闭包才完整（实测 2458 公理）
OWLReasoner r = rf.createReasoner(probe);
```

### 骨架

```java
OWLOntologyManager m = OWLManager.createOWLOntologyManager();
File f = new File(".../ontology/tcm-shexiang.owl");
m.getIRIMappers().add(new AutoIRIMapper(f.getParentFile(), true));   // ← 约束 2
OWLOntology o = m.loadOntologyFromOntologyDocument(f);
OpenlletReasoner r = OpenlletReasonerFactory.getInstance().createReasoner(o);
r.precomputeInferences();
System.out.println("公理数=" + o.getAxiomCount() + " 一致性=" + r.isConsistent());

// 正向：某类推断出的全部父类（含八纲）
System.out.println(r.getSuperClasses(c, false).getEntities());
// 反向：某八纲类推断出的全部子类（验证 axiom 是否生效）
System.out.println(r.getSubClasses(yin, false).getEntities());
```

### 验证设计要点

- **正反双向**：正向查「判据类 → 八纲」，反向查「八纲 → 判据类」（确认 axiom 生效）。
- **必设对照组**：挑几个**不应**挂八纲的类（如 `PurpleTongue`/`WhiteCoating`/`GreasyCoating`），
  确认它们**推断不出** `Han/Re/Xu/Shi/Yin/Yang` —— 否则说明挂载过宽。
- **回归检查**：顺带打印六经类（`Taiyangbing` 等）的 `Biao/Li + Yang/Yin`，确认没被改坏。
- **模拟患者（最强验证）**：在探针本体里 `AddAxiom` 造一个测试类 ⊑ 成分类（如 ⊑ `ThinTongue` + ⊑ `PaleWhiteTongue`），
  `r.flush()` 后查 `getSuperClasses()` —— 能推出目标证候/八纲才算定义真的生效。

## 铁律 34：**`析取等价类 ⊓ 析取等价类` 是性能红线**（合病先例 21s → 218s）

**背景**：`tcm-core.owl` 的 ontology `rdfs:comment`（v7.2）原文：

> 删除 7 个合病类的 `owl:equivalentClass`，保留 `rdfs:subClassOf Liujingbing`。
> 原因：合病类的等价类是 **A ∩ B** 形式，A、B 本身是**复杂析取等价类**，
> Openllet 在 TBox precompute 时对交集做**笛卡尔积展开**，分支数达数千，
> **全局 precompute 从 21 秒暴涨到 218 秒**。

**推论**：任何「`X ≡ 析取A ⊓ 析取B`」的写法都要先跑性能计时。**特别是**：
- 若把 八纲 写成 `Han ≡ unionOf(判据…)`（析取等价类），再写 `六经 ≡ 病位 ⊓ 病性` → **就是合病模式，会炸**。
- **安全写法**：让**八纲保持原子类**（**不写 `≡`**，只让判据 `⊑` 八纲），
  则 `六经 ≡ Biao ⊓ Yang` 只展开成两个**原子类**相交，**不触发笛卡尔积**。
- **更稳的写法**：八纲连 `≡` 都不写 —— 判据 `⊑` 八纲 已是**充分条件**，
  「判据 ⇒ 八纲」方向已成立；而「八纲 ⇒ 判据」**没有任何使用场景**（判定流程永远从四诊往上推）。
  `≡` 的「定义完备性」作用可由**离线覆盖率校验脚本**替代。

**验收**：任何本体改动后跑一次 precompute 计时，**红线 60s**。

## 铁律 35：**六经提纲证不足以反推病位** —— `六经 ≡ 病位⊓病性` 会推不出少阴/厥阴

**背景**：设计要求 `六经 ≡ 病位 ⊓ 病性`，但逐条拆解六经现有 `≡ 症状组合` 后发现**四个缺口**：

| 六经 | 提纲给的病位证据 | 提纲给的病性证据 | 缺口 |
|---|---|---|---|
| 太阳 | 恶寒/恶风+脉浮 ✅ | ❌ 无 | **阳缺** |
| 阳明 | 大便硬/腹满 ✅ | 口渴/潮热/谵语 ✅ | 无 ✅ |
| 少阳 | 口苦 ✅ | ❌ 无 | **半表半里（胸胁/往来寒热）+ 阳缺** |
| 太阴 | 腹满/下利 ✅ | 脉弱/沉细/沉微/淡白舌 ✅ | 无 ✅ |
| 少阴 | ❌ **无** | 脉微细/但欲寐 ✅ | **表缺** |
| 厥阴 | ❌ **无** | 阴阳俱见 | **半表半里缺** |

**只有阳明、太阴能自足推出「病位⊓病性」**。

**少阴缺口的根因（历史遗留）**：`Shaoyinbing` 的 `rdfs:comment` 第 5 条原文
「剔除『恶寒/身痛』单独路径，**避免与太阳病争分类**」——
在「症状组合 ≡」范式下这是对的（少阴靠脉证自足），
但在「病位⊓病性 ≡」范式下**直接导致少阴推不出来**。

**教训（通用）**：
- 换判定范式（`症状组合 ≡` → `病位⊓病性 ≡`）时，**必须逐条重算「原判据在新范式下是否还够用」**，
  不能假定「原来的判据搬过去就行」。原范式下**刻意剔除**的边（如少阴的恶寒），在新范式下可能是**必需的**。
- 补法要留意**跨属性组合**：`恶寒 ⊓ 不发热 → 表` 是 `you_zhengzhuang` 两条限制的相交，
  而六经模板用的「属性限制」写法（`you_zhengzhuang some X ⊓ you_maixiang some Y`）**表达不了同属性相交**，
  必须改用**具名判据类**（`A7 ≡ you_zhengzhuang some Ehan ⊓ you_zhengzhuang some Bufare`，`A7 ⊑ Biao`）。

## 铁律 36：六经八纲的**医理硬结论**（查过医书，别再凭感觉推）

做「六经 ≡ 病位⊓病性」重构时，逐条查证了医书。以下四条是**有原文铁证的结论**，直接照用：

### ① 少阴的「表」证据 = **无热恶寒**
- 《伤寒论》**7条**：「病有发热恶寒者，发于阳也；**无热恶寒者，发于阴也**。」
- 胡希恕《据证分类法》：「**这里的发热恶寒和无热恶寒为太阳病、少阴病的主要鉴别点**。」
  「由此不难看出**少阴病为表证的阴性病**。」
- 胡希恕九步法：「无热、恶寒、**脉沉微细**者，为**表阴证（少阴病）**。」
- 北中医马家驹：「少阴病为**病位在表**的阴证，即**表阴（虚寒）证**。」
- → 判据：**恶寒 ⊓ 不发热 → 表**。（301条「反发热，脉沉」是变例，本以无热为常。）

### ② 厥阴的「半表半里」证据 = **厥阴提纲证本身**
- 胡希恕解 326条：「厥阴病上虚下寒……**寒在半表半里**，本不下利，
  与寒在里的太阴病自利益甚者不同。」→ **明言「寒在半表半里」**。
- 胡希恕九步法：「**消渴、气上撞心、心中疼热、饥而不欲食、脉微细或沉弦者，为半表半里阴证（厥阴病）**。」
- → 判据：**消渴 ⊔ 气上撞心 ⊔ 心中疼热 ⊔ 饥而不欲食 → 半表半里**。
- **不要**以为「厥阴提纲没有半表半里证据」—— 那是按脏腑经络理解才有的错觉。

### ③ 太阳/少阳的「阳」证据
- 胡希恕九步法：「表证：**发热、恶寒、脉浮紧有力者，为表阳证（太阳病）**。」
- 胡希恕解 263条：「**热郁于半表半里**……上迫头脑，则**口苦、咽干、目眩**。」
- → 太阳靠 `浮紧脉 ⊑ Shi`；少阳靠「口苦+咽干+目眩 → 半表半里 **+ Re**」。
- ⚠️ **`弦脉` 不挂 `Yang`**：265条「脉**弦细**，头痛发热者，属少阳」→ 弦细（虚）也属少阳，弦脉不定阴阳。

### ④ 沉脉**不挂「里」**；沉紧脉**只挂「实」**
- 301条「少阴病，始得之，反发热，**脉沉**者，麻黄附子细辛汤主之」+ 九步法「脉沉微细者，为**表阴证**」
  → **少阴是表证而脉沉**。挂「里」会把少阴误判为里证。**铁证。**
- 135条「结胸**热实**，脉沉而紧」（大陷胸汤，阳）vs《金匮》「**寒疝**绕脐痛……**其脉沉紧者**，大乌头煎主之」（阴）
  → **沉紧脉寒热皆见，病性不定，只挂 `Shi`**。
  （`tcm-core.owl` 太阴分支曾把 `沉紧脉` 当「里寒实」，135条明言「热实」，标注不确。）

### ⑤ 少阳与厥阴**可过渡**，不是非此即彼
- 陈慎吾：「柴胡桂枝干姜汤治疗**少阳病而又兼见阴证机转者**，用之最恰。」
- 胡希恕：「使半表半里的**阳证变为半表半里的阴证**。可知小柴胡汤从阴，是适应治疗半表半里阳证，
  **从阳则适应治疗半表半里阴证**。」
- → **`DisjointClasses(少阳病, 厥阴病)` 与「阴阳俱见 → 厥阴」逻辑上不相容**：
  厥阴患者（半表半里 + 热 + 寒）会**同时**满足 `少阳 ≡ 半表半里⊓Yang` 与 `厥阴 ≡ 半表半里⊓Yin`
  → Openllet 报 inconsistency。**✅ 已裁定删除该互斥**（`tcm-core.owl` 仅此一处互斥），
  由应用层按「阴阳俱见优先判厥阴」消歧（只影响输出，不影响一致性）。
- 用 `¬` 区分（`少阳 ≡ 半表半里⊓Yang⊓¬Yin`）**不行**：265条「脉弦细」属少阳（弦细⊑Xu⊑Yin）会被误杀；
  用 `¬Han` 也不行：「往来寒热」本身有寒。

vs Mode B（修复后）** 两组对照。实测 Mode A = 9/9 场景全空（六经=[] 八纲=[]），Mode B = PASS=9。
**这种「修复前后同 harness 双模对照」比单跑一次更有说服力**——它直接证明「缺口就是这两处」。

**教训（通用）**：
- **文档里的代码假设会过时**。动手前先 `grep` 确认「文档点名的类/方法是否真在 `src/main/java` 且被引用」，
  别照着 stale 文档改死代码。
- **改「模块抽取」类逻辑时，务必同时检查 seed 是否覆盖所有上游层**（本例漏了判据层），
  以及 `collectClassClosure` 的**方向**（只向上，不会向下/横向拉引用者）。
- **`addObjectAssertionsAndCopyTypes` 的语义是「拷到 obj，不是拷到 patient」**——需要患者直接带类型时，
  必须额外 `ClassAssertion(patient, 类)`。

## 铁律 38：验证「患者级推理」用**最小四诊模块集**，别用 `tcm-all.owl`（32min → 1.2s）

**背景**：要验证「某患者 ABox 能否推出某六经/八纲」，最直觉的写法是加载 `tcm-all.owl`（像
`TaiyinbingDefinitionTest` 那样）。**实测：precompute >32 分钟不收敛**（CPU 满载、WS 3.1GB）。

**根因**：`tcm-all.owl` 还 import 了**方证模块**（`taiyang`/`jueyin`/`shaoyin_taiyin`/`shaoyang_yangming`/
`zabing`/`duli`/`hebing`/`fanggen`/`jiajia`/`rules`）与 `fangji-abox`。这些模块里大量个体带**六经合取项**，
与新版 `六经 ≡ 病位⊓病性` 相互作用 → 推理爆炸。

**正解（1.2 秒）**：只加载**四诊子集**，用 `AutoIRIMapper` 按 IRI 显式加载：

```java
OWLOntologyManager m = OWLManager.createOWLOntologyManager();
m.getIRIMappers().add(new AutoIRIMapper(new File(ONT_DIR), true));
String[] mods = {"core","zhengzhuang","maixiang","shexiang",
                 "shexiang-abox","zhengzhuang-abox","maixiang-abox"};
for (String mod : mods) m.loadOntology(IRI.create("http://www.tcm-classics.org/jingfang/" + mod));
OWLOntology probe = m.createOntology(IRI.create(NS + "_probe"));
for (String mod : mods) m.applyChange(new AddImport(probe, df.getOWLImportsDeclaration(IRI.create(BASE + mod))));
m.addAxioms(probe, patientAbox);
OWLReasoner r = rf.createReasoner(probe);
r.precomputeInferences(InferenceType.CLASS_ASSERTIONS);
```

> 模块 IRI 形如 `http://www.tcm-classics.org/jingfang/<name>`（**无 `#`**）；
> 类/个体 IRI 才是 `.../jingfang#<frag>`。两者别混。
> `addObjectAssertionsAndCopyTypes(probe, ...)` 传 `probe` 即可（OWLAPI 的 `classAssertionAxioms` 会走 imports 闭包）。
> **同理**：`_bagang_verify` 这类「TBox 判据探针」的正确输入是 `tcm-shexiang.owl`（356 公理，1.2s），
> **不是** `tcm-all.owl`。曾因 runner 误传 `tcm-all.owl` 白等 32 分钟。

## 铁律 39：判据的**合取项类必须有 ABox 个体**，否则判据永不触发（TBox 对 ≠ 能跑）

**背景**：步 2 建的 31 个 `Panju_*` 判据，`≡` 用**属性限制**写成
`you_zhengzhuang some Fuman ⊓ you_zhengzhuang some Tu ⊓ …`。这类判据**靠患者的对象断言直接满足**，
**不需要**患者被断言成判据类（与铁律 37 的「发现类」机制不同）。

**但**：若某个合取项类**没有 ABox 个体**（`<frag>_instance`），患者**永远无法**引用它
（症状目录由 ABox 构建）→ 该判据**在 TBox 层完全正确、在运行期永不触发**。

**实测（2026-09-19）**：31 个判据中 **10 个是死的**：

| 判据 | 缺失类 |
|---|---|
| A3 | `ShenTengtong` |
| A5 | `Gujietengtong` |
| B1 | `Ziliyishen` |
| B2 / D4 | `FumanJuAn` |
| C2 | `Momobuyushiyin` |
| C5 | `Qishangzhuangxin` |
| E2 | `Shouzujueleng` |
| E3 | `WeiHan`, `Juanwo` |
| E5 | `Sizhinileng` |

这 10 个类**都存在于 TBox**（非悬空 IRI），只是 ABox 无个体。后果：`Li` 只剩 B3/B4/B5/B6 可达；
太阴病（`Li ⊓ Yin`）经 B1 的路径**已断**。

**审计脚本（每次改判据后必跑）**：

```python
# 逐判据取 you_* 合取项，比对 ABox 是否有 <frag>_instance
props = re.findall(r'<owl:onProperty rdf:resource="#(you_[a-z]+)"/>\s*'
                   r'<owl:someValuesFrom rdf:resource="#([^"]+)"', panju_body)
missing = [(p, c) for p, c in props if ('#' + c + '_instance') not in abox]
```

> **注意**：判据块的提取要**按 `owl:Class` 深度配平**，不能用 `.*?</owl:Class>` ——
> `equivalentClass` 里嵌了 `intersectionOf`，非贪婪会提前截断（会得到「合取项为空」的假结果）。

**修法（择一）**：(a) 补 `<frag>_instance` 个体；(b) 判据改用**已有个体**的近义类
（如 `Shouzujueleng`→`Shouzuleng`、`WeiHan`→`Ehan`；注意 `WeiHan` 畏寒 ≠ `Weihan` 微恶寒）。

## 铁律 40：**三阶段专用 minibox + 每步物化** —— 八纲/六经/方证各用各的模块（2026-09-19）

**背景**：`TCMOntologyJobWorker` 的三段推理原先**共用**一个 minibox（八纲阶段直接复用六经模块），
模块偏大。目标：**每阶段只加载该阶段需要的本体**，且**每步做完后把结果物化**，供下一步当固定事实消费。

**设计（已落地）**：

| 阶段 | 常量 | cacheKey | 模块抽取 | 生产实测 mini 公理 |
|---|---|---|---|---|
| 八纲 | `STAGE_BG = "#STAGE_BG"` | `patientIri + STAGE_BG` | `extractBagangModule(input)` | **454** |
| 六经 | `STAGE_LJ = "#STAGE_LJ"` | `patientIri + STAGE_LJ` | `extractLiujingModule(input)` | **529** |
| 方证 | `STAGE_FZ = "#STAGE_FZ"` | `patientIri + STAGE_FZ` | `extractFangzhengModule(input, stage1Types)` | **72** |

对应三个入口：`withBagangReasoner` / `withLiujingReasoner` / `withFangzhengReasoner`，
都走 `MiniReasoningContextManager.withContext(cacheKey, tboxSupplier, aboxBuilder, action)`。

**`extractBagangModule` 的 seed（八纲专用，比六经小）**：
患者四诊类 + `bagangSubclasses` + `bagangPanjuSubclasses`（**判据层**）+ `TOP_LEVEL_CLASSES` + 个体类型。
**不含**六经白名单 / 兼夹证 / 方证子树 → 比六经模块少约 30 条公理（454 vs 529），八纲结果**完全一致**。

**单向物化链（严格 八纲→六经→方证）**：
1. 八纲阶段结束 → 把 `patientTypes` 写入 `input.bagangTypes`，log `[物化] 八纲已固定: {...}`；
2. `miniCtxMgr.clearByPrefix(patientIri)` 清掉本患者上下文，使六经阶段**重建**时带上物化八纲；
3. `extractLiujingModule` 检测到 `input.bagangTypes` 非空 → **跳过判据层 seed**（模块更小、更快），
   log `[阶段1] 八纲已物化 {...}，跳过判据层 seed`；
4. 六经阶段结束 → 写入 `input.liujingTypes`，log `[物化] 六经已固定: {...}`，再清上下文；
5. 方证阶段 `extractFangzhengModule` 把 `input.bagangTypes` + `input.liujingTypes` 注入 seed，
   作为**固定值**直接消费（`assertMaterializedTypes` 把二者断言到患者个体）。

**关键点**：
- **`六经 ≡ 病位 ⊓ 病性`** 是 Openllet 把患者归入六经的**唯一路径**；`belongsToLiujing` 是
  `owl:AnnotationProperty`，推理机**忽略**它（Java 只读它做方证-六经缓存）。
- **物化是「写回 `PatientInput` + 清缓存」**，不是写回本体文件。`clearByPrefix` 是让下一阶段
  **重新建上下文**（带上新断言）的必要动作，漏了它下一阶段仍用旧上下文 → 物化不生效。
- **八纲模块必须含判据层**（`bagangPanjuSubclasses`），否则患者不被归入判据 → 八纲全空（同铁律 37 缺口 1）。
- **启动时一次性全量加载**（`tcm-all.owl`，`TBox 推理完成！隐式公理已展开`，约 157–168s）是**预期行为**，
  与「每阶段 minibox」不冲突：全量加载用于建索引/缓存，推理阶段才切 minibox。

**验证手法**：写 `_BagangMiniVerify`，同一批场景跑 **`withSix=true`（六经模块）vs `withSix=false`（八纲模块）**
双模对照，比对八纲结果 + 模块规模。实测 **PASS=16 FAIL=0**，八纲模块少 30 条公理、9 个场景八纲输出逐字一致。
（同铁律 37 的「双模对照」思路：证明「换模块不换结果」。）

**生产日志核对（改完必看）**：
```
[阶段0] 患者症状=N, 初始=53, 闭包=143, mini 公理=454   ← STAGE_BG
[物化] 八纲已固定: [...]
[阶段1] 患者症状=N, 初始=67, 闭包=167, mini 公理=529   ← STAGE_LJ
[物化] 六经已固定: [...]
[阶段2] ... 初始=14, 闭包=15, mini 公理=72              ← STAGE_FZ
```
若 `[阶段1]` 的 `mini 公理` 仍等于 529 且**没有** `八纲已物化…跳过判据层 seed`，
说明 `bagangTypes` 为空（输入为空或八纲未定），**不是**物化失效。

## 铁律 41：**合病方证的六经只能写注解，不能写等价类** —— 病位/病性不互斥会「交叉推出 4 个六经」（2026-09-19）

**背景**：`六经 ≡ 病位 ⊓ 病性`（太阳=表阳、阳明=里阳、少阳=半表半里阳、太阴=里阴、**少阴=表阴**、厥阴=半表半里阴）。
给方证「指派六经」的既有做法是把六经类注入 `equivalentClass` 的 `intersectionOf` 首位。
**但这对跨病性的合病方证会出错。**

**实测**：`Wendantangzheng ≡ 少阳 ⊓ 太阴 ⊓ 症状`
```
少阳 = 半表半里 ⊓ 阳 ;  太阴 = 里 ⊓ 阴
⇒ ⊑ 里 ⊓ 阴 ⊓ 半表半里 ⊓ 阳
⇒ 推理机推出 太阴 + 少阳 + 阳明(里阳) + 厥阴(半表半里阴)   ← 4 个！
```
（`_InjectVerify` 实测 `推理六经=[Jueyinbing, Shaoyangbing, Taiyinbing, Yangmingbing]`）

**根因**：病位（表/里/半表半里）与病性（阴/阳）**都没有声明互斥**（全本体唯一 `DisjointClasses` 已删；
现存 `disjointWith` 只在方证之间做鉴别）。所以 `A⊓B` 会推出 病位×病性 的**全部交叉组合**。

**为何现有 4 个合病类没暴露**：`TaiyangShaoyangHebing` / `ShaoyangYangmingHebing` /
`TaiyangYangmingHebing` / `TaiyinShaoyinHebing` 配对的六经**病性相同**，交叉后不产生新组合。
**少阳太阴合病是第一个跨病性合病。**

**正解（已采用）**：合病方证的六经**只写 `belongsToLiujing` 注解（可多条），不写等价类**。
依据：
- 生产 `filterFangzheng` 走 `fangzhengLiujingMap`，该 map 由 `OntologyModuleUtils.findRelatedClasses`
  从**注解**（∪ 父类 ∪ 等价类命名类）构建 → 注解足够；
- 六经阶段 minibox **不含方证类**（`extractLiujingModule` seed 无 `fangzhengSubclasses`），
  推理机**从不对方证做六经分类** → 等价类注入无用且有害。

**反例（单经安全）**：只注入**一个**六经（如 `Gualouqumaiwanzheng ≡ 太阴 ⊓ 症状`）→ 只推出该六经，无交叉。
故**单经方证照旧写等价类，合病方证只写注解**。

**验收口径（`_LiujingAssignVerify`）**：必须查**两个口径**——
- **注解口径**（= 生产 `fangzhengLiujingMap` 的来源）：`注解 ∪ 父类 ∪ 等价类命名类 ∩ 六经` **必须等于期望**；
- **推理口径**（`reasoner.getSuperClasses`）：**不得越界**（合病方证可为空，但不能推出期望之外的六经）。
> 只看「等价类里有没有六经」的审计（`_FangzhengLiujingAudit`）会把合病方证误报为「推理机不认」——
> 合病方证**按设计**只写注解，该状态是正常的。

**教训（通用）**：给本体加「多值逻辑归属」前，先问「这两个值合取会不会推出第三个」。
**非互斥的维度做合取 = 交叉积**。要么保证合取项同维同值，要么改用注解/应用层。

### 41.1 交叉积**不只影响方证，也影响患者**（2026-09-19 探针实测）

`_harness/_HebingProbe.java` 直接问推理机「某八纲组合推出哪些六经」：

| 八纲组合 | 推出六经 | 评价 |
|---|---|---|
| 半表半里 + 里 + 阳 + 阴 | **少阳, 太阴, 阳明, 厥阴**（4 个） | ❌ 交叉积 |
| 表 + 里 + 阳 | 太阳, 阳明（2 个） | ✅ |
| 表 + 里 + 阴 | 太阴, 少阴（2 个） | ✅ |

**规律：合病两经病性相同 → 正确；病性不同 → 交叉积**
（多出 `里⊓阳`=阳明、`半表半里⊓阴`=厥阴）。

**生产影响**：少阳太阴合病的患者，推理机给 4 个六经 →
`resolveLiujingMutex`（`LIUJING_MUTEX_PAIRS = {Shaoyangbing→Jueyinbing}`，
「半表半里阴覆盖阳」）**移除少阳、保留厥阴** → 最终 `{太阴, 阳明, 厥阴}`，
**既不是少阳太阴合病，也不是任何真实证型**。
→ **该 mutex 是掩盖交叉积的创可贴，且掩盖后结果仍是错的。**

### 41.2 根因：扁平八纲丢失「病位-病性配对」

合病 = **多个独立的（病位, 病性）对**。扁平 ABox（患者直挂 `Li`/`Banbiaobanli`/`Yang`/`Yin`）
无法区分「里来自 A 方面、阳来自 B 方面」与「里阳同出一源」→ 产生 `里⊓阳`。

**要真正「按推理机推合病」→ 八纲判定个体化（reify）**：
```owl
Judgment ⊑ Thing ;  hasBingwei/hasBingxing : Judgment → Bagang
Patient ⊑ ∃hasJudgment.Judgment
Taiyinbing   ≡ ∃hasJudgment.(∃hasBingwei.Li ⊓ ∃hasBingxing.Yin)
Shaoyangbing ≡ ∃hasJudgment.(∃hasBingwei.Banbiaobanli ⊓ ∃hasBingxing.Yang)
```
患者挂两个判定个体 → 推出**恰好 太阴+少阳**，无交叉积。
代价：八纲阶段断言方式要改（判据 → 判定个体 → 病位/病性），中等重构。

> **决策点**：先定「病位/病性是否互斥」——**不互斥是交叉积的根源**。
> 但若声明互斥，则「半表半里 ⊓ 里」= ⊥，合病在 ABox 层直接不可表达。
> 故互斥与合病**不可兼得**，除非走 reify 路线。

（= 铁律 39）。否则判据永不触发 → 八纲缺项 → 六经为空。

### 42.4 加减药期望值：**多条规则可同时命中**

真武汤证患者若**同时有下利与呕**，316 条两条方后注**都会命中**：
`去芍药加干姜` **且** `去附子加生姜` → 实际去药是 `[芍药, 附子]`，不是 `[附子]`。
写期望值前先想清楚患者症状会命中**哪几条**规则，别只盯标题那一条。

另：规则 `add X` 而 X **本就在母方**时，引擎记为**剂量调整**（`dosageChanges`），
`addedCn` 为空、`herbsCn` 不重复。例：小柴胡汤证+渴（人参）、真武汤证+呕（生姜）。

### 42.5 断言写法

- **六经**：用 `SIX_CHANNEL_WHITELIST`（6 个）过滤后精确匹配 —— 推理结果里还含
  `Liujingbing`（父类）与 `*Hebing`（合病类），必须滤掉。
- **方证**：只断言 `contains(期望方证)` —— realize 常同时命中近邻方证
  （真武汤证+呕 还命中麻黄附子甘草汤证；小青龙汤证+渴 还命中麻黄汤证），
  生产侧靠 `rankCandidatesWithScores` 按症状命中数排序取 Top1。

## 已知踩坑

- **RDF/XML 注释里禁止出现 `--`**：给 `.owl` 追加块时用 `<!-- ---------- 分段 ---------- -->` 做分隔符，
  会让**整个本体解析失败**（`SAXParseException: 注释中不允许出现字符串 "--"`），
  且报错行号指向文件末尾附近（如 L1105），**容易误以为是新加的类写错**。
  分隔符改用 `=`（`<!-- ========== 分段 ========== -->`）或干脆不写分隔注释。
  **排查手法**：`re.finditer(r'<!--[^>]*-->', s)` 逐条检查 `'--' in m.group(0)[4:-3]`。
- **离线测试里 `labelOf()` 会回退成英文 fragment**：`TCMOntologyJobWorker.yaowuLabelMap` 由 `loadIncompatibilitiesFromObda()` 通过 **OBDA 查询**填充（需 Ontop+MySQL）。离线测试只调 `loadHerbRulesForTest()`，该表为空 → `labelOf("Gualougen")` 返回 `"Gualougen"` 而非「瓜蒌根」，`addedCn`/`removedCn`/`herbsCn` 全是英文。**测试要输出中文需自行解析** `tcm-yaowu-abox.owl` 的 `rdfs:label`。
- **症状个体带 `_instance` 后缀，药名个体不带**：`tcm-zhengzhuang/maixiang/shexiang-abox.owl` 里是 `#Fare_instance`，而 `tcm-yaowu-abox.owl` 里是 `#Chaihu`（无后缀）。`SymptomCatalog.byFragment()` 只截 `#` 不做后缀处理，所以传裸 fragment 查不到，要传 `fragment + "_instance"`。
- **`retain` 动作不置 `changed`**：`deriveFormula` 里只有 `removes`/`adds` 会置 `changed=true`，`retains` 不会。所以「真武汤证 + 小便不利 → retain 茯苓」这种「本有则不动」的规则**命中但 `derived=false`**、`appliedRules` 为空。这是合理语义（无变化即不派生），但展示时会显示「命中规则 0 条」，容易误读为规则没匹配。
- **症状映射输出必须是完整 IRI，不是裸 fragment**：`symptom-mapping` 的 `symptomIris`/`pulseIris`/`tongueIris`/`fuzhengIris` 要输出 `BASE_NS + fragment`（如 `http://www.tcm-classics.org/jingfang#Fare_instance`），因为下游 `sizhen-input` 及八纲/六经/方证推理都按 **IRI** 查找个体；`mappingDetail[*].fragment` 才是裸 fragment（供前端展示/人工确认回传）。两者混用会导致下游查不到个体。
- **症状目录里没有的 label 不要写进测试/文档**：例如 `胁下胀满` 不存在，正确是 `胸胁苦满`（`Xiongxiekuman_instance`）；`欲呕` 的 fragment 是 `Yuou_instance`（不是 `Yuyou_instance`）。写之前先查 ABox。
- **字面召回召不回语义远距表述**：如「两边肋骨下面胀痛」→「胸胁苦满」二者**无任何共享字符**，子串/超串/Dice/字符交集全部失效。LLM 语义映射的候选集必须能在必要时升级为**全目录**，否则防幻觉校验会把正确答案误杀。
- **Java 正则别用控制字符做占位符**：用 `\u0001` 保护 `(A OR B)` 子串时，还原步骤会静默失败，导致括号组退化成 `[0]`。改用**手写括号深度扫描器**按顶层 `AND` 切分。
- **OWLAPI `annotationAssertionAxioms()` 不保序**：不能按位置把注解与其它注解配对。需要文档顺序时，**直接解析 OWL 源文件**（正则扫 `<owl:Class rdf:about="#X">…</owl:Class>` 块）。
- **本体 `equivalentClass` 析取项里写「父类」会过宽，导致误判**：`tcm-core.owl` 的太阴病分支 1 原写
  `（腹满|呕吐|食不下） ∩ （弱脉|沉细脉|沉微脉|淡白舌|CoatingColor）`，末项是**父类** `CoatingColor`（苔色），
  而 `WhiteCoating`/`YellowCoating`/`GreyCoating`/`BlackCoating` 全是它的子类 →
  「腹满 + 黄苔」（阳明里实热证）被误判为太阴病（里阴证），八纲凭空多出「阴证」、六经变「阳明太阴合病」。
  **排查手法**：先查该类自身 `coreEvidence`（本例「脉弱、沉细、沉微、**舌淡苔白**」），
  按证据把父类收窄为具体子类（`CoatingColor` → `WhiteCoating`）。
  **注意** `DryCoating`/`ThickCoating`/`GreasyCoating` ⊑ `CoatingTexture`（苔质）、
  `TongueWithThorns` ⊑ `PrickledTongue` ⊑ `TongueShape` —— 都**不是** `CoatingColor` 子类，
  只有苔色路径会触发，别把无关项一起改。
- **改本体后必须重启 Worker**：`OntologyService.tBoxOntology` 在**构造时**从 `ontology.main-path` 加载并缓存，
  运行中的 Worker 永远不会感知文件变更。Worker 常由 **IntelliJ** 启动（命令行含 `idea_rt.jar` agent），
  需用户在 IDE 内重启，不要直接 kill。
  判断是否陈旧：比对 `tcm-core.owl` 的 `LastWriteTime` 与 Worker 进程 `StartTime`。
- **XML 注释内不得出现 `--`**：`<!-- ---------- -->` 会导致 `not well-formed (invalid token)`，改用 `<!-- === ... === -->`。
- 药物个体在 `tcm-yaowu-abox.owl` 是 `owl:NamedIndividual`（不是 `owl:Class`），fragment 即拼音名（`Gegen`→葛根）。
- **重启 app 必须「脱离父 shell」**：`TCMApplication` 启动约 157–168s，若用普通 `Popen`/`&` 启动，
  **父 shell 一退出进程就被回收**（曾连续两次「启动成功但随即消失」）。正解（Python）：
  ```python
  subprocess.Popen(cmd, creationflags=0x00000008 | 0x00000200,  # DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP
                   close_fds=True, stdout=logf, stderr=subprocess.STDOUT)
  ```
  并用 `run_in_background` 启动；等 `Started TCMApplication in ... seconds` 出现即就绪。
- **`症状映射` 阶段的输入契约是 `userInput`（自由文本），不是 `symptomIris`（IRI 列表）**：
  `handleSymptomMapping` 从 job 变量读 `userInput` 再调 `symptomMappingService.map(...)`。
  若测试/调用方只传 `symptomIris`，映射阶段看到空输入 → `症状映射[第0轮]: 已识别 0 项 | 症状=[]`
  → 整条链全空（八纲/六经/方证皆空）。**这是调用契约不匹配，不是推理/物化 bug**
  （此时 `[物化] 八纲已固定: []` 属正常，因为确实没有可物化的内容）。
  排查顺序：先看 `症状映射[第0轮]` 那行——`已识别 0 项` 就说明**问题在入口，不在推理**。

## 铁律 45：解析 OWL 判据**必须用 ElementTree 递归**，正则处理不了「交集里嵌并集」（2026-09-19）

**踩坑**：用正则解析 `<owl:equivalentClass>` 时，若块内含 `<owl:unionOf>` 就整块当 union 分支处理
→ **把 `Panju_A8`（交集里嵌并集）误判为纯 union**，少阴簇 50 例全部漏判，通过数被算成 433（真值 474）。

**正确做法**：`xml.etree.ElementTree` 递归转表达式树，支持任意嵌套：
```python
def _node(el):                      # owl:Restriction / owl:Class → 表达式节点
    if el.tag.endswith('}Restriction'):
        return ('restr', prop, frag)
    inter = el.find('owl:intersectionOf', NS)
    if inter is not None: return ('and', [_node(c) for c in list(inter)])
    uni = el.find('owl:unionOf', NS)
    if uni is not None: return ('or',  [_node(c) for c in list(uni)])
```
`owl:intersectionOf rdf:parseType="Collection"` 的成员就是该元素的**直接子元素**，ElementTree 直接可取。

**同类坑**：正则按 `</owl:Class>` 非贪婪匹配会在**内嵌匿名类**处截断 → 判据解析全空。
凡涉及 OWL 结构解析，一律用 XML 解析器，不要用正则。

**附带发现**：`tcm-all.owl` 是**纯 import 聚合器**（自身无类定义），
`owl:imports` 指向 `core`/`zhengzhuang`/`maixiang`/… 由
`OntologyService.loadOntologyFilesWithOWL` 的 `AutoIRIMapper(parentDir, true)` + `catalog-v001.xml` 解析
→ **改分册即生效，无需重新合并 `tcm-all.owl`**（`application.yml: ontology.main-path` 指向它）。

## 铁律 46：**禁止**把单症状/单脉象直接 ⊑ 八纲（白名单），一律用**合取判据**（2026-09-19，用户裁定）

## 铁律 64：**互斥四诊只收「一定互斥」者；互斥公理只用于「矛盾检测」，不得进入分类推理模块**（2026-09-22，用户铁律）

用户原话：「按照医理补充一些互斥的症状，比如恶寒和不恶寒就是互斥，沉脉与浮脉就是互斥，

四诊参合应该有矛盾」。

### 64.1 互斥类的收录标准（只收「一定互斥」，宁缺勿造）

互斥 = **同一维度上不可能同时成立**的两个四诊所见。只允许以下三类，且每对必须能指到出处：

| 类别 | 例 | 依据 |
|---|---|---|
| 逻辑否定对 | 恶寒 / 不恶寒；汗出 / 无汗；口渴 / 不渴；小便不利 / 小便利 | 命题与其否定，逻辑上必斥 |
| 脉象对立对 | 浮 / 沉；数 / 迟；滑 / 涩；虚 / 实；洪 / 微；弦 / 缓 | 《濒湖脉学》「脉位/脉率/脉势」对立 |
| 单值维度内互斥 | 舌色（淡白/红/绛/紫）两两；苔色（白/黄/灰黑）两两；苔质（润/燥、薄/厚、腻/腐） | 《中医舌诊》：同一舌面在同一时刻只能呈现一种 |

- **不得**把「常同时出现」「倾向相反」当作互斥（如「发热」与「恶寒」可并见——太阳表证即是）。
- 表达形式：`owl:disjointWith` + `huChiReason` 注解（写明医理/医书出处，供审计）。
- 落地文件：`ontology/tcm-huchi.owl`（49 对，54 条公理），由 `catalog-v001.xml` 与 `tcm-all.owl` 引入。

### 64.2 用途一：追问过滤（路A）

生成「建议补充的四诊」时，**与已输入四诊互斥的选项一律不得出现**
（实现：`removeMutuallyExclusive`，在 PANJU 层与 FANGZHENG 层各过滤一次）。

### 64.3 用途二：四诊参合矛盾（一致性检查节点）

互斥四诊同现时，`ontology-consistency-check` 节点**必须报告矛盾**，并**定位到具体哪一对**：
输出 `sizhenConflict=true`、`conflictPairs`、`conflictPairsCn`（如「浮脉 ⊥ 沉脉：脉位……」）。

### 64.4 关键工程约束：互斥公理**不得**进入分类推理模块

- **原因**：OWL 语义下，个体同时属于两个 `owl:disjointWith` 的类 ⇒ 本体**不一致**。
  若互斥公理留在推理模块里，患者一旦同时具备互斥四诊（如浮脉 + 沉脉），
  Openllet 会抛 `InconsistentOntologyException` 并**拒绝分类推理**，整条诊断流程中断。
- **做法**：模块抽取后，在 **OntologyFramework 侧**剔除 `owl:disjointWith`
  （`stripDisjointAxioms`，用于八纲/六经/方证三个模块），一致性判定改以**互斥索引**
  `detectSizhenConflicts` 为唯一判据（更精确：直接给出冲突对，且不中断流程）。
- **合规性**：剔除互斥公理只会**放宽可满足性**，不改变任何**可满足类**的正向蕴含，
  故不影响方证/六经/八纲的判定结果（已由 `HuchiProbe` 30/30 与全量回归验证）。
- **与铁律 51 的关系**：该剔除**只在 `OntologyFramework` 内完成**，
  **未改动** `OpenlletResolver` / `OntopOBDAHandler` 任何文件。

### 64.5 自检清单

1. 新增的每一对互斥，是否都能指到医书/医理出处？不能 → 不得写入。
2. 是否把「可并见」误判为「互斥」？是 → 删除该对。
3. 互斥公理是否被误带入推理模块？是 → 必须剔除（否则矛盾输入会中断诊断）。
4. 矛盾输入下，流程是否仍能走完并给出诊断，同时如实上报矛盾？否 → 违反本条。
