## 一、`TaiyinbingDefinitionTest` 无法加载本体（UnloadableImportException）

### 现象

```
org.semanticweb.owlapi.model.UnloadableImportException:
  Could not load imported ontology: <http://www.tcm-classics.org/skos/zhengzhuang>
  Cause: OWLOntologyCreationIOException: java.net.UnknownHostException: www.tcm-classics.org
```

5 个用例一个都没执行（`@BeforeAll` 抛异常）。

### 根因

`tcm-all.owl` 自 2026-09-21 起新增了 SKOS 词表导入：

```xml
<owl:imports rdf:resource="http://www.tcm-classics.org/skos/zhengzhuang"/>
```

物理文件是 `ontology/tcm-zhengzhuang_skos.ttl`，由 `catalog-v001.xml` 登记。
生产链路（`OntologyService.loadOntologyFilesWithOWL`）能解析它，因为该方法是
**两段式**的：

1. `AutoIRIMapper(parentDir, true)` —— 处理 `.owl/.rdf/.xml/.omn/.ofn`；
2. 扫描目录下所有 `.ttl`，用 `TurtleDocumentFormat` 解析出 `owl:Ontology` 的 IRI，
   再逐个注册 `SimpleIRIMapper`（`OntologyService.java:246-280`）。

而本测试只做了第 1 步。`AutoIRIMapper` 的扩展名白名单是硬编码的

```java
private final Set<String> fileExtensions =
    new HashSet<>(Arrays.asList(".owl", ".xml", ".rdf", ".omn", ".ofn"));
```

**不含 `.ttl`**；且它内部用 SAX 解析，Turtle 文件即便加进白名单也解析不出 ontology IRI。
于是该 import 无映射 → OWLAPI 退化为 HTTP 拉取 → 离线必然 `UnknownHostException`。

### 修复

在测试中复刻生产的两段式策略，新增 `registerTtlMappings(OWLOntologyManager, Path)`：

- 扫描本体目录下 `*.ttl`；
- 用隔离的探测 manager（`MissingImportHandlingStrategy.SILENT`）以
  `FileDocumentSource(ttl, TurtleDocumentFormat)` 读出 ontology IRI；
- 对目标 manager 注册 `SimpleIRIMapper(ontologyIRI → ttlFile)`。

### 验证

```
[TaiyinDef] 已注册 1 个 TTL 本体映射（供离线解析 owl:imports）
[TaiyinDef] 精简 TBox：剔除方证等价类定义 265 条；剩余公理 18005 条
Test run finished after 4770 ms
[ 5 tests found ] [ 5 tests successful ] [ 0 tests failed ]
```

**5/5 通过，4.77s**（预算 10s）。

### 为什么不需要把 SKOS 排除出推理本体

`tcm-zhengzhuang_skos.ttl` 是纯词表：737 个 `skos:Concept` 个体，
`skos:prefLabel/notation/inScheme/exactMatch` 各 737 条、`zz:classMatch` 737 条，
**`subClassOf` 与 `equivalentClass` 均为 0 条**。它对「六经 ≡ 病位 ⊓ 病性」的
推理零贡献，实测加入后总耗时 4.77s（原记录 5.4s），无性能退化，故不剔除。

## 二、套件运行器静默吞掉「容器级失败」（假绿）

### 现象

修复前跑 `run_suite.sh TaiyinbingDefinitionTest`：

```
TaiyinbingDefinitionTest   0  0  0  0   无用例
√ 全部通过。
SUITE_EXIT=0
```

测试类明明因 `@BeforeAll` 抛异常而完全没执行，汇总却报「无用例」并判定全部通过。

### 根因

`FangzhengSuiteRunner.Recorder` 的监听器对非用例标识符直接返回：

```java
public void executionFinished(TestIdentifier id, TestExecutionResult result) {
    if (!id.isTest()) return;      // ← 类级容器失败被丢弃
    ...
}
```

类级 `@BeforeAll` 失败属于**容器级失败**，不是用例失败。丢弃后该类一个用例都不会
执行，汇总里只剩「无用例」，退出码仍为 0 —— 任何类的加载/初始化失败都会变成假绿。

### 修复

新增 `recordContainerFailure(...)`：对 `ClassSource` 容器且状态为 `FAILED` 的，
记为一条 `<整个类>` 失败用例，进入汇总、报告与退出码。只取 `ClassSource`，
避免把引擎/套件根容器的失败重复计一遍。

### 验证

用临时类（`@BeforeAll` 抛 `IllegalStateException`）验证：

```
[失败] TmpContainerFailTest  <整个类>  「TmpContainerFailTest」  0.00s
        └─ 模拟 @BeforeAll 失败（本体加载异常）
× 存在 1 个失败用例，详见上方失败明细。
SUITE_EXIT=1
```

验证后临时类已删除。

## 三、遗留阻塞：Zeebe broker 分区 1 反复 INACTIVE（环境缺陷，非本次改动引入）

跑全量套件时 7 个类报容器级失败：

```
Time out between gateway and broker: Request timed out after PT15S
```

### 定位

`c8run-8.9.6/camunda-zeebe-8.9.6/logs/zeebe.log`：

```
[2026-09-22 16:28:15.189] ERROR io.atomix.raft.impl.LogCompactor - Failed to compact up to index 147541
io.camunda.zeebe.journal.JournalException: java.nio.file.FileSystemException:
  ...\raft-partition\partitions\1\raft-partition-partition-1-3.log
    -> ...\raft-partition-partition-1-3.log_2-deleted:
  另一个程序正在使用此文件，进程无法访问。
[2026-09-22 16:28:15.194] ERROR io.atomix.raft.impl.RaftContext - An uncaught exception occurred, transition to inactive role
```

- 分区 1 的 raft 日志压缩（`Segment.markForDeletion` → `Files.move`）在 Windows 上
  因文件被占用而失败，抛未捕获异常 → 分区 `LEADER → INACTIVE`，此后不再恢复。
- 网关端口 26500 仍在监听，所以 `run_suite.sh` 的预检（仅 TCP 连通性）报「可达」，
  但任何 job 都无法激活 → `NoRemoteHandler ... subject command-api-1`。

### 时间线（今日）

| 时刻 | 事件 |
|---|---|
| 00:57:44 | 同一 bug 首次触发（`...-8.log → ...-8.log_1-deleted`），分区 INACTIVE |
| 01:11 / 01:14 / 06:44 / 12:34 / 12:41 / 12:43 / 12:46 / 12:53 | 多次重启 |
| 15:11:07 | 重启，分区 1 成为 LEADER（term=2），**健康** |
| 15:13 – 16:18 | 空闲正常（每分钟仅 1 行快照心跳） |
| 16:28:15 | 再次触发同一 bug，分区 INACTIVE，至今未恢复 |

### 结论

- 该缺陷**与本次测试改动无关**：改动只涉及 `TaiyinbingDefinitionTest`（不在 280 例套件内）
  与 `FangzhengSuiteRunner`（仅上报逻辑，不改测试语义）。
- 触发条件与写入量相关（快照/压缩在套件跑完后触发），即**跑全量套件本身会诱发该 bug**，
  因此「280/280」的验收结果当前不可复现，需先解决 broker 稳定性。
- 修复方向（未执行，属运行环境范畴）：Windows Defender / 索引器对该 data 目录加排除项、
  调整 raft 段大小或快照周期以降低压缩频率、或改用 Linux 容器运行 broker。
