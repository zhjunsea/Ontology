## 一、总览

### 1.1 一句话定位

把《伤寒论》「病脉证并治」体系编译成可计算本体，由 **Camunda 编排的 10 个 JobWorker**
串成一条**全自动**诊断流水线：自然语言四诊输入 → 症状实例个体 → 一致性检查 →
八纲 → 六经 → 方证 → 兼夹证 → 母方 → 方后注加减 → 诊断解释。

### 1.3 四条贯穿性设计原则

| 原则 | 铁律 | 落点 |
|---|---|---|
| **逻辑链单向**：判据 → 八纲 → 六经 → 方证 | 32、60 | 每阶段只消费上游物化结果，严禁下游反推上游 |
| **八纲只由症状推出**，严禁由方证反推 | 43 | `handleBagangClassification` 只取患者推理结果 |
| **结果形态三态化**：只有「完全 realize」才算结论 | 16 | `outcome` + `fangzhengRealized` 驱动网关 |
| **一切以本体定义为准，本体以医书医理为准** | 26、53、61、63 | 判据/公理改动须有医书依据 |

### 3.2 全自动约束（BPMN 头注原文）

> 前端只负责「输入症状」与「展示结果 + 依据」，流程内部**不得出现任何人工任务（userTask）**，
> 必须由 JobWorker 一路跑到结束事件。因此症状映射后直接进入四诊录入，不再有「人工确认症状映射」
> 回环；一致性检查不通过 / 无方证推荐时，直接落到 `EndEvent_NoResult`。

> ⚠️ **实现现状提示**：`TCMDiagnosisService` 仍保留 `TASK_CONFIRM_SYMPTOMS` /
> `TASK_REVISE_SIZHEN` 常量与 `POST /{key}/confirm`、`/{key}/tasks/{taskKey}` 端点，
> 但当前 BPMN **不产生任何 userTask**，调用确认端点会抛
> 「当前流程没有待确认的症状映射任务」。属历史遗留，见铁律 13。

## 四、逐阶段设计

> 约定：每阶段由 `TCMOntologyJobWorker` 中一个 `@JobWorker(type=..., autoComplete=false)`
> 方法实现，**显式 complete / throwError**（`autoComplete=false`，异常时抛 BPMN error 而非静默成功）。

### ① `symptom-mapping` — 症状映射

| 项 | 内容 |
|---|---|
| 实现 | `handleSymptomMapping` → `SymptomMappingService.map(...)` |
| 输入变量 | `userInput`、`confirmed` / `rejected` / `extra`（可选）、`mappingRound` |
| 输出变量 | `symptomIris` / `pulseIris` / `tongueIris` / `fuzhengIris`、`needsConfirmation`、`ambiguousSymptoms`、`unmatchedTexts`、`mappingDetail`、`mappingSummary`、`mappingRound`(+1) |
| 错误码 | `SYMPTOM_MAPPING_FAILED` |

**三层策略**：

| 层 | 策略 |
|---|---|
| **L1 确定性检索** | 精确 → 同义词 → 同义词包含 → 子串 → 超串 → 字符 Dice 模糊 |
| **L2 LLM 语义映射** | 把**白名单候选**喂给大模型，要求只能从白名单中选择（**防幻觉**）；窄候选集无法覆盖「语义远距」表述（如「两边肋骨下面胀痛」→「胸胁苦满」），故有一次**全目录候选**的升级调用 |
| **L3 置信度门控** | ≥0.85 直接采纳；≥0.50 采纳但标记待确认；<0.50 不采纳 → 进 `unmatchedTexts` |

> **同义词唯一权威来源**：本类**不含任何硬编码症状同义词表**。所有「口语/文言/缩写 →
> 本体规范名」映射一律经 `SymptomCatalog` 从 SKOS 词表
> （`tcm-zhengzhuang_skos.ttl`）加载。新增同义词只改 SKOS，不改代码。

### ② `sizhen-input` — 录入四诊

| 项 | 内容 |
|---|---|
| 输入 | `symptomIris` / `pulseIris` / `tongueIris` / `fuzhengIris` |
| 处理 | 建患者 IRI `Patient_<processInstanceKey>`；`clearPatientCache` 清旧缓存；`detectSizhenConflicts` 检测互斥；预热六经推理上下文 |
| 输出 | `patientIri`、`recorded`、`inconsistent`、`sizhenConflict`、`conflictPairs`、`conflictPairsCn` |
| 错误码 | `SIZHEN_INPUT_FAILED` |

> **关键设计**：互斥公理（`owl:disjointWith`）已从推理模块**剔除**（`stripDisjointAxioms`），
> 故一致性**不依赖推理机**，而由「互斥索引」直接定位「哪两个四诊互斥」——更精确，
> 且不会因矛盾中断诊断流程（铁律 64）。

### ③ `ontology-consistency-check` — 一致性检查

| 项 | 内容 |
|---|---|
| 输入 | `patientIri` |
| 处理 | 以互斥索引为**唯一判据**判定 `conflicts`；生成可读说明 |
| 输出 | `consistent`、`unsatisfiableClasses`（恒空）、`sizhenConflict`、`conflictPairs`、`conflictPairsCn`、`conflictMessage` |
| 错误码 | `CONSISTENCY_FAILED` |

### ④ `bagang-classification` — 八纲分类

| 项 | 内容 |
|---|---|
| 推理 | `withBagangReasoner` → `extractBagangModule`（**阶段 0 minibox**） |
| 处理 | 取患者推理类型 ∩ 八纲子类；**阴阳消解**；**物化** |
| 输出 | `bagangResult{表里,寒热,虚实,阴阳,bagangTypes,bagangTypesCn,complete}` |
| 错误码 | `BAGANG_FAILED` |

**阴阳消解**（`resolveYinYang`，胡希恕《六经八纲》）：阴阳为八纲总纲，本应由病性决定
（热/实属阳，寒/虚属阴），但**表证的阴阳另有规定**——表阳证为太阳病，表阴证为少阴病，
二者以 **281 条少阴提纲「脉微细，但欲寐」**（`Panju_E1`）为别，**不以虚实论**
（太阳中风虽属表虚仍为表阳证）。故「阳证」与「阴证」双现时：

1. **纯表证**（表里仅「表证」）：`Panju_E1` 成立 → 阴（少阴）；否则 → 阳（太阳）。
2. **其余**（含里证或半表半里）：热证 → 阳；寒证 → 阴；实证 → 阳；虚证 → 阴；皆无 → 阳。

**物化**：把八纲固定到 `input.bagangTypes`，并把命中的**判据**固定到 `input.panjuTypes`
（供六经阶段消解「病位×病性」交叉积）；随后 `miniCtxMgr.clearByPrefix(patientIri)`
清掉推理上下文，使下一阶段重建时带上物化八纲、且可省去判据层 seed。

### ⑤ `liujing-classification` — 六经分类

| 项 | 内容 |
|---|---|
| 推理 | `withLiujingReasoner` → `extractLiujingModule`（**阶段 1 minibox**） |
| 处理 | 取患者推理类型 ∩ 六经白名单 → **交叉积消解** → **六经消解**（当前停用）→ 合病标记 → **物化** |
| 输出 | `sixChannel`、`sixChannelCn`、`liujingTypes`、`liujingTypesCn`、`isCombinedChannel`、`combinedDiseaseMark` |
| 错误码 | `LIUJING_FAILED` |

**六经 ≡ 病位 ⊓ 病性**：太阳=表⊓阳、阳明=里⊓阳、少阳=半表半里⊓阳、
太阴=里⊓阴、少阴=表⊓阴、厥阴=半表半里⊓阴。

**交叉积消解**（`resolveLiujingCrossProduct`）：

- **问题**：本体未声明病位之间、病性之间互斥，故患者同时具备 ≥2 病位与 ≥2 病性时，
  推理机会推出「病位×病性」的**完全交叉积**伪影。例：柴胡桂枝干姜汤证患者八纲 =
  半表半里+里+虚+阳+阴 → 推出少阳/厥阴/阳明/太阴四经，而实际当为「少阳太阴合病」。
- **医理依据**：病性与病位并非自由组合，而由**判据绑定**。判据类同时 ⊑ 病位与 ⊑ 病性者
  即锁定该组合（`Panju_C6`（往来寒热+胸胁苦满）⊑ 半表半里 ⊓ 阳 → 少阳；
  `Panju_B8`（腹满+虚寒脉）⊑ 里 → 里配阴 = 太阴）。
- **算法**（**仅当**推出的六经恰为「病位 × 病性」的**完全交叉积**时启用；单经、正常合病、
  三阳合病等「部分交叉」均原样返回）：
  1. 对每个病位 p：若患者命中的某判据 J ⊑ p 且 J ⊑ 某病性 s，则 p↔s；
  2. 未被判据绑定的病位，与未被占用的病性配对（按排序稳定分配）；
  3. 病位+病性 → 六经，仅保留推理机已推出的六经。

**合病标记**（`buildCombinedDiseaseMark`）：三阳合病、太少两感，以及 15 种两经合病
（太阳阳明 / 太阳少阳 / 少阳阳明 / 阳明太阴 / 少阳太阴 / 太阴少阴 / 少阴厥阴 …）；
未列出的多经组合按太阳→阳明→少阳→太阴→少阴→厥阴顺序拼接「X Y 合病」。

> 铁律 35：六经提纲证**不足以反推病位**；铁律 41：合病方证的六经**只能写注解**，
> 不能写等价类（否则交叉推出 4 个六经）。

### ⑥ `fangzheng-classification` — 方证分类

| 项 | 内容 |
|---|---|
| 推理 | `withLiujingReasoner`（取阶段1类型）→ `withFangzhengReasoner`（**阶段 2 minibox**） |
| 处理 | realize 命中集 + 候选池打分排序 → 结果形态 → 双路径 → 证据明细 |
| 输出 | `fangzheng` / `fangzhengCn`、`fangzhengTypes`、`candidateFangzhengs(Cn)`、`candidateScores`、`candidateMatchedMain(Cn)`、`candidateMissingMain(Cn)`、`candidateMatchedPoss(Cn)`、`outcome`、`matchedMainSymptoms(Cn)`、`matchedPossSymptoms(Cn)`、`fitScore`、`realizedCount`、`pathA`、`pathB`、`fangzhengRealized`、`fangzhengCandidates` |
| 错误码 | `FANGZHENG_FAILED` |

**双通道**：

- **realize 命中**（推理机完全命中方证充要定义）→ 才算结论。
- **候选池**：`filterFangzheng` 按阶段1类型 + 患者四诊 + 物化八纲筛出相关方证，
  缓存于 `fangzhengCandidatesCache`；`rankCandidatesWithScores` 按
  `hits/required、gap、poss、prio` 结构化打分排序（**无自由权重**）。

**结果形态** `outcome`：

| 值 | 条件 | 语义 |
|---|---|---|
| `CONFIRMED` | realize 命中 1 个 | 直接输出，并告知命中了哪个主证 |
| `CONFIRMED_MULTI` | realize 命中多个 | 按符合度排序，Top1 为结论，其余作「或然/并列候选」 |
| `NO_MAIN_MATCH` | realize 零命中 | `fangzheng = "方证未定"`，候选**不得冒充结论**（铁律 16） |

**双路径**（仅 `NO_MAIN_MATCH` 时生成，`analyzeGaps`）：

- **路A 追问**：两层——第一层**判据缺口**（定八纲/六经），第二层**方证主证缺口**（定方证）。
  只对 `gap ≤ GAP_MAX(=2)` 者生成；**剔除抽象类**（八纲/六经不得作为可选项暴露给用户，
  铁律 62）；**互斥过滤**（与已输入症状互斥者不得作为追问选项，铁律 64.2）。
- **路B 或然症候选**：`evidence = POSS_ONLY`，**永不写入结论**。

**阈值常量**：`CANDIDATE_DISPLAY_TOP_N = 10`、`FALLBACK_TOP_N = 25`、`GAP_MAX = 2`。

**方证父子层级**（`FANGZHENG_PARENT_TO_CHILDREN`）：依「方随证转、随证加减」，
母方与子方得分接近时**优先子方**（白虎汤类、柴胡汤类、理中汤类、栀子豉汤类、半夏泻心汤类）。

### ⑦ `jianjiazheng-classification` — 兼夹证

| 项 | 内容 |
|---|---|
| 推理 | `withLiujingReasoner` + `extractFragmentsByMetaClass(..., jianJiaSubclasses)` |
| 输出 | `jianJiaZhengs`、`jianJiaZhengsCn` |
| 错误码 | `JIANJIAZHENG_FAILED` |

兼夹证是**加味来源**：其 `addHerbs` 注解在 ⑧⑨ 阶段被读取为加味药物。

### ⑧ `prescription-recommendation` — 母方推荐

| 项 | 内容 |
|---|---|
| 输入 | `fangzheng`、`jianJiaZhengs`、患者症状 |
| 处理 | 方证 → 方剂（注解 `hasFormula`）→ OBDA 查组成 → 方剂注解加减味 → 兼夹加味 → **方后注加减派生** → **配伍禁忌检查** |
| 输出 | `finalFormula(Cn)`、`baseFormula(Cn)`、`baseHerbs(Cn)`、`herbs(Cn)`、`addedHerb(Cn)`、`removedHerb(Cn)`、`warnings`、`derived`、`derivedFormulaName`、`appliedRules`、`ruleSources`、`dosageChanges`、`yaozhengApplied`、`yaozhengNotes` |
| 错误码 | `PRESCRIPTION_FAILED` |

- 方证未定 / 无方剂 → 输出 `emptyRx()` 后正常完成。
- **药证兜底**：无规则命中且症状超出主证范畴时启用。

### ⑨ `herb-modification` — 加减药（方后注派生）

| 项 | 内容 |
|---|---|
| 输入 | `fangzheng`、`baseFormula`（⑧ 输出）、`baseHerbs(Cn)`、`addedHerb`/`removedHerb`、患者症状 |
| 处理 | 与 ⑧ **共用 `computeHerbModification`**，保证两步结果**逐字段一致** |
| 输出 | `finalFormula(Cn)`、`herbs(Cn)`、`derived`、`appliedRules`、`ruleSources`、`dosageChanges`、`removedHerb(Cn)`、`addedHerbCn`、`warnings`、`herbModificationApplied`、`herbModificationSummary` |
| 错误码 | `HERB_MODIFICATION_FAILED` |

**规则引擎**（`rules.owl` v2.7，46 方证 / 84 规则）：

- 规则形式：`IF <症状合取> THEN remove X + add Y (剂量) + ...`，附 `ruleSource` 出处。
- **解析要点**：OWLAPI 的 `annotationAssertionAxioms()` **不保证文档顺序**，无法把
  `addHerbRule` 与其 `ruleSource` 按位置配对；故**直接按 XML 文档顺序**解析源文件，
  保证「规则 ↔ 出处」一一对应。
- 多条规则可同时命中。

### ⑩ `diagnosis-explanation` — 诊断解释

| 项 | 内容 |
|---|---|
| 输入 | `sixChannelCn`、`fangzhengCn`、`finalFormulaCn`、`derived`、`baseFormulaCn`、`ruleSources` |
| 输出 | `explanation`（如「六经：太阴病，方证：理中汤证，推荐方剂：理中汤。」；派生时附「本方由X依方后注加减法派生（依据：…）」） |
| 收尾 | `clearPatientCache(patientIri)` 清理 `patientInputs` / `fangzhengCandidatesCache` / minibox 上下文 |
| 错误码 | `EXPLANATION_FAILED` |

## 五、推理内核：三阶段 minibox + 每步物化

> 铁律 37：真正的生产推理路径**不是** `SixChannelInferenceEngine`，而是 Worker 的
> 「模块抽取」两阶段（现为三阶段）。铁律 40：八纲/六经/方证**各用各的模块**。

### 5.1 三阶段模块集

| 阶段 | 方法 | 模块 seed | 说明 |
|---|---|---|---|
| **阶段 0 · 八纲** | `extractBagangModule` | 患者症状 + 八纲类 + **判据层** + 顶层类 + ABox 个体类型 | 不含六经白名单/兼夹/方证 → 模块最小、最快 |
| **阶段 1 · 六经+兼夹** | `extractLiujingModule` | 患者症状 + **六经白名单** + 八纲类 + 兼夹证 + 顶层类 +（**八纲未物化时**才加判据层） | 八纲已物化则省判据层 seed → 更小更快 |
| **阶段 2 · 方证** | `extractFangzhengModule` | 患者症状 + `filterFangzheng` 筛出的相关方证 + **物化八纲/六经** + 顶层类 | 方证匹配直接消费物化结果 |

公共步骤：`collectClassClosure` → `extractTBoxModule` → **`stripDisjointAxioms`**。

### 5.2 每步物化（关键机制）

```
八纲阶段结束 → input.bagangTypes = 八纲fragments
             → input.panjuTypes  = 命中的判据fragments
             → miniCtxMgr.clearByPrefix(patientIri)   ← 清上下文

六经阶段结束 → input.liujingTypes = 六经fragments
             → miniCtxMgr.clearByPrefix(patientIri)

方证阶段     → 消费 input.bagangTypes + input.liujingTypes
```

物化使「上游结论」作为**固定值**进入下游模块 seed，下游无需重推上游，
既保证单向性（铁律 60），又显著缩小模块、缩短推理时间。

### 5.3 互斥公理剔除

`stripDisjointAxioms` 把 `owl:disjointWith` 从**分类推理模块**中剔除，
互斥关系只保留在「四诊互斥索引」中，用于：

1. **追问过滤**（路A）——互斥症状不得作为追问选项；
2. **四诊参合矛盾检测**（一致性检查节点）。

> 铁律 64.4：互斥公理**不得**进入分类推理模块。原因：一旦进入，矛盾四诊会让推理机
> 判定本体不一致而中断整条流程。

### 5.4 性能要点

| 措施 | 效果 |
|---|---|
| TBox/ABox 分离 | `CLASS_HIERARCHY` 345s → 47s（988 个体移出 TBox 入口） |
| 关 CD 分类 + 高级缓存 | precompute 中位数 84.7s → 18.7s |
| 三阶段 minibox | 每阶段只加载相关类闭包，避免全本体分类 |
| 物化 + 上下文清理 | 下游免重推上游；避免跨阶段缓存膨胀 |

### 6.2 TBox / ABox 分离（铁律 55、56）

- **ABox 已从 TBox 入口移出**（2026-09-20），改由 `tcm-all-abox.owl` **单独加载**。
- 原因：`OntologyService.gettBoxOntology()` 会合并「所有已加载本体」的全部公理，
  ABox 混入后 Openllet 分类会对每个类做 ABox 一致性检查
  （`CDOptimizedTaxonomyBuilder.checkSatisfiability → ABoxImpl.isConsistent`），
  988 个体使 `CLASS_HIERARCHY` 达 345s。移出后实测 **345s → 47s**。
- **ABox 不能删，只能「搬家」**（铁律 55）：诊断链路靠它查「症状个体 → 类」。
- `fangji-abox` / `yaowu-abox` 已迁入 MySQL，不再在本体加载。

### 6.3 SKOS 词表

- `tcm-zhengzhuang_skos.ttl` 为**纯词表**：737 个 `skos:Concept`，
  `subClassOf` / `equivalentClass` 均 **0 条**，对六经推理**零贡献**。
- 加载方式：`OntologyService.loadOntologyFilesWithOWL` 两段式——`AutoIRIMapper` +
  扫描目录下 `.ttl`，用 `TurtleDocumentFormat` 解析出 `owl:Ontology` IRI，
  再注册 `SimpleIRIMapper`。
- ⚠️ **离线测试注意**：OWLAPI `AutoIRIMapper` 扩展名白名单硬编码为
  `{.owl,.xml,.rdf,.omn,.ofn}`，**不含 `.ttl`**，且内部走 SAX 解析（Turtle 加进白名单也无效）。
  故任何离线加载 `tcm-all.owl` 的测试**必须复刻上述两段式**，否则会退化为 HTTP 请求
  并抛 `UnloadableImportException`。详见 `design/22 离线测试加载与套件运行器缺陷修复.md`。

| 一致性检查 | 依赖 Openllet 判本体不一致 | **互斥索引**（互斥公理已剔出推理模块） |
| 症状输入 | 手工录入 OWL 个体断言 | **自然语言 → SKOS 词表 + LLM 白名单映射**（737 个体 / 1231 同义词） |
| 无结论时 | 未定义 | **三态结果 + 双路径**（路A 追问 / 路B 或然症候选） |
| ABox | 与 TBox 同文件 | **TBox/ABox 分离**（345s → 47s） |
| 性能 | 未涉及 | 关 CD 分类 + 高级缓存（84.7s → 18.7s） |
