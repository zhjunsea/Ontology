## 铁律 15：「未定」占位符绝不能进候选列表 —— 否则零匹配输入被误判为诊断成功

`TCMOntologyJobWorker` 的方证 worker 在无候选时会把 `fangzheng = "方证未定"`，
若把它一并 `add` 进 `topCandidates`（→ `fangzhengTypes` / `candidateFangzhengs`），会连带触发两处误判：

- BPMN `Gateway_HasRecommendation` 的 `fangzhengTypes != []` 成立 → 走 `EndEvent_Success`；
- Java `hasRecommendation` 的 `fangzhengCn != null` 成立 → `outcome=DIAGNOSED`。

结果：「今天天气不错我想去公园散步」这种 0 匹配输入被显示成一次成功诊断。

**修复原则（双保险）**：
1. worker 侧：占位符**只**写进 `fangzheng` / `fangzhengCn`（供前端显示「方证未定」），
   **不写进** `fangzhengTypes` / `candidateFangzhengs`（保持空列表）。
   注意下游有 `"方证未定".equals(fangzhengFragment)` 的短路判断，`fangzheng` 本身**不能**改成 null。
2. 服务侧：判定「有无推荐」时把 `方证未定` / `六经难定` / `未定` 视为空。

**验证要落到「实际经过哪个终止事件」**，不能只看 Java 返回的 `outcome`：

```bash
curl -s -X POST http://localhost:9080/v2/element-instances/search \
  -H "Content-Type: application/json" \
  -d '{"filter":{"processInstanceKey":"<key>"},"page":{"limit":200}}'
# 期望：正常输入含 EndEvent_Success；无关输入含 EndEvent_NoResult
```

## 铁律 16：结果形态三态化 —— 只有「完全 realize」才算诊断结论

方证分类必须区分两种来源，**不能混为一谈**：

- **完全 realize**：Openllet 推理把患者个体归入该方证类（`realizedMatches` 非空）→ 这才是**确定性结论**；
- **仅候选**：只是 Jaccard 打分排出来的候选项 → 只能作为**候选**展示，不得冒充结论。

流程与代码的三态映射（v1.4 起）：

| 形态 | BPMN 终止事件 | 网关条件 | `outcome` |
| --- | --- | --- | --- |
| 完全 realize | `EndEvent_Success` | `=fangzhengRealized = true` | `DIAGNOSED` |
| 有候选未 realize | `EndEvent_Candidates` | `=fangzhengRealized = false and fangzhengCandidates != null and fangzhengCandidates != []` | `CANDIDATES` |
| 无候选 | `EndEvent_NoResult` | `=fangzhengRealized = false and (fangzhengCandidates = null or fangzhengCandidates = [])` | `NO_RESULT` |

要点：
1. `Gateway_HasRecommendation` 是**三分支**互斥网关，三条 FEEL 条件必须覆盖且互斥（结构测试
   `outcomeGatewayThreeWayConditions` 守护）。
2. worker 输出 `fangzhengRealized`（boolean）+ `fangzhengCandidates` / `fangzhengCandidatesCn` /
   `fangzhengCandidateDetails`；`fangzhengCandidateDetails[i].hitSymptoms` 是该候选**命中的症状**
   （元素 `{fragment, label}`），供前端逐条展示。
3. `TCMDiagnosisService.outcomeOf` 的判定顺序：`fangzhengRealized=true` → DIAGNOSED；
   `fangzhengCandidates` 非空 → CANDIDATES；旧 fallback → DIAGNOSED；否则 NO_RESULT。
4. 新增终止事件后，**务必同步补 BPMNDI**（`EndEvent_Candidates_di` + `Flow_HasRecommendation_Candidates_di`），
   否则结构测试的「图形信息完整」断言会失败。
5. 验证同样要落到「实际经过哪个终止事件」（见铁律 15 的 element-instances 查询）。

## 铁律 18：候选排序「小定义方证胜出」是 Jaccard 分母被六经症状池灌大的结果

**症状**：临床直觉上该排第一的方证（如 白头翁汤证）排在某个「后世小方」之后（如 温胆汤证）。

**排查三步**（照此顺序，别乱猜）：
1. 看 `fangzhengCandidateDetails` 的 `hits` / `required` / `jaccard` / `hitSymptoms`。
2. 打开本体看该方证的 `equivalentClass`，**特别注意它是否以某个六经类（如 `Jueyinbing`）为合取项**。
3. 看那个六经类的 `equivalentClass` 是否要求多个支路同时成立。

**机制**：`ScoredFangzheng.jaccard() = hits / (patientSize + required - hits)`，而
`required` 由 `OntologyModuleUtils.collectRestrictionFillers` 计算，它会
**递归继承父类/合取类的限制**（`subClassAxiomsForSubClass` + 递归进 named class）。
所以「⊑ 某六经病」的方证，其 `required` 会把**整个六经病的症状池**算进分母：

- 白头翁汤证 ≡ `厥阴病 ∧ 下利 ∧ 里急后重`；厥阴病要求「上热（消渴/气上撞心/心中疼热）**且** 下寒（手足冷/下利/沉微/饥不欲食/吐蛔）」→ required=11。
- 温胆汤证 ≡ `心烦 ∧ 不得眠` → required=2。
- 患者「下利，里急后重，脉大，苔黄，不得眠」（5 症）：
  温胆汤证 1/2 → 1/(5+2-1)=**0.167**；白头翁汤证 2/11 → 2/(5+11-2)=**0.143** → 小定义方证胜。

**关键推论**：这类方证**永远不会 realize**，因为它的 `equivalentClass` 含六经合取项，
而六经定义若太窄（如厥阴病要求上热下寒俱全），纯「热利下重」患者推不出厥阴病。
**验证手法**：补上该六经病的完整证候再跑一次——若立刻 realize 并给出正确方证，
就证明是「六经定义过窄」而非「方证定义错误」。
（实测：`消渴，气上撞心，心中疼热，下利，里急后重` → DIAGNOSED / 厥阴病 / 白头翁汤证。）

**修复方向（择一，需医学判断，勿擅自改本体）**：
- 本体侧：该方证不以六经类为必要条件；或放宽六经定义；或给方证独立充分条件。
- 打分侧：`required` 不计继承来的六经级症状池；或改用「本方证自身鉴别症状覆盖率」；
  或对高特异性症状（里急后重/下利）加权。

## 铁律 19：区分「呈现语义」与「排序语义」——改前者不要声称修了后者

排查「为什么给出 X 方证」时，先 `git log` / `git diff` 确认**当前改动到底动了什么**。
本工程曾出现：未 realize 时旧代码 `fangzheng = displayScored.get(0).fragment()`
**直接把 Jaccard Top1 候选当成方证**（仅服务端 `log.warn`，用户不可见）；
改为 `fangzheng = "方证未定"` + 独立候选列表后，**排序没变，只是不再冒充结论**。
所以「改了呈现」不等于「改了排序」——回答用户时必须讲清是哪一种。

## 铁律 21：三个「象」文件的层级状况完全不同 —— 症状是扁平的

做任何「按症状/脉/舌归类」的统计或推理前，先知道这个事实：

| 文件 | 类数 | 层级 | 证据 |
|---|---|---|---|
| `tcm-maixiang.owl`（脉象） | 68 | ✅ **已分层 + 已有组合层** | 38 个复合脉用**多重 `subClassOf` + `equivalentClass` 交**：`Fujinmai 浮紧脉 ⊑ Maixiang, Fumai, Jinmai` |
| `tcm-shexiang.owl`（舌象） | 71 | ⚠️ **有分类树，但无组合层** | 7 个维度（舌质颜色/舌苔/舌形/舌态/舌下络脉/舌面润燥/苔色苔质），**`equivalentClass` 0 处、`intersectionOf` 0 处** |
| `tcm-zhengzhuang.owl`（症状） | 576 | ❌ **扁平** | **563/576（97.7%）** 直接 `subClassOf Zhengzhuang`，仅 ~13 个有其它父类 |

**量化对比（判断「有没有组合层」的快捷手法）**：

```python
t.count('equivalentClass'), t.count('intersectionOf')
# tcm-maixiang.owl → 78, 76   ← 有组合层
# tcm-shexiang.owl →  0,  0   ← 无组合层（红舌与黄苔在两条互不相干的支路上）
```

**复合脉的现成模板**（舌象/症状要建组合层时照抄）：

```owl
<owl:Class rdf:about="#Fujinmai">
    <rdfs:subClassOf rdf:resource="#Maixiang"/>   <!-- 根 -->
    <rdfs:subClassOf rdf:resource="#Fumai"/>      <!-- 原子 1 -->
    <rdfs:subClassOf rdf:resource="#Jinmai"/>     <!-- 原子 2 -->
    <rdfs:label xml:lang="zh">浮紧脉</rdfs:label>
    <rdfs:comment xml:lang="zh">《伤寒论》3条、35条：伤寒，麻黄汤证核心脉。</rdfs:comment>
    <owl:equivalentClass><owl:Class><owl:intersectionOf rdf:parseType="Collection">
        <owl:Class rdf:about="#Fumai"/><owl:Class rdf:about="#Jinmai"/>
    </owl:intersectionOf></owl:Class></owl:equivalentClass>
</owl:Class>
```

模式 = **多重 `subClassOf`（供归类）+ `equivalentClass` 交（供定义）+ `rdfs:comment` 引条文**。

**推论（很重要）**：
- 「脉舌能归类、症状不能归类」的根因是**结构问题，不是医学问题**。
- `干呕` / `呕` / `吐` / `哕` / `噫气` 在症状本体里是**平级兄弟类**，本体不知道它们相关。
- 需要「细粒度 ⊑ 粗粒度」时，**脉象已有现成模板可照抄**，症状侧需自行补，
  但**最小可行范围只需覆盖判据用到的症状**（数十个，不是 576 个）。
- 补层级必须是**投影不是替换**：细粒度类原样保留（方证鉴别用，`干呕 ≠ 呕 ≠ 吐` 决定不同方证），
  只**新增**一条粗粒度父类边供上层使用。

## 铁律 22：`belongsToLiujing` 是「篇章归属」，不是「八纲归属」

`belongsToLiujing` 记录的是方证在《伤寒论》**篇章中的位置**，与胡希恕体系的八纲归属**不一致**。

**铁证**：`shaoyin_taiyin.owl` 的 `Sinitangzheng`（四逆汤证）：
```
belongsToLiujing = 少阴病
you_zhengzhuang  = 手足冷、下利清谷     ← 两个都是「里寒」症状
```
- 本体：四逆汤证 → 少阴病（少阴病篇位置）
- 胡希恕：四逆汤证 → **太阴病（里阴证）**；少阴病是**表阴证**（麻黄附子细辛汤类）

**后果**：拿 `belongsToLiujing` 推病位，`下利清谷` 会被算成「表」，与医理「里」直接冲突；
大量「里」症状因挂在少阴/厥阴方证下被算成「表/半表半里」→ **普遍多值**。

**用法约束**：
- ❌ 不要用它推导八纲（病位/病性）。
- ✅ 只用于**校验/展示**（辨出的六经 vs 方证归属，不符则报警）。
- 统计判据资格时，**合病方证（`belongsToLiujing` 多值）必须排除**，否则症状分布被「灌宽」
  （例：呕吐 全口径=表,里；仅单经方证=**里**）。

## 铁律 23：八纲判据的准入标准 —— 必须能定八纲；定不了的**不是「低级别」，而是「不在这张表里」**

给八纲写判据时的**准入标准**（用户定）：**每条判据必须能定八纲**。

**⚠️ 已废弃的四级模型（v2/v3 的 A/B/C/D）**：曾把「定不了八纲、只定证素」的舌象列为 **D 级**。
**用户裁定这是概念错误**：「定不了八纲感觉没有意义，为啥要建 D 级？」
→ **D 级取消**。定不了八纲的舌象**不是判据的低级别**，而是**证候组合层的成员**（见铁律 24）。

**现行模型（v4）：两层分离**

| 层 | 目标 | 舌象成员 | 落点 |
|---|---|---|---|
| **八纲判据层** | **八纲** | **A 级**（单象定）：淡白舌→`Han`+`Xu`、红舌→`Re`、绛舌→`Re`、黄苔→`Re`<br>**B 级**（组合才定）：黑燥苔→`Re`、黑滑苔→`Han`、灰燥苔→`Re`、灰滑苔→`Han` | 挂**具体**的 `Han`/`Re`/`Xu`/`Shi`（阴阳靠 4 条 axiom 上溯）；病位判据挂 `Biao`/`Li`/`Banbiaobanli` |
| **证候组合层** | **证候/证素** | Z-1 瘦薄舌⊓淡白舌→气血两虚；Z-2 瘦薄舌⊓红绛舌→阴虚火旺；Z-3 点刺舌⊓大热→脏腑热盛；Z-4 灰腻苔→湿浊<br>单象→证素：紫舌/青舌→血瘀、胖大/齿痕→水湿、裂纹→津伤、腻/腐→湿浊、剥/镜面/无苔→胃气伤、舌下络脉→血瘀、白苔→表/寒/湿、薄/厚→病位、润/滑/燥/糙→津液 | `⊑ ZhengHouZuhe`，再由证候→八纲 |

**组合必要性判据（用户铁律 5）**：**能单独定的就直接定，不加组合**（加组合是冗余）；
**组合只在「单个不能定」时才需要**。

| 组合 | 八纲层 | 证候层 |
|---|---|---|
| 淡白舌⊓白苔 | ❌ 冗余（淡白舌已定阴） | ❌ 也冗余（白苔不带新证素） |
| 紫舌⊓畏寒 | ❌ 冗余（畏寒已定阴） | ✅ 可留（寒凝血瘀是证候） |
| 瘦薄舌⊓舌色 | ❌ 冗余（舌色已定阴阳） | ✅ 进（气血两虚 / 阴虚火旺） |
| 点刺舌⊓大热 | ❌ 冗余（大热已定阳） | ✅ 进（脏腑热盛） |
| 灰腻苔 | 本就不定八纲 | ✅ 进（湿浊证素） |

→ **八纲判据层里真正需要组合的只有灰黑苔 4 个**（单看苔色定不了寒热）。

**两条关键医理（有医书依据，勿凭直觉改）**：

1. **舌象不能单独定病位**。依据《医门棒喝》：**「望舌不过察病之标，必合脉症方得其本。」**
   表证舌象基本正常（淡红舌薄白苔，正常人也如此）→ 无特异性；少阳舌象也无特异性。
   → 「薄苔→表」「厚苔→里」**不能作独立判据**，只能作弱佐证。
2. **黑苔判寒热靠「苔色 + 苔质润燥」组合，不是靠颜色**。
   - 国家中医药管理局《中医基础术语》：「黑苔……主里证，或为热极，或为寒盛。苔黑而**燥裂**……**热极津枯**；苔黑而**滑润**……**寒盛阳衰**」
   - 《伤寒金镜录》：「舌内有黑形如小舌者，乃**邪热结于里**也」
   - 《舌鉴辨证》（寒极）：「**虚寒而舌黑者，则必湿滑无苔，多津，口不苦，唇不燥，无朱点，无芒刺，无罅裂，刮之明净，如水浸猪腰**……是**脏腑极寒**之舌也」
   - **灰苔同理**：《辨舌指南》「**灰色苔者，即黑苔之轻也**……**当与黑苔同治**」→ 灰燥苔→阳、灰滑苔→阴。
   → 该书区分寒热**列了 7 个指征**，不是只看颜色。

**推论：凡「双向」的舌象/症状都不能单独定八纲**，必须与其他证据组合。
- **紫舌/青舌**：既主寒凝血瘀又主热盛血瘀 → 不能单独定病性，更不能靠苔色定，须配症状。
- **白苔**：主表（阳）/寒（阴）/湿 → 双向，不定病性。
- **黑苔、灰苔**：双向，须配苔质润燥。
- **瘦薄舌**：瘦薄而色淡→气血两虚(阴)；瘦薄而色红绛干燥→阴虚火旺(阳) → 双向，靠舌色。
- **点刺舌**：主热盛但特异性不足（正常人舌尖可见）→ 须配大热。
- **积粉苔**：主流主热毒(阳)，但许公岩主「脾胃寒湿之极」(阴) → **有争议，不列 A 级**。

## 铁律 24：两层分离 —— 「八纲判据层」与「证候组合层」是两张表，不是一张表的两个级别

**用户裁定**：「定成 D 级感觉没有意义，为啥要建 D 级？」

**核心**：一个舌象/症状**定不了八纲 ≠ 它是判据的低级别**，而是它**根本不是八纲判据**。

| | 八纲判据层 | 证候组合层（`ZhengHouZuhe`） |
|---|---|---|
| 目标 | **八纲** | **证候 / 证素** |
| 判据资格 | 必须能定八纲 | 不要求定八纲 |
| 组合必要性 | 组合**才**定出八纲 | 组合**坐实**证候 |
| 落点 | `⊑ Han/Re/Xu/Shi`（阴阳靠 axiom 上溯）/ `Biao`/`Li`/`Banbiaobanli` | `⊑ ZhengHouZuhe`，再由证候→八纲 |

**证候组合层允许跨证据层**（舌 ⊓ 症 ⊓ 脉）：如 Z-3「点刺舌 ⊓ 大热」是舌象⊓症状。
这与用户「青紫舌应与其他**症状**组合」的裁定一致。

**OWL 要点**：证候组合类**不写** `⊑ Yin`/`⊑ Yang`（八纲由组合中的舌色/大热成分定，
或本就不定八纲），只写 `⊑ ZhengHouZuhe` + `equivalentClass` 交。

**⚠️ 证候不设「阴阳归属」**（用户裁定：「**阴虚火旺为啥一定要有阴阳归属？这个单一[证候]不能归属，就用组合症状。**」）：

- **证候不是八纲判据，不该有阴阳归属**。问「阴虚火旺属阴还是属阳」是**层次错位** ——
  证候组合层的产物是**证候**，阴阳是**八纲判据层**的事。
- 阴阳由**组合成分**提供（红绛舌→`Re`→阳、淡白舌→`Han`+`Xu`→阴、大热→阳）。
- **不要**在文档/表格里给证候设「证候→八纲」列，也**不要**在 `rdfs:comment` 写「证候→八纲：X」。
- 这正是铁律 5「单个不能定就用组合」的体现：**组合的产物是证候，阴阳来自成分**。

## 铁律 27：胡希恕「**寒热有常，而虚实无常**」—— 判「虚＋热」类证候阴阳归属的终极依据

**问题**：`阴虚火旺`（虚＋热）到底属阴还是属阳？三种说法都"有道理"：
① 虚属阴→阴；② 热属阳→阳；③ 阴阳俱见。

**答案（胡希恕，冯世纶整理，北京市中医药管理局官网刊载）**：

> 「**寒者必阴，热者必阳，在任何情况下永无变异**。但虚实则不然，当其与寒热交错互见时，反其阴阳，
> 即如虚而寒者，当然为阴，但**虚而热者，反而为阳**。」

**规则**（判定阴阳的优先级）：

| 情形 | 阴阳 | 依据 |
|---|---|---|
| 有**寒**（不论虚实） | **阴** | 寒者必阴（**有常**） |
| 有**热**（含**虚热**） | **阳** | 热者必阳（**有常**） |
| **不寒不热** | 实→阳、虚→阴 | 虚实定阴阳（**无常**，仅在无寒热时生效） |

**关键**：**寒热是「有常」的（决定阴阳，永不反转）；虚实是「无常」的（会被寒热反转）**。
所以「虚属阴」只是**总纲层面的泛言**（胡希恕：「泛言阴，则不定必寒」），
一旦与「热」并见，就被反转。

**推论（写判据/证候→八纲映射时直接用）**：

| 证候 | 组成 | 阴阳 |
|---|---|---|
| 气血两虚 | 虚＋**无热** | **阴** |
| **阴虚火旺** | 虚＋**热**（虚热） | **阳** |
| 阳虚（虚寒） | 虚＋寒 | 阴 |
| 实热 | 实＋热 | 阳 |
| 实寒 | 实＋寒 | 阴 |

→ **同为虚证，因寒热不同而分属阴阳**。这就是「虚实无常」的落地。

**「阴阳俱见」的适用边界**：胡希恕的「阴阳俱见」指**寒热并见**（上热下寒之类 → 厥阴病）。
**只有热、没有寒**的证候（如阴虚火旺）**不是**阴阳俱见，不能套用。

**出处权威性排序**（本项目采用）：
1. 胡希恕「寒热有常，虚实无常」（**判定规则**，专门解决此问题）← **取这个**
2. 《中医诊断学》「表、热、实隶属于阳；里、寒、虚统属于阴」（**总纲概括**）
3. 一般「寒热错杂」套用（**边界不符**，阴虚火旺无寒）

**⚠️ 适用范围（重要，勿越界）**：本原则用于**八纲判据层** ——
当某条**判据**（如复合脉「细数脉」= 虚＋热）同时含虚与热时，用它定阴阳（**虚＋热→阳**）。
**不用于**给**证候组合层**的证候（阴虚火旺等）贴阴阳标签 —— **证候不挂八纲**（见铁律 24）。
「阴虚火旺属阴还是属阳」是**层次错位**的提问，正确做法是**由组合成分提供阴阳**。

## 铁律 28：4 条八纲 axiom —— `Re/Han` 是**硬约束**，`Xu/Shi` 是**可反转默认值**（写本体时勿写死）

**背景**：本体 `Bagang` 下 9 个子类**彼此平级、零 axiom**。依医理（铁律 26）应补 4 条：

```owl
<owl:Class rdf:about="#Re"><rdfs:subClassOf rdf:resource="#Yang"/></owl:Class>
<owl:Class rdf:about="#Shi"><rdfs:subClassOf rdf:resource="#Yang"/></owl:Class>
<owl:Class rdf:about="#Han"><rdfs:subClassOf rdf:resource="#Yin"/></owl:Class>
<owl:Class rdf:about="#Xu"><rdfs:subClassOf rdf:resource="#Yin"/></owl:Class>
```

**⚠️ 但 4 条的性质不同**（依胡希恕「寒热有常，虚实无常」，铁律 27）：

| axiom | 性质 | 理由 |
|---|---|---|
| `Re ⊑ Yang`、`Han ⊑ Yin` | **硬约束**（可放心写死） | 「寒者必阴，热者必阳，**永无变异**」 |
| `Xu ⊑ Yin`、`Shi ⊑ Yang` | **默认值**（**遇寒热反转时失效**） | 「虚而**热**者反而为**阳**；实而**寒**者反而为**阴**」 |

**实施坑（必看）**：若把 `Xu ⊑ Yin` 当硬约束写死，则
**「阴虚火旺」= 虚 + 热 → 会被推理机判成阴证**（错，应为阳证 / 阳虚热证）。
同理 `Shi ⊑ Yang` 写死会把**寒实结胸（实 + 寒）判成阳证**（错，应为阴证）。

**正确做法**：把 `Xu`/`Shi` 的阴阳归属**交给含寒热的复合判据去定** ——
即判据挂 `Han`/`Re`（硬）或挂含寒热的具体组合，**不要**单靠 `Xu`/`Shi` 上溯阴阳。

**实施现状（v4.6，用户确认 ② 后落地）**：4 条 axiom **全部**以 `rdfs:subClassOf` 写入
`tcm-core.owl`（`Han/Re/Xu/Shi` 各加一条 `subClassOf #Yin`/`#Yang`），并各附 `rdfs:comment`
标注「有常/无常」。Openllet 实测：`PaleWhiteTongue → {Han, Xu, Yin}` ✅、`RedTongue → {Re, Yang}` ✅。

> **遗留风险（v4.8 已裁定，方案 A）**：`Xu ⊑ Yin` 写死后，一个同时 ⊑ `Xu` 与 ⊑ `Re` 的类
> （如「阴虚火旺」型判据）会被推断为 **`Yin` 与 `Yang` 并见**（= 寒热错杂 / 阴阳俱见）。
> 这**未必是错**（胡希恕「阴阳俱见 → 厥阴病」）—— **用户已裁定「同时为阴阳也可以，不是问题」**，
> 故**保留硬 ⊑**（方案 A）。**实测（2026-09-18）当前本体无任何实体同时挂「虚+热」或「实+寒」**，

>
> **未来风险（实施 ⑤/⑥ 前须裁定）**：一旦新增「虚+热」判据（细数脉、虚热证）或「实+寒」判据

## 铁律 32：逻辑链是 **判据 → 八纲 → 六经 → 方证**；**别把代码的运算顺序当成逻辑顺序**

**背景**：排「剩余步骤实施顺序」时，我据代码写成「方证判定只用六经不用八纲；八纲由六经反推」，
据此误判「改八纲（⑥）不会波及方证（⑦⑧）」。**用户纠正**：
> 「不应该是先判定八纲，然后根据八纲定六经，然后根据六经定方证吗？只能说是不直接用八纲吧，是八纲推出来的。」

**正确的逻辑链（设计 §0.1/§0.2）**：
```
判据（症状组合 / 脉象组合 / 舌象 A-B 级）
  │ 判定
  ▼
八纲（病位：表/里/半表半里；病性：阴/阳）
  │ 定义式组合（六经 = 病位 × 病性，§0.2「无推理」）
  ▼
六经（太阳/阳明/少阳/太阴/少阴/厥阴）
  │ 空间约束
  ▼
方证
```
**方证不直接用八纲，但八纲经六经间接决定方证 → 八纲是方证的「上游硬依赖」。**

**⚠️ 实测：本体与代码的方向与设计相反（真实缺口）**：

| 环节 | 设计（§0.2/§7.1） | 本体实现 | 代码实现 |
|---|---|---|---|
| 六经定义 | `六经 ≡ 病位 ⊓ 病性` | `六经 ≡ 症状组合`（`you_zhengzhuang some 恶寒 ⊓ you_maixiang some 浮脉`），`⊑ 病位⊓病性` | — |
| 八纲来源 | **由判据判定** | 六经的**父类**（`⊑`）→ 六经 ⇒ 八纲 | `determineBiaoLiFromLiujing` / `determineYinYangFromLiujing` → **六经 ⇒ 八纲** |

→ 即 **设计是「八纲 → 六经」，实现是「症状 → 六经 → 八纲」**（方向颠倒）。
→ 要让「八纲 → 六经」成立，须把 六经 的 `≡` 从**症状组合**改为**病位 ⊓ 病性**，
   并把代码的 `determine*FromLiujing` 反转为「由八纲定六经」；**六经提纲证**要迁出到**八纲判据**。

**教训（通用）**：
- **代码的运算顺序 ≠ 逻辑顺序**。代码可能因实现便利而「反着算」（如先诊断六经再读八纲），
  但**逻辑依赖方向**由设计决定。排期、判依赖时，**以设计/医理为准，不以代码为准**（呼应铁律 26）。
- 判「A 改动会不会波及 B」时，要问「**逻辑上 B 是否依赖 A**」，而不是「**代码里 B 是否读了 A**」。

**另两条结构事实（仍然成立）**：
- **六经的 `≡` 用「属性限制」写法**：`Taiyangbing ≡ intersectionOf( unionOf( you_zhengzhuang some Ehan, you_zhengzhuang some Efeng ), you_maixiang some Fumai )`
  —— 患者级 `has-property-some` 限制。**本体没有 A1-A6/B1-B6/C1-C4/D1-D6/E1-E5 这些「组合判据类」**。
- **方证是 ABox 个体**（`tcm-fangji-abox.owl`），不是类。

> ⚠️ **更正（2026-09-18 实测）**：`belongs_to_liujing` **不在任何 .owl 里**（`tcm-fangji-abox.owl` 扫描 0 次），
> 且 `tcm-all.owl` 中 `fangji-abox` / `yaowu-abox` 的 `owl:imports` **已被注释**（注明「已放入 MySQL 数据库」）。
> → **⑦「方证移除经病合取项」/ ⑧「belongsToLiujing 降级」是 MySQL 侧改动，不是 OWL 改动。**

## 铁律 35：**六经提纲证不足以反推病位** —— `六经 ≡ 病位⊓病性` 会推不出少阴/厥阴

**背景**：设计要求 `六经 ≡ 病位 ⊓ 病性`，但逐条拆解六经现有 `≡ 症状组合` 后发现**四个缺口**：

| 六经 | 提纲给的病位证据 | 提纲给的病性证据 | 缺口 |
|---|---|---|---|
| 太阳 | 恶寒/恶风+脉浮 ✅ | ❌ 无 | **阳缺** |
| 阳明 | 大便硬/腹满 ✅ | 口渴/潮热/谵语 ✅ | 无 ✅ |
| 少阳 | 口苦 ✅ | ❌ 无 | **半表半里（胸胁/往来寒热）+ 阳缺** |
| 太阴 | 腹满/下利 ✅ | 脉弱/沉细/沉微/淡白舌 ✅ | 无 ✅ |
| 少阴 | ❌ **无** | 脉微细/但欲寐 ✅ | **表缺** |
| 厥阴 | ❌ **无** | 阴阳俱见 | **半表半里缺** |

**只有阳明、太阴能自足推出「病位⊓病性」**。

**少阴缺口的根因（历史遗留）**：`Shaoyinbing` 的 `rdfs:comment` 第 5 条原文
「剔除『恶寒/身痛』单独路径，**避免与太阳病争分类**」——
在「症状组合 ≡」范式下这是对的（少阴靠脉证自足），
但在「病位⊓病性 ≡」范式下**直接导致少阴推不出来**。

**教训（通用）**：
- 换判定范式（`症状组合 ≡` → `病位⊓病性 ≡`）时，**必须逐条重算「原判据在新范式下是否还够用」**，
  不能假定「原来的判据搬过去就行」。原范式下**刻意剔除**的边（如少阴的恶寒），在新范式下可能是**必需的**。
- 补法要留意**跨属性组合**：`恶寒 ⊓ 不发热 → 表` 是 `you_zhengzhuang` 两条限制的相交，
  而六经模板用的「属性限制」写法（`you_zhengzhuang some X ⊓ you_maixiang some Y`）**表达不了同属性相交**，
  必须改用**具名判据类**（`A7 ≡ you_zhengzhuang some Ehan ⊓ you_zhengzhuang some Bufare`，`A7 ⊑ Biao`）。

## 铁律 36：六经八纲的**医理硬结论**（查过医书，别再凭感觉推）

做「六经 ≡ 病位⊓病性」重构时，逐条查证了医书。以下四条是**有原文铁证的结论**，直接照用：

### ① 少阴的「表」证据 = **无热恶寒**
- 《伤寒论》**7条**：「病有发热恶寒者，发于阳也；**无热恶寒者，发于阴也**。」
- 胡希恕《据证分类法》：「**这里的发热恶寒和无热恶寒为太阳病、少阴病的主要鉴别点**。」
  「由此不难看出**少阴病为表证的阴性病**。」
- 胡希恕九步法：「无热、恶寒、**脉沉微细**者，为**表阴证（少阴病）**。」
- 北中医马家驹：「少阴病为**病位在表**的阴证，即**表阴（虚寒）证**。」
- → 判据：**恶寒 ⊓ 不发热 → 表**。（301条「反发热，脉沉」是变例，本以无热为常。）

### ② 厥阴的「半表半里」证据 = **厥阴提纲证本身**
- 胡希恕解 326条：「厥阴病上虚下寒……**寒在半表半里**，本不下利，
  与寒在里的太阴病自利益甚者不同。」→ **明言「寒在半表半里」**。
- 胡希恕九步法：「**消渴、气上撞心、心中疼热、饥而不欲食、脉微细或沉弦者，为半表半里阴证（厥阴病）**。」
- → 判据：**消渴 ⊔ 气上撞心 ⊔ 心中疼热 ⊔ 饥而不欲食 → 半表半里**。
- **不要**以为「厥阴提纲没有半表半里证据」—— 那是按脏腑经络理解才有的错觉。

### ③ 太阳/少阳的「阳」证据
- 胡希恕九步法：「表证：**发热、恶寒、脉浮紧有力者，为表阳证（太阳病）**。」
- 胡希恕解 263条：「**热郁于半表半里**……上迫头脑，则**口苦、咽干、目眩**。」
- → 太阳靠 `浮紧脉 ⊑ Shi`；少阳靠「口苦+咽干+目眩 → 半表半里 **+ Re**」。
- ⚠️ **`弦脉` 不挂 `Yang`**：265条「脉**弦细**，头痛发热者，属少阳」→ 弦细（虚）也属少阳，弦脉不定阴阳。

### ④ 沉脉**不挂「里」**；沉紧脉**只挂「实」**
- 301条「少阴病，始得之，反发热，**脉沉**者，麻黄附子细辛汤主之」+ 九步法「脉沉微细者，为**表阴证**」
  → **少阴是表证而脉沉**。挂「里」会把少阴误判为里证。**铁证。**
- 135条「结胸**热实**，脉沉而紧」（大陷胸汤，阳）vs《金匮》「**寒疝**绕脐痛……**其脉沉紧者**，大乌头煎主之」（阴）
  → **沉紧脉寒热皆见，病性不定，只挂 `Shi`**。
  （`tcm-core.owl` 太阴分支曾把 `沉紧脉` 当「里寒实」，135条明言「热实」，标注不确。）

### ⑤ 少阳与厥阴**可过渡**，不是非此即彼
- 陈慎吾：「柴胡桂枝干姜汤治疗**少阳病而又兼见阴证机转者**，用之最恰。」
- 胡希恕：「使半表半里的**阳证变为半表半里的阴证**。可知小柴胡汤从阴，是适应治疗半表半里阳证，
  **从阳则适应治疗半表半里阴证**。」
- → **`DisjointClasses(少阳病, 厥阴病)` 与「阴阳俱见 → 厥阴」逻辑上不相容**：
  厥阴患者（半表半里 + 热 + 寒）会**同时**满足 `少阳 ≡ 半表半里⊓Yang` 与 `厥阴 ≡ 半表半里⊓Yin`
  → Openllet 报 inconsistency。**✅ 已裁定删除该互斥**（`tcm-core.owl` 仅此一处互斥），
  由应用层按「阴阳俱见优先判厥阴」消歧（只影响输出，不影响一致性）。
- 用 `¬` 区分（`少阳 ≡ 半表半里⊓Yang⊓¬Yin`）**不行**：265条「脉弦细」属少阳（弦细⊑Xu⊑Yin）会被误杀；
  用 `¬Han` 也不行：「往来寒热」本身有寒。

## 铁律 37：**真正的生产推理路径不是 `SixChannelInferenceEngine`** —— 是 Worker 的「模块抽取」两阶段

**背景**：做「六经 ≡ 病位⊓病性」重构时，文档（`六经重构具体方法.md` §1.5/§6）假定生产路径是
`SixChannelInferenceEngine` + `determine*FromLiujing`。**实测这是 STALE 的**：

| 类/方法 | 实际状态 |
|---|---|
| `SixChannelInferenceEngine` | **死代码**（全工程无引用） |
| `determineBiaoLiFromLiujing` / `determineYinYangFromLiujing` | 只存在于 `src/tmp/TCMOntologyJobWorker.java` —— **不在 Maven 构建里**（`src/main/java` 才是 source root，`src/tmp` 被忽略） |

→ 文档里的「降级 `determine*FromLiujing`」**在活跃代码中天然已满足**，无需改。

**真正的生产路径**（`TCMOntologyJobWorker`）：

```
handleBagangClassification / handleLiujingClassification
  └─ extractBagangModule / extractLiujingModule      ← 构造 TBox 种子（seed）
       └─ OntologyModuleUtils.collectClassClosure    ← 只沿 ≡/⊑ 向上走
            └─ extractTBoxModule                     ← 滤掉 ABox 公理
```

1. **seed 缺「判据」子树**：`extractLiujingModule` 的 seed 只加了 `liujingSubclasses` + `bagangSubclasses`，

   永远传不到患者 → 八纲/六经不可达。

**修法（4 处，均在 `TCMOntologyJobWorker`）**：
- 加字段 `bagangPanjuSubclasses`；`init()` 里 `getAllNamedSubclasses(BASE_NS + "BagangPanju")`；

- `buildPatientAxioms` 里对症状/脉象/舌象/复正逐个 `assertFindingTypes(...)`（把发现类**直接断言到患者**）；
- 新增 helper `assertFindingTypes(df, axioms, patient, iris)`：`df.getOWLClassAssertionAxiom(getOWLClass(BASE_NS+f), patient)`。

**验证手法（生产链复刻 harness）**：写 `_ProdChainVerify`，**照抄** `extractLiujingModule` 的 seed 构造 +
`buildPatientAxioms` + `collectClassClosure` + `extractTBoxModule`，跑 **Mode A（修复前：seed 无判据、患者无类型）
vs Mode B（修复后）** 两组对照。实测 Mode A = 9/9 场景全空（六经=[] 八纲=[]），Mode B = PASS=9。
**这种「修复前后同 harness 双模对照」比单跑一次更有说服力**——它直接证明「缺口就是这两处」。

**教训（通用）**：
- **文档里的代码假设会过时**。动手前先 `grep` 确认「文档点名的类/方法是否真在 `src/main/java` 且被引用」，
  别照着 stale 文档改死代码。
- **改「模块抽取」类逻辑时，务必同时检查 seed 是否覆盖所有上游层**（本例漏了判据层），

## 铁律 41：**合病方证的六经只能写注解，不能写等价类** —— 病位/病性不互斥会「交叉推出 4 个六经」（2026-09-19）

**背景**：`六经 ≡ 病位 ⊓ 病性`（太阳=表阳、阳明=里阳、少阳=半表半里阳、太阴=里阴、**少阴=表阴**、厥阴=半表半里阴）。
给方证「指派六经」的既有做法是把六经类注入 `equivalentClass` 的 `intersectionOf` 首位。
**但这对跨病性的合病方证会出错。**

**实测**：`Wendantangzheng ≡ 少阳 ⊓ 太阴 ⊓ 症状`
```
少阳 = 半表半里 ⊓ 阳 ;  太阴 = 里 ⊓ 阴
⇒ ⊑ 里 ⊓ 阴 ⊓ 半表半里 ⊓ 阳
⇒ 推理机推出 太阴 + 少阳 + 阳明(里阳) + 厥阴(半表半里阴)   ← 4 个！
```
（`_InjectVerify` 实测 `推理六经=[Jueyinbing, Shaoyangbing, Taiyinbing, Yangmingbing]`）

**根因**：病位（表/里/半表半里）与病性（阴/阳）**都没有声明互斥**（全本体唯一 `DisjointClasses` 已删；
现存 `disjointWith` 只在方证之间做鉴别）。所以 `A⊓B` 会推出 病位×病性 的**全部交叉组合**。

**为何现有 4 个合病类没暴露**：`TaiyangShaoyangHebing` / `ShaoyangYangmingHebing` /
`TaiyangYangmingHebing` / `TaiyinShaoyinHebing` 配对的六经**病性相同**，交叉后不产生新组合。
**少阳太阴合病是第一个跨病性合病。**

**正解（已采用）**：合病方证的六经**只写 `belongsToLiujing` 注解（可多条），不写等价类**。
依据：
- 生产 `filterFangzheng` 走 `fangzhengLiujingMap`，该 map 由 `OntologyModuleUtils.findRelatedClasses`
  从**注解**（∪ 父类 ∪ 等价类命名类）构建 → 注解足够；
- 六经阶段 minibox **不含方证类**（`extractLiujingModule` seed 无 `fangzhengSubclasses`），
  推理机**从不对方证做六经分类** → 等价类注入无用且有害。

**反例（单经安全）**：只注入**一个**六经（如 `Gualouqumaiwanzheng ≡ 太阴 ⊓ 症状`）→ 只推出该六经，无交叉。
故**单经方证照旧写等价类，合病方证只写注解**。

**验收口径（`_LiujingAssignVerify`）**：必须查**两个口径**——
- **注解口径**（= 生产 `fangzhengLiujingMap` 的来源）：`注解 ∪ 父类 ∪ 等价类命名类 ∩ 六经` **必须等于期望**；
- **推理口径**（`reasoner.getSuperClasses`）：**不得越界**（合病方证可为空，但不能推出期望之外的六经）。
> 只看「等价类里有没有六经」的审计（`_FangzhengLiujingAudit`）会把合病方证误报为「推理机不认」——
> 合病方证**按设计**只写注解，该状态是正常的。

**教训（通用）**：给本体加「多值逻辑归属」前，先问「这两个值合取会不会推出第三个」。
**非互斥的维度做合取 = 交叉积**。要么保证合取项同维同值，要么改用注解/应用层。

### 41.1 交叉积**不只影响方证，也影响患者**（2026-09-19 探针实测）

`_harness/_HebingProbe.java` 直接问推理机「某八纲组合推出哪些六经」：

| 八纲组合 | 推出六经 | 评价 |
|---|---|---|
| 半表半里 + 里 + 阳 + 阴 | **少阳, 太阴, 阳明, 厥阴**（4 个） | ❌ 交叉积 |
| 表 + 里 + 阳 | 太阳, 阳明（2 个） | ✅ |
| 表 + 里 + 阴 | 太阴, 少阴（2 个） | ✅ |

**规律：合病两经病性相同 → 正确；病性不同 → 交叉积**
（多出 `里⊓阳`=阳明、`半表半里⊓阴`=厥阴）。

**生产影响**：少阳太阴合病的患者，推理机给 4 个六经 →
`resolveLiujingMutex`（`LIUJING_MUTEX_PAIRS = {Shaoyangbing→Jueyinbing}`，
「半表半里阴覆盖阳」）**移除少阳、保留厥阴** → 最终 `{太阴, 阳明, 厥阴}`，
**既不是少阳太阴合病，也不是任何真实证型**。
→ **该 mutex 是掩盖交叉积的创可贴，且掩盖后结果仍是错的。**

### 41.2 根因：扁平八纲丢失「病位-病性配对」

合病 = **多个独立的（病位, 病性）对**。扁平 ABox（患者直挂 `Li`/`Banbiaobanli`/`Yang`/`Yin`）
无法区分「里来自 A 方面、阳来自 B 方面」与「里阳同出一源」→ 产生 `里⊓阳`。

**要真正「按推理机推合病」→ 八纲判定个体化（reify）**：
```owl
Judgment ⊑ Thing ;  hasBingwei/hasBingxing : Judgment → Bagang
Patient ⊑ ∃hasJudgment.Judgment
Taiyinbing   ≡ ∃hasJudgment.(∃hasBingwei.Li ⊓ ∃hasBingxing.Yin)
Shaoyangbing ≡ ∃hasJudgment.(∃hasBingwei.Banbiaobanli ⊓ ∃hasBingxing.Yang)
```
患者挂两个判定个体 → 推出**恰好 太阴+少阳**，无交叉积。
代价：八纲阶段断言方式要改（判据 → 判定个体 → 病位/病性），中等重构。

> **决策点**：先定「病位/病性是否互斥」——**不互斥是交叉积的根源**。
> 但若声明互斥，则「半表半里 ⊓ 里」= ⊥，合病在 ABox 层直接不可表达。
> 故互斥与合病**不可兼得**，除非走 reify 路线。

## 铁律 49：**本体正确性 > 测试通过率**；脉象/舌象→病性公理须逐条对权威医书（2026-09-19，用户铁律）

1. 模拟器/测试通过数**只是校验手段**，**绝不能**作为「保留或删除某条公理」的取舍依据。

3. 判定「保留」还是「改」时，**先查医书原文**，不要凭印象。

| 公理 | 医书原文 | 裁定 | 处置 |
|---|---|---|---|
| `沉弦脉 ⊑ 虚` | 濒湖「**沉弦悬饮内痛**」(实)；胡希恕「**沉弦，为里**…主水饮」「弦…**是实脉，主邪实**」 | **错** | 撤 ⊑虚 |

- **`结脉` vs `结代脉` 易混**：`结代脉 ⊑ 虚`（代脉主「脏气衰」）是对的，

## 铁律 58：**名义量（`owl:hasValue`）不得进入 TBox** —— 方证→方剂 用注解表达（2026-09-20，已实测）

**根因实测**（`_harness/AblationProbe.java`，tcm-all.owl 7426 公理 / 262 个体 / 1164 类）：

| mode | 改动 | CLASS_HIERARCHY |
|---|---|---|
| full | 不改 | 384738 / 451589 / 55230 ms（方差极大，见铁律 54） |
| noeq | 删 366 条 `owl:equivalentClass` | **1641 ms** |
| noind | 删 1783 条触及个体的公理 | 47168 ms |
| **nohasvalue** | **删 270 条 `you_chufang` 名义量** | **15509 ms** |
| norange | 删 42 条 range/domain | 290616 ms |
| noabox | 删 787 条断言 | 161086 ms |

**结论：慢 = 366 条等价定义 × 262 个方剂名义量个体的「相互作用」。**
只删 ≡（1.6 s）或只删名义量（15.5 s）都快；两者都在就 385 s。单看任一方都不慢。

**医理依据（铁律 53）**：
1. 方证的定义应由「六经病位 + 特征症状群」给出（方证相应：证由症候界定）。
   把处方写进 `≡` 定义 = 用治疗反定义证候，逻辑循环；
   **且使该方证永不可被推出**——患者就诊时并无处方断言（duli 有 5 例如此）。
2. 「有是证用是方」是治疗对应关系，属元数据，不是定义性公理。

**落地做法**（`_harness/_nominal_audit.py` 审计 + `_harness/_nominal_to_anno.py` 改写）：
- 审计：265 个方证类含名义量，共 270 条（260 条仅 `⊑`，5 条 duli 混在 `≡` 里），262 个方剂个体。
- 改写：删 `⊑` 名义量公理 + 删 `≡` 内名义量操作数；在方证类上写 `<chufang rdf:resource="#方剂"/>`。
- `tcm-core.owl` 新增注解属性 `#chufang`（label 主治方剂）。
- `TCMOntologyJobWorker.extractFormula` 优先读注解，保留旧名义量分支兼容。
- 校验：XML 良构；`you_chufang` 仅剩属性声明；
  `collectRestrictionFillers` 只用 you_zhengzhuang/you_maixiang/you_shexiang/you_fuzheng，不受影响。

**推论**：任何「类 → 个体」的映射（方剂、药材、条文…）都不要用名义量写进 TBox，
一律用注解属性；否则 SROIQ 分类会因名义量与等价定义叠加而爆炸。
