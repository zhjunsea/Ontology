## 1. 目标与范围

### 1.1 目标

把现有「本体 + 规则引擎 + BPMN 流程」封装成一个**可交互的诊断应用**：

1. 用户用**自然语言**描述症状（如「发烧怕冷，两边肋骨下面胀痛，还老想吐」）。
2. 由**大模型 + 确定性检索**共同把自然语言映射到本体中的**症状实例个体**（`*_instance`）。
3. 用映射结果调用 `Jingfang_Diagnosis.bpmn` 完成八纲 → 六经 → 方证 → 兼夹证 → 方剂 → **加减药** → 解释的完整推理。
4. 输出结构化诊断结果（六经、方证、推荐方剂、药物组成、加减依据、配伍禁忌警告、解释文本）。

> **关键交互约束（v1.3 起）**：网页只承担两件事——**输入症状**、**展示诊断结果与依据**。
> 中间过程**不得有任何人工介入**：流程由 JobWorker 一路跑到结束事件，网页只从 Camunda
> 取回结果与解释。因此低置信度映射不再弹确认框，而是按当前最优结果继续推理，
> 并把「低置信度 / 未匹配」作为**依据提示**展示在结果里。
>
> **结果形态约束（v1.4 起）**：只有当方证被**完全 realize**（Openllet 推理把患者个体归入该
> 方证类）时，才给出**确定性诊断结果**；否则退化为**候选方证 Top10**，并逐条列出该候选
> **命中的症状**；若连候选都没有，则给出「无法给出诊断」。三种形态分别对应三个结束事件
> `EndEvent_Success` / `EndEvent_Candidates` / `EndEvent_NoResult`。

### 1.2 范围

| 包含 | 不包含 |
| --- | --- |
| 症状实例个体映射（三层策略） | 患者档案管理、历史病历持久化 |
| BPMN 全自动改造（+2 服务任务、+2 终止事件（无结果 / 候选），**0 人工任务**） | 用户权限体系 |
| REST API + 单页 Web UI | 移动端适配 |
| 加减药（方后注）显式步骤化 | 中药剂量换算与煎服法生成 |
| 单元测试 + 流程集成测试 | 生产级 LLM 网关/限流 |

### 1.3 关键设计约束

- **本体是唯一事实来源**：症状、脉象、舌象、方剂、药物、加减规则全部来自 OWL，代码不硬编码医学知识（仅保留口语同义词表）。
- **LLM 可降级**：LLM 不可用时，应用必须仍能用确定性策略工作（只是召回率下降），不得因 LLM 故障而整体不可用。
- **流程必须自终止**：任何输入都必须在有限时间内收敛到某个结束事件，不得停在人工任务上等待（否则网页会永久转圈）。
- **向后兼容**：既有 `prescription-recommendation` 的输出契约保持不变，避免破坏既有集成测试。

## 3. 症状实例个体映射（核心）

### 3.1 数据基础

`SymptomCatalog` 从 ABox 文件加载**实例个体**（不是类）：

| 文件 | 类别 | 实例数 | 命名规则 |
| --- | --- | --- | --- |
| `tcm-zhengzhuang-abox.owl` | 症状 | 576 | `#<类名>_instance`，`rdfs:label` 为中文 |
| `tcm-maixiang-abox.owl` | 脉象 | 68 | 同上 |
| `tcm-shexiang-abox.owl` | 舌象 | 72 | 同上 |
| （无 ABox） | 腹证 | 0 | 当前本体未生成腹证实例，保留空类别 |

每条目录项：`{fragment, iri, label, category, aliases}`。

> **为什么直接解析 ABox 文件而不用推理机？**
> 目录是**静态枚举**，不需要推理；直接解析文件可让 `SymptomCatalog` 独立于 `BackendService`（后者初始化需 OBDA/MySQL），从而可被单元测试直接构造。

### 3.2 三层映射策略

输入：用户自然语言片段（先按标点/换行切分为若干「表述单元」）。
输出：每个表述单元 → 匹配结果。

#### L1 确定性检索（永远执行，不依赖网络）

对每个表述单元 `t`，对目录中每条 `e` 计算分数：

| 规则 | 分数 | 说明 |
| --- | --- | --- |
| 完全相等（`t == e.label`） | 1.00 | 最强 |
| 同义词命中（`aliasOf(t) == e.label`） | 0.95 | 口语 → 规范名 |
| `t` 包含 `e.label` | 0.80 + 0.2·len(e.label)/len(t) | 「两边肋骨胀痛」→「胁痛」 |
| `e.label` 包含 `t` | 0.70 | 「咳」→「咳嗽」 |
| 字符 Dice 系数 ≥ 0.5 | 0.6·dice | 兜底模糊 |

取 top-k（k=3）作为候选，最高分记为 `s1`。

#### L2 LLM 语义映射（可选，可降级）

触发条件：L1 未能给出「可直接采纳」结果的表述单元（即进入 `pending` 的表述）。

调用方式：**递进式召回（两轮）**。

**第一轮 —— 窄候选集（精度优先）**

候选清单 = 各待处理项的 L1 top-k 并集；若不足 20 条，再按「待映射文本字符 ∩ 目录 label 字符」召回补足，上限 `llm-candidate-limit`（默认 60）。

要求 LLM **只能从候选清单中选择**，输出严格 JSON：

```json
{
  "matches": [
    {"text": "两边肋骨下面胀痛", "fragments": ["Xiongxiekuman_instance"], "confidence": 0.9, "reason": "对应胸胁苦满"}
  ],
  "unmatched": ["某个无法映射的表述"]
}
```

**第二轮 —— 全目录候选（召回优先，仅对第一轮未解析项）**

窄候选集靠**字面**召回构造，无法覆盖**语义远距**表述。典型例子：

> 「两边肋骨下面胀痛」→ `Xiongxiekuman_instance`（胸胁苦满）

二者**无任何共享字符**，任何字面召回（子串 / 超串 / Dice / 字符交集）都召不回该实例，于是 LLM 即便正确选出它，也会被防幻觉校验丢弃。

因此对第一轮仍未解析的表述，再调一次 LLM，候选清单 = **整个症状目录**（上限 `llm-full-catalog-limit`，默认 800，覆盖当前 716 个实例）。若目录本身不比窄候选集大，则跳过升级。

> **防幻觉判据（两轮一致）**：LLM 返回的 fragment 必须存在于**本次候选清单**中，而候选清单始终是症状目录的子集 —— 因此「发明目录外症状」在任何一轮都会被丢弃。白名单只是**召回引导**，目录才是**合法性判据**。

LLM 不可用（未配置 / 超时 / 解析失败）→ 记 `llmAvailable=false`，直接使用 L1 结果。

#### L3 置信度标注（v1.3：不再门控流程）

对每个表述单元，最终置信度 `c`：

| 情况 | c | 处理 |
| --- | --- | --- |
| L2 命中且 `confidence ≥ 0.75` | L2 置信度 | 直接采纳 |
| L1 完全相等 / 同义词 | ≥ 0.95 | 直接采纳 |
| L1 包含类且 `s1 ≥ 0.85` | s1 | 直接采纳 |
| `0.5 ≤ s1 < 0.85` | s1 | **采纳并标记低置信度** |
| `s1 < 0.5` 且无 L2 结果 | < 0.5 | **不采纳**，进入 `unmatched` |

标注（仅用于展示，**不阻断流程**）：

```
needsConfirmation = (存在 c < 0.85 的已采纳项) || (unmatched 非空)
```

- `needsConfirmation = true` **不再**触发人工确认任务；流程照常继续，
  该标记透出到前端，作为「依据」区的一条提示（低置信度映射 / 未匹配表述）。
- 未匹配的表述单元被如实记录在 `unmatchedTexts`，供用户判断是否需要补充描述。

#### 原子症状组合

本体中部分症状是**复合类**（如「心下痞硬」由原子症状合成）。映射层只负责给出**实例个体**；组合语义由既有 `OntologyModuleUtils.addSynthesizedComposites` 在 `sizhen-input` 阶段自动合成，映射层不重复实现。

### 3.3 幂等与重跑

`symptom-mapping` 仍是可重入的（便于将来扩展「补充症状后重跑」），但 v1.3 的流程中
**不再有回环**，每个实例只执行一次：

```
输入变量：
  userInput        : String   原始自然语言
  confirmed        : List<String>  预置采纳的 fragment（可选，当前仅测试框架使用）
  rejected         : List<String>  预置拒绝的 fragment（可选）
  extra            : List<String>  预置补充的 fragment（可选）
  mappingRound     : int      轮次（当前恒为 0 → 输出 1）

输出变量：
  symptomIris / pulseIris / tongueIris / fuzhengIris : List<String>（**完整 IRI**，见下）
  needsConfirmation : boolean  （低置信度标注，不再门控流程）
  ambiguousSymptoms : List<{text, candidates:[{fragment,label,score}]}>
  unmatchedTexts    : List<String>
  mappingDetail     : List<{text, fragment, iri, label, category, confidence, source}>
  mappingSummary    : String   人类可读摘要
  mappingRound      : int
```

> **IRI 契约（重要）**：`symptomIris` / `pulseIris` / `tongueIris` / `fuzhengIris` 输出的是
> **完整 IRI**（`BASE_NS + fragment`，如 `http://www.tcm-classics.org/jingfang#Fare_instance`），
> 因为下游 `sizhen-input` 及其后的八纲/六经/方证推理都按 **IRI** 查找个体。
> `mappingDetail[*].fragment` 仍是裸 fragment（供前端展示），
> `mappingDetail[*].iri` 是完整 IRI。两者不可混用。

## 4. BPMN 流程改造（v1.3：全自动）

### 4.1 改造前后对比

**改造前**（13 个节点，含 2 个人工任务）：

```
开始 → 症状映射 → [是否需要确认?]
                    ├─是→ 确认症状映射(人工) → 症状映射（回环重跑）
                    └─否→ 录入四诊 → 一致性检查 → [是否一致?]
                                                  ├─是→ 八纲 → 六经 → 方证 → 兼夹证 → 母方推荐
                                                  │                                    ↓
                                                  │                              加减药(方后注)
                                                  │                                    ↓
                                                  │                            生成诊断解释 → [是否有推荐?]
                                                  │                                            ├─有→ 诊断完成
                                                  └─否→ 修改四诊信息(人工) ←───────────────────┘─无┘
```

**改造后**（15 个节点，**0 个人工任务**）：

```
开始 → 症状映射 → 录入四诊 → 一致性检查 → [是否一致?]
                                            ├─是→ 八纲 → 六经 → 方证 → 兼夹证 → 母方推荐
                                            │                                    ↓
                                            │                              加减药(方后注)
                                            │                                    ↓
                                            │                            生成诊断解释 → [结果形态?]
                                            │                                            ├─完全realize→ 诊断完成
                                            │                                            ├─有候选→ 给出候选方证(Top10+命中症状)
                                            └─否→ 无法给出诊断 ←──────────────────────────┘─无候选┘
```

> `Gateway_HasRecommendation`（名「结果形态？」）由 v1.3 的两分支扩为 **三分支**，
> 判定依据是流程变量 `fangzhengRealized` 与 `fangzhengCandidates`。

**摘除的节点**（全自动约束：BPMN 中不得出现 `userTask`）：

| 节点 | 类型 | 摘除原因 |
| --- | --- | --- |
| `Gateway_NeedConfirm` | exclusiveGateway | 确认门控已无意义 |
| `Task_ConfirmSymptoms` | userTask | 人工确认会永久阻塞网页 |
| `Task_ReviseSizhen` | userTask | 人工修改四诊会永久阻塞网页 |

**新增的节点**：

| 节点 | 类型 | 作用 |
| --- | --- | --- |
| `EndEvent_NoResult` | endEvent | 一致性不通过 / 无候选方证时的终止态，名「无法给出诊断」 |
| `EndEvent_Candidates` | endEvent | 方证未完全 realize 但存在候选时的终止态，名「给出候选方证」（v1.4 新增） |

**新增的连线**：

| 连线 | 走向 |
| --- | --- |
| `Flow_Mapping_To_Input` | `Task_SymptomMapping` → `Task_InputSizhen` |
| `Flow_Consistent_No`（改向） | `Gateway_Consistent` → `EndEvent_NoResult` |
| `Flow_HasRecommendation_Yes`（改条件） | `Gateway_HasRecommendation` → `EndEvent_Success`，条件 `=fangzhengRealized = true` |
| `Flow_HasRecommendation_Candidates`（v1.4 新增） | `Gateway_HasRecommendation` → `EndEvent_Candidates`，条件 `=fangzhengRealized = false and fangzhengCandidates != null and fangzhengCandidates != []` |
| `Flow_HasRecommendation_No`（改条件） | `Gateway_HasRecommendation` → `EndEvent_NoResult`，条件 `=fangzhengRealized = false and (fangzhengCandidates = null or fangzhengCandidates = [])` |

**方证分类 worker 的两个关键流程变量**（`fangzheng-classification` 输出）：

| 变量 | 类型 | 含义 |
| --- | --- | --- |
| `fangzhengRealized` | boolean | 是否有方证被**完全 realize**（`realizedMatches` 非空） |
| `fangzhengCandidates` | list | 未 realize 时的 Top10 候选方证 fragment 列表（已按得分排序） |
| `fangzhengCandidatesCn` | list | 同上，中文名列表 |
| `fangzhengCandidateDetails` | list | 每个候选的明细：`fragment` / `label` / `hits` / `required` / `jaccard` / `hitSymptoms`（该候选**命中的症状**列表，元素为 `{fragment, label}`） |

| `Task_JianJiaZheng` | `jianjiazheng-classification` | 兼夹证分类 |
| `Task_Prescription` | `prescription-recommendation` | 母方推荐 |
| `Task_HerbModification` | `herb-modification` | 加减药（方后注派生） |
| `Task_Explanation` | `diagnosis-explanation` | 生成诊断解释 |

### 4.3 为什么要单独一个「加减药」步骤

方后注加减（`rules.owl` v2.7，46 个方证 / 84 条规则）在语义上**独立于方剂推荐**：

- **方剂推荐**回答「这是哪个方证、母方是什么」——由方证分类结果直接决定，是**确定性**的；
- **加减药**回答「该患者的症状超出母方标准证候时，如何依《伤寒论》方后注加减」——依赖**患者症状集合**与规则条件匹配，是**条件性**的。

两者拆开后：

1. 流程图上直接可见「加减药」环节，符合临床「方随证转、随证加减」的思维；
2. 便于审计：`appliedRules` / `ruleSources` 可独立展示与追溯。

### 4.4 兼容性处理（重要）

既有集成测试（`ShaoyangYangmingFangzhengTest`、`JueyinFangzhengTest` 等）断言 `prescription-recommendation` 输出 `finalFormula` / `herbs` / `derived`。

**改造策略**：把加减药派生逻辑抽成私有方法 `applyHerbModification(...)`，被两个 Worker 共用：

- `handlePrescriptionRecommendation`：**保持原有完整输出**（含派生结果）→ 既有测试零影响；
- `handleHerbModification`：作为**显式步骤**调用同一方法，输出权威的最终方剂组成，并额外输出 `herbModificationApplied` 等审计字段。

两个 Worker 结果**逐字段一致**，不存在语义分叉。

### 4.5 既有集成测试的契约适配（重要）

改造后 `Task_SymptomMapping` 成为开始事件后的**首个节点**，其输入契约是
`userInput` + `confirmed` / `rejected` / `extra`（fragment），输出契约是
`symptomIris` / `pulseIris` / `tongueIris` / `fuzhengIris`（**完整 IRI**）。

既有 8 个方证集成测试（经 `JingfangTestSupport.assertFangzheng`）沿用**改造前**的契约：
直接把四诊 IRI 预置为流程变量。两者冲突的后果是——映射节点读到空 `userInput` / 空 `extra`，
映射出空结果并**覆盖**测试预置的 IRI，下游 `sizhen-input` 拿到空四诊，
八纲/六经/方证全部塌陷（表现为 `fangzheng` 断言得到 `null`）。

**适配方式（只改测试框架，不改算法）**：`JingfangTestSupport.startProcessAndGetResult`
在提交流程变量前调用 `toProcessVariables(...)`，把预置的四诊 IRI 拆成 fragment 写入 `extra`：

- `extra` 是本文档定义的「预置补充的 fragment」通道，`SymptomMappingService.map`
  对该通道的处理是「查目录 → 命中则以置信度 1.0 采纳（`USER_EXTRA`）」，
  因此**不经过 L1/L2 猜测**，测试对下游推理的精确控制（含六经锚点注入）完整保留；
- 若用例已按新契约传 `userInput`，则原样透传、不做任何改写；
- `assertFangzheng` 新增 `assertSizhenMapped(...)` 契约守护：断言预置四诊 IRI
  全部出现在映射节点的输出通道中，失败时直接指出「契约破坏」，而不是让下游断言先报错。

**前提**：`extra` 里的 fragment 必须存在于 `SymptomCatalog` 加载的四个 ABox 文件
（`tcm-zhengzhuang-abox.owl` / `tcm-maixiang-abox.owl` / `tcm-shexiang-abox.owl` /
`tcm-fuzheng-abox.owl`）内，否则会被映射服务**静默丢弃**。
已核对 7 个测试类共 628 个 fragment 与 14 个六经锚点全部命中目录。

> 注意 `tcm-fuzheng-abox.owl` 当前**不存在**，故 `fuzhengIris` 通道目录为空——
> 腹证类 fragment 会被静默丢弃。测试中 `fuzhengIris` 目前均为空，暂未受影响。

## 6. Web UI

单页应用（`src/main/resources/static/index.html`，零构建依赖，纯原生 JS + CSS）。
**只做两件事：输入症状、展示结果与依据。**

1. **输入区**：多行文本框 + 「开始诊断」按钮 + 示例症状快捷填充。
2. **进度区**（`status = RUNNING` 时出现）：转圈 + 已用时秒数 + 流程阶段标签。
3. **结果区**（`status = COMPLETED` 时出现）：
   - `outcome = DIAGNOSED`（方证完全 realize）：
     - **诊断结果**：六经 / 方证 / 推荐方剂 / 母方 四张主卡片；兼夹证标签
     - **药物组成**：母方药物 + 新增药物高亮 + 删除药物删除线
     - **加减药依据**：命中规则**原文**、**出处**、剂量调整
     - 配伍禁忌警告（红色）
     - **诊断解释**全文
   - `outcome = CANDIDATES`（方证未完全 realize）：
     - 顶部**信息提示条**：说明当前方证未完全 realize，下方给出候选
     - **候选方证（TopN）· 命中的症状**：每个候选一行，显示 `#排名`、方证名、
       `命中 x/y · 相似度`，以及该候选命中的**症状徽章**（`hitSymptoms`）
   - `outcome = NO_RESULT`：提示「无法给出诊断」及原因
   - **诊断依据**（各形态通用）：
     - 症状映射明细表（原表述 → 本体实例 → 类别 → 置信度 → 来源）
     - 八纲与候选方证
     - 提示条：未匹配表述 / 低置信度映射 / 大模型不可用降级

前端轮询 `GET /api/diagnosis/{key}`（1 秒间隔，上限约 5 分钟），
`status != RUNNING` 时停止轮询并渲染结果。

| 回归 | `mvn -o -pl OntologyFramework -am test` | 全量回归 | 同上 |

集成测试用 `zeebe-process-test-extension` 8.9.6 提供的内存引擎，**不依赖**外部 Camunda 与 MySQL，可在 CI 中运行。

> **构建注意**：`OntologyFramework` / `OntopOBDAHandler` / `OpenlletResolver` 三个模块的编译输出目录都叫 `target/classes`。
> surefire 默认生成 manifest-only jar 时会把多个同名 `target/classes` 压缩成同一个相对名 `classes`，
> 导致运行期只有第一个模块的类可解析，其余模块抛 `ClassNotFoundException`。
> 因此 `OntologyFramework/pom.xml` 的 surefire 配置中必须设置 `<useManifestOnlyJar>false</useManifestOnlyJar>`。
>
> 另外 `OntopOBDAHandler` 的 `OntopObdaHandlerApplicationTests` 依赖真实 MySQL/OBDA 环境，
> 离线回归时需排除：`-Dtest='!OntopObdaHandlerApplicationTests'`。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| LLM 幻觉出不存在的症状实例 | 输出后校验：fragment 必须存在于**本次候选清单**（始终是症状目录子集），目录外片段一律丢弃 |
| 语义远距表述（字面召回召不回） | 递进式召回：第一轮窄候选集未解析 → 第二轮升级为全目录候选 |
| 全目录候选导致提示词膨胀 | `llm-full-catalog-limit` 上限（默认 800，覆盖当前 716 个实例）；超限截断并告警 |
| LLM 不可用 | 自动降级 L1；`llmAvailable` 字段透出 |
| **流程停在人工任务上导致网页永久等待** | **全自动约束**：BPMN 中禁止 `userTask`，由 `JingfangBpmnStructureTest#noUserTasksInFullyAutomaticFlow` 守护 |
| **无方证推荐时流程无法收敛** | 三条分支分别汇入 `EndEvent_Success` / `EndEvent_Candidates` / `EndEvent_NoResult`，`outcome` 对应 `DIAGNOSED` / `CANDIDATES` / `NO_RESULT` |
| **候选方证被误当作确定性诊断** | 只有 `fangzhengRealized = true`（Openllet 推理归入该方证类）才走 `EndEvent_Success`；仅 Jaccard 打分的候选一律走 `EndEvent_Candidates`，前端以「候选」措辞展示，不冒充结论 |
| 低置信度映射被静默采纳 | 不阻断流程，但 `needsConfirmation` 透出到前端「依据」区，明确提示用户 |
| 症状目录与本体不同步 | 目录在启动时从 ABox 文件加载；提供 `/catalog` 接口核对数量 |
| 破坏既有集成测试 | 加减药逻辑抽为共享方法，`prescription-recommendation` 输出契约不变 |
| 腹证无 ABox 实例 | 保留空类别，映射层不产出腹证；流程变量置空列表 |
