## 1. 概述与范围

本模块含**两条独立可执行流程**，均部署到 Camunda 8 / Zeebe，由引擎按 BPMN 拓扑驱动，`serviceTask` 派发作业给 `PizzaOntologyJobWorker`：

| 流程 | process id | 名称 | 定位 | 角色任务 |
|---|---|---|---|---|
| 烘焙流程 | `PizzaMakingStandardProcess` | 通用披萨标准制作工艺流程 | **全自动**：给定披萨类型，按本体取组件、按 `matchedWord` 分支走完制作链 | 无 userTask（全 serviceTask） |
| 设计流程 | `PizzaOntologyDesignProcess` | 披萨本体驱动定制流程 | **人机协同**：本体推理出约束/可选项 → 用户逐组件选择 → 汇总并写库 | 4 个 userTask + 1 个启动表单 |

两者共用同一套 JobWorker 能力，但**只用到 9 个 jobType 中的 4 个**（见 §5）。

> 说明：本文只描述流程**拓扑与绑定契约**；本体约束语义见《披萨本体设计》，Worker 算法与整体架构见《披萨应用-顶层设计》。

## 2. 流程总览

```
【烘焙流程 PizzaMakingStandardProcess】
Start → （揉制→醒发→成型 三段查询本体时长）
      → 获取酱汁 → 酱汁网关 ─┬─ 白酱 ─┐
                             ├─ 番茄红酱 ─┤→ 汇合 → 获取奶酪 → 奶酪网关 ─┬─ 奶酪 → 基础奶酪铺设 ─┐
                             └─ 无酱料 ──┘                                  └─ 无奶酪 ─────────────┴→ 获取配料
      → 配料网关 ─┬─ 配料 → 顶层配料铺设 ─┐
                   └─ 无配料 ─────────────┴→ 获取封层 → 封层网关 ─┬─ 封层 → 补铺封层 ─┐
                                                                   └─ 没封层 ───────────┴→ 汇合
      → 烘烤 → 装饰 → 切检 → End

【设计流程 PizzaOntologyDesignProcess】
Start(表单:披萨类型) → 本体约束推理
      → 饼底网关 ─┬─ 是 → 选择饼底 ─┐
                   └─ 否 ──────────┴→ 奶酪网关 ─┬─ 是 → 选择奶酪 ─┐
                                                 └─ 否 ────────────┴→ 酱汁网关 ─┬─ 是 → 选择酱汁 ─┐
                                                                                 └─ 否 ────────────┴→ 配料网关 ─┬─ 是 → 选择配料 ─┐
                                                                                                                 └─ 否 ────────────┴→ 生成总结与校验 → End
```

### 3.3 网关与分支条件

所有排他网关的分支条件均读取流程变量 **`matchedWord`**（由上游 `get-component` 写入），采用 Zeebe FEEL 表达式。

| 网关 id | 名称 | 出边 id | 边名 | 条件表达式 | 目标节点 |
|---|---|---|---|---|---|
| `Gateway_SauceChoice` | 酱汁类型 | `Flow_Sauce_White` | 白酱 | `= matchedWord = "白酱"` | `Task_WhiteSauce` |
| | | `Flow_Sauce_Tomato` | 番茄红酱 | `= matchedWord = "番茄红酱"` | `Task_TomatoSauce` |
| | | `Flow_0sefal0` | 否 | `= matchedWord = "无酱料"` | `Gateway_SauceMerge` |
| `Gateway_CheeseChoice` | 是否添加奶酪？ | `Flow_Cheese_Yes` | 是 | `= matchedWord = "奶酪"` | `Task_BaseCheese` |
| | | `Flow_Cheese_No_To_GetTopping` | 否 | `= matchedWord = "无奶酪"` | `Task_GetTopping` |
| `Gateway_0xkqhps` | 是否有顶层配料 | `Flow_1s2ck8n` | 是 | `= matchedWord = "配料"` | `Task_ToppingSpread` |
| | | `Flow_1m3vm03` | 否 | `= matchedWord = "无配料"` | `Task_GetTopCheese` |
| `Gateway_TopCheeseChoice` | 是否需要封层？ | `Flow_TopCheese_Yes` | 有封层 | `= matchedWord = "封层"` | `Task_TopCheese` |
| | | `Flow_TopCheese_No` | （否） | `= matchedWord = "没封层"` | `Gateway_TopCheeseMerge` |

> **`matchedWord` 语义**：由 `get-component` 经 `Utilities.resolveMatchedWord(...)` 在 TBox `rdfs:label` 中按候选标签匹配得到；`candidateLabels` 约定**首元素为「无该组件」、末元素为「缺省组件」**。同一流程内多个 `get-component` 依次复用同名变量 `matchedWord`，**每次写入覆盖上一次**，故每个网关只依赖最近一次取组件的结果。

### 4.3 网关与分支条件

设计流程按 `pizza-limitation` 输出的 **`needXxx`（布尔）** 决定 userTask 是否出现；每个 userTask 完成后**无条件汇入下一个网关**（即 4 组「网关 + 可选 userTask」串成一条链）。

| 网关 id | 名称 | 出边 | 边名 | 条件表达式 | 目标节点 |
|---|---|---|---|---|---|
| `GW_Crust` | 需要饼底? | `Flow_Crust_Yes` | 是 | `= needCrust = true` | `UT_Crust` |
| | | `Flow_Crust_No` | 否 | `= needCrust = false` | `GW_Cheese` |
| `GW_Cheese` | 需要奶酪? | `Flow_Cheese_Yes` | 是 | `= needCheese = true` | `UT_Cheese` |
| | | `Flow_Cheese_No` | 否 | `= needCheese = false` | `GW_Sauce` |
| `GW_Sauce` | 需要酱汁? | `Flow_Sauce_Yes` | 是 | `= needSauce = true` | `UT_Sauce` |
| | | `Flow_Sauce_No` | 否 | `= needSauce = false` | `GW_Topping` |
| `GW_Topping` | 需要配料? | `Flow_Topping_Yes` | 是 | `= needTopping = true` | `UT_Topping` |
| | | `Flow_Topping_No` | 否 | `= needTopping = false` | `Task_Summary` |

> userTask 完成后的出边：`Flow_Crust_Done`→`GW_Cheese`、`Flow_Cheese_Done`→`GW_Sauce`、`Flow_Sauce_Done`→`GW_Topping`、`Flow_Topping_Done`→`Task_Summary`。

## 8. 关键设计与约定

1. **两流程同为「本体驱动」但交互模式不同**：烘焙=全自动编排（`matchedWord` 分支），设计=人机协同（`needXxx` 决定 userTask 是否出现）。
2. **分支判据分两套**：烘焙读字符串 `matchedWord`（组件名称标签），设计读布尔 `needXxx`（本体约束是否命中）。
3. **jobType 字面量解耦**：BPMN 与 Java 无引用；改拓扑不需改 Worker（只要 jobType 对齐）。
4. **userTask 由本体驱动弹性出现**：`needXxx=false` 时该组件直接跳过（如素食/白披萨无某组件），流程图结构固定而**运行路径可变**。
5. **流程仅编排、不承载业务约束**：工艺约束（禁肉/禁入炉等）写在 `documentation` 文字里，**未做引擎级校验**；真正约束由本体推理承担。
6. **资源路径**：`ontology.bpmn-path` / `ontology.design-bpmn-path` 定位两流程；相对模块根目录。
