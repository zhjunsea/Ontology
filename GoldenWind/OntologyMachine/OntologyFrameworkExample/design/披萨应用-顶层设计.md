## 1. 概述与定位

`OntologyFrameworkExample`（应用简称 **Pizza**）是本工程中的**示例应用模块**，用于端到端演示并验证「**本体驱动 + BPMN 编排 + Ontop 虚拟数据访问**」这一技术路线的可行性。它与 `OntologyFramework`（TMSD 塔架中段设计）是同工程内**并列、独立**的两个应用：一个以「披萨」为业务样板，一个以「塔架中段定制化设计」为业务样板，共享底层的 `OpenlletResolver` 与 `OntopOBDAHandler` 两个能力模块。

**核心特征：**

- **本体即真相**：业务约束（披萨类型 → 组件取舍/取值范围）由 OWL 本体（TBox）表达，由 Openllet 推理器在运行时判定，而非硬编码在程序中。
- **BPMN 管编排**：流程拓扑（含分支/用户任务）定义在 BPMN 中，部署到 Camunda 8 / Zeebe 由引擎驱动，应用侧不解析 BPMN。
- **Ontop 虚拟取数**：业务数据（组件库存/价格等）留在 MySQL 关系表，经 Ontop OBDA 映射按需重写为 SQL，应用以 SPARQL 视角读写。
- **消息外发**：低库存等事件经 RabbitMQ 异步外发，不参与主流程编排。

## 3. 运行时架构与分层

```
┌──────────────────────────────────────────────────────────────┐
│ 编排层（BPMN，部署到 Zeebe）                                    │
│   myPizzaBakingProcess.bpmn (PizzaMakingStandardProcess)       │
│   myPizzaTypeDesignProcess.bpmn (PizzaOntologyDesignProcess)   │
│   由 Camunda 8 / Zeebe 引擎按拓扑驱动，serviceTask 派发作业       │
└───────────────▲──────────────────────────────────────────────┘
                │ jobType 字面量绑定（BPMN type ⇄ @JobWorker(type)）
┌───────────────┴──────────────────────────────────────────────┐
│ 应用层（Spring Boot 应用 = JobWorker）                          │
│   PizzaOntologyJobWorker（9 个 @JobWorker）                     │
│   PizzaApplication（入口）、Utilities、RabbitMqHandler          │
└───┬─────────────────────────┬──────────────────┬──────────────┘
    │                         │                  │
┌───▼─────────────┐  ┌────────▼────────┐  ┌──────▼────────────┐
│ 领域/本体层      │  │ 数据访问层       │  │ 消息层            │
│ OWL TBox+ABox   │  │ Ontop OBDA      │  │ RabbitMQ          │
│ Openllet 推理    │  │ → MySQL         │  │ 低库存告警外发     │
│ SKOS 术语        │  │ 3 条映射         │  │                   │
└─────────────────┘  └─────────────────┘  └───────────────────┘
```

- **编排层**只描述"怎么串"，不含算法；**应用层**只描述"每步怎么算"；**本体层**描述"约束对不对"；**数据层**提供实例数据；**消息层**做异步外发。
- 五者通过 **jobType 字面量 / 本体 IRI / OBDA 映射** 松耦合连接（详见 §5）。

### 4.2 九类 JobWorker（`PizzaOntologyJobWorker`，均 `autoComplete=false`）

| # | jobType | 能力 | 关键回写变量 |
|---|---|---|---|
| 1 | `insert-component` | 插入组件个体（自动按表拆分） | `createdInstanceIri` |
| 2 | `update-individual` | 更新个体属性 | `updateSuccess` |
| 3 | `delete-component` | 删除个体 | `deletedRows` |
| 4 | `query-instances` | 按根类检索 ABox 实例 | `queryResults`（键可配，默认 `strResult`） |
| 5 | `query-property-value-ontology` | 查本体属性值 | `propertyValues` |
| 6 | `query-property-value-db` | 查数据库属性值 | `propertyValues` |
| 7 | `get-component` | 由 `pizzaType + targetProperty` 求最佳匹配组件类型 → ABox 取最低价实例 → 标签匹配 | `componentName`/`componentPrice`/`matchedWord` |
| 8 | `pizza-limitation` | 解析饼底/奶酪/酱汁/配料四属性的约束与可选项 | `needXxx`/`xxxOptions`/`xxxInstances`（12 个变量） |
| 9 | `pizza-summary-generator` | 组装摘要 + TBox 一致性校验 + 写入 `MyPizza_<ts>` 实例 | `pizzaSummary`/`ontologyValidationStatus`/`myPizzaInstanceIri` |

> 上述 9 个 jobType 即两个 BPMN 中 `serviceTask` 的 `zeebe:taskDefinition type` 取值来源（见《流程设计》）。

## 5. 解耦机制（核心设计）

### 5.1 BPMN ↔ 流程引擎 ↔ JobWorker

BPMN 与 JobWorker **无代码级引用**：
- BPMN 部署到 Zeebe 后，引擎按拓扑创建/推进实例；到达 `serviceTask` 时，按该节点 `zeebe:taskDefinition type` 派发作业；
- 订阅**同名 jobType** 的 `@JobWorker` 方法被回调，算完回写流程变量，引擎继续下一步。

> 一句话：**BPMN 管「怎么串」、引擎管「按序驱动」、Worker 管「每步怎么算」、本体管「约束对不对」，靠 jobType 字面量绑定。**

### 5.2 Worker ↔ 本体（推理）

Worker 经 `BackendService`（`com.ocean.openlletresolver.*`）取 `ReasonerService`/`OntologyService`：
- `pizza-limitation` 用推理器做 **BFS 父类链 + 子类展开**，解析各组件属性的约束与候选；
- TBox 一致性由 `reasoner.isConsistent()` 判定。

### 5.3 Worker ↔ 数据（Ontop 虚拟访问）

- 读：`OntologyService.buildValuesClause(...)` 生成 `VALUES`，`ObdaHandler.executeAboxQuery(sparql)` 经 **Ontop** 把 SPARQL 重写为 SQL 打到 MySQL（`myPizza.obda` 三条映射）；
- 写：`InsertService`/`UpdateService`/`DeleteService` 经 `OntopMappingResolver` **按表自动拆分**，并保证事务原子性/回滚。

### 5.4 多上下文幂等初始化（`@PostConstruct init()`）

`init()` 先 `OBDAHandler.init(props, obda)`；若抛 `IllegalStateException`（判为同一 JVM 内已初始化）则复用连接池，并 `BackendService.setInstance(null)` 丢弃上一上下文已 `dispose` 的 reasoner，再 `BackendService.getInstance(mainOntologyPath, obdaHandler)` 重建。该幂等化解决了「同 JVM 多 Spring 上下文」场景下复用被 dispose 的 reasoner 而失败的问题。

## 6. 端到端数据流

1. **发起**：外部（Camunda 控制台 / 测试）以 `variables={pizzaType:<IRI>}` 创建实例（`PizzaMakingStandardProcess` 或 `PizzaOntologyDesignProcess`）。
2. **本体推理（TBox + Openllet）**：解析类型约束与可选项。
3. **Ontop 取数（ABox）**：SPARQL→SQL→MySQL，取组件实例与价格。
4. **计算/写库**：`insert/update/delete-component` 与 `pizza-summary-generator` 写 `pizza_components`/`crust_components`/`myPizza`；各 worker 回写流程变量。
5. **分支**：烘焙流程按 `matchedWord` 走分支；设计流程按 `needXxx` 决定 userTask 是否出现。
6. **消息外发**：低库存经 `SwrlRuleTriggerListener` → `RabbitMqHandler.send("pizza.low-stock.exchange","low.stock.alert",payload)` → 路由到 `pizzaQueue`。

`EnvPrepare`（`com.ocean.envprepare`）按子命令分发（`start` / `createdb` / `create-rabbitmq`）：
- 依据 `env-prepare` 节点启动/校验 Ontop、Camunda、RabbitMQ；
- 依据 `ddl-file`/`data-file` 建库建表并灌数据；
- 依据 `rabbitmq.*` 经 Management HTTP API 创建 Exchange/Queue/Binding。

- 应用入口激活 Profile `PizzaBPMNTest`（`PizzaBpmnRealEngineTest` / `PizzaBakingProcessInMemoryTest` 依赖该 Profile 激活 worker）；
- 运行需外部 Camunda 8（`localhost:26500`）、Ontop（`8080`）、MySQL、RabbitMQ 就绪（真实引擎套假定环境已就绪、不做探测）。

## 8. 关键设计决策与约定

1. **本体为唯一约束来源**：组件取舍与范围由 TBox 定义，程序不硬编码业务约束。
2. **jobType 字面量绑定**：BPMN 与 Worker 解耦的关键，改 BPMN 不需改 Java 引用（仅需 jobType 对齐）。
3. **Ontop 虚拟数据**：业务数据不迁入本体文件，留在关系库经映射按需访问。
4. **TBox/ABox 分离**：`pizza-all.owl` 为总入口；TBox（`core`/`components`/`processes`）与 ABox（`*-abox`）分层组织。
5. **幂等初始化**：支撑同 JVM 多上下文（内存套 + 真实套同跑）。
6. **约定**：资源路径用相对路径；临时/日志产物落模块根 `logs/`。
