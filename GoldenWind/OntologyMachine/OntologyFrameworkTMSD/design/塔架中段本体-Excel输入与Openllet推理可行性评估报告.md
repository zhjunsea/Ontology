## 一、结论速览

| 问题 | 结论 |
|------|------|
| 能否「一键」从两个 Excel 直接得到「需要修改的地方」？ | ❌ **不能**。缺 3 个必要环节（数据接入、历史设计实例库、设计环节概念） |
| Openllet 能否读 Excel？ | ❌ **不能**。DL 推理机不读文件，这是脚本/映射层的职责 |
| Openllet 能否执行流程编排（原「从后往前逐级匹配」）？ | ❌ **不能**。流程为**有序过程控制**，DL 无此语义（现行流程已改为**完全正向单链路、无匹配无回退**，本身不再需要匹配） |
| Openllet 能否做数值计算（扶持位置、梯子高度、平齐、锥段插值）？ | ❌ **不能**。本体文档已明确列为「无法用 DL 表达」，须外置 SWRL/脚本 |
| Openllet 能否输出「需要修改的地方」？ | ✅ **能，但仅限一种**：把设计值实例化后，检出**违反约束公理的个体（现行：19 条可数值校验约束 + 9 条基数约束）** → 「此处不满足设计准则，需修改」 |
| 能否让 Openllet 推导「哪些设计环节需重做」？ | ⚠️ **可以，但需先补本体**：目前本体中**没有任何**「设计环节 / 匹配层级 / 匹配结果」概念（实测 grep 为空），Openllet 无从推理 |
| 两个 Excel 的字段能否被本体承载？ | ⚠️ **中段相关字段大部分可以**（几何/法兰/附件/平台/机型/扶持），**门洞门框、疲劳等级、T型法兰**无对应；**防雷螺柱角度已建模（v16.0）** |

**一句话结论**：**Openllet 只能承担「校验」一环，不能承担「读数据 + 走流程 + 算数值」三环。** 要得到完整的「需要修改的地方」，必须补齐「Excel→本体映射」「历史设计实例库」「设计环节概念」三件事，且流程编排仍须由 BPMN/脚本执行。

## 四、Openllet 的能力边界（依据 OWL 2 DL 规范与本体文档）

### 4.1 Openllet 能做的（本体现已支持）

1. **一致性校验（最直接产出「需修改项」）**——把设计值实例化后，检出违反 `owl:Restriction` 的个体。
2. **分类 / 实例化**——由属性推断个体所属类（焊接灯 vs 线槽灯、钢绳导向 vs 爬梯导向升降机）。
3. **完整性校验**——`owl:qualifiedCardinality` 检出「有且仅有 1 个塔筒/平台/爬梯」等缺值。
4. **身份识别**——`owl:hasKey`（`:筒节编号`、`:机型名称`、`:区域名称`）。
5. **双向查询**——`owl:inverseOf`（17 条）。

### 4.2 Openllet 不能做的（本体文档已明确）

| 事项 | 原因（本体文档原文） |
|------|---------------------|
| 读 Excel / 文件 | 推理机不处理 I/O |
| 从后往前逐级匹配 + 提前终止 | 属**有序过程控制**，DL 无此语义 |
| `:扶持位置` =（筒高−1250）÷2 | 「DL 不支持数值公式计算」 |
| `:梯子高度` = 筒高 | 「跨属性相等」 |
| `:支撑位置` = `:托架位置`（平齐） | 「跨属性相等，须 SWRL 9.4」 |
| 相邻附件实际中心距 | 「需跨个体比较，DL 无法表达，须 SWRL 9.3」 |
| `:平台所在处内径`（锥段插值） | 「数值计算」 |
| 单位换算 | 「Openllet 不处理单位」 |
| 封闭世界下的「缺值」完备检测 | 「OWA 假设，仅能用基数限制近似」 |

## 五、要「输出需要修改的地方」，必须补齐的三件事

### 缺口 1：Excel ↔ 本体 字段映射（数据接入层）— **必须补**

- **现状**：本体不含 sheet/列下标（正确），但**映射表不存在**。
- **证据**：分析报告 §7.4 建议「单独维护一份『Excel ↔ 本体』字段映射表（BPMN 或配置文件）」——**至今未落地**。
- **需交付**：一份映射表 + 一个解析脚本，把两个 Excel 转成 RDF 个体。
- **归属**：**脚本**，不是 Openllet。

### 缺口 2：历史设计实例库（ABox）— **必须补**

- **现状**：本体为**纯 TBox**（OBDA 留空）；具名个体仅 4 个（V12/V15/V17/V19，均为 `:机型` 分类值），**无任何设计实例**。
- **证据**：流程符合性核查报告 §步骤3 已指出「本体为 TBox（概念层），无『历史设计实例库/版本』机制 ⚠️ 属实例层（ABox）职责」。
- **需交付**：把历史设计方案（每套 = 两个 Excel）实例化为本体个体，形成可比较的实例库。
- **归属**：**数据 + 脚本**。

### 缺口 3：「设计环节 / 匹配结果」概念（推理层）— **要 Openllet 参与就必须补**

- **现状**：本体中**无任何** `step` / `match` / `hit` / `环节` 类或属性（实测 grep = 空）。9 步流程**只存在于 BPMN**。
- **后果**：Openllet **无从推理**「哪些设计环节需执行 / 需修改」。
- **若要补**，需在本体新增：
  - 类 `:设计环节`（子类 `:平台设计` / `:筒节设计` / `:高度设计` / `:直径设计` / `:附件类型替换` / `:升降机设计`）
  - 属性 `:匹配层级`（内径/筒节/高度/直径/连接方式/机型）、`:匹配结果`（命中/未命中）
  - 规则：`未命中筒节 → 需执行 筒节设计 及其后续`（可用类定义表达）
- **注意**：即使补齐，**流程控制流仍须 BPMN/脚本**执行，Openllet 只负责「由已断言的环节结果推导需执行环节」。
  > ⚠️ 更正（v16.5）：现行设计范式为**完全正向单链路、无匹配无回退**（BPMN 9 serviceTask + 10 顺序连线、无网关），已不存在「从后往前逐级判定 + 提前终止 + 命中即复用」；缺口 3 的「匹配结果」概念相应不再需要，「设计环节」概念仍缺失。

## 六、端到端分工建议（三层）

```
① 数据接入层（脚本）          ② 流程编排层（BPMN/脚本）           ③ 推理层（Openllet）
─────────────────────      ──────────────────────────      ──────────────────────
两个 Excel                  步骤1 塔筒外形设计                 一致性校验：
  │                           │                                 · 违反约束公理的个体（19 数值+9 基数）
  ├─ 字段映射表（待建）        ├─ 6 级从后往前匹配（有序+提前终止）      → 「此处需修改」
  ▼                           │                                 · 基数/完整性缺值
RDF 个体（本次输入）          ├─ 命中 → 复用 / 未命中 → 执行环节     分类/实例化：
  +                          ▼                                 · 焊接灯/线槽灯
历史设计实例库（待建）        「需执行的设计环节清单」              · 钢绳/爬梯导向升降机
                            （= 需要修改的地方）                 身份识别：hasKey
                              │
                              └─ 设计值写回本体 ──────────────► 校验 → 输出违规清单
```

**关键点**：**「需要修改的地方」有两个来源，必须分清**：
1. **流程来源**（BPMN/脚本产出）：由设计环节决定「哪些环节需执行」——**Openllet 不参与**（除非按缺口 3 补本体）。
2. **校验来源**（Openllet 产出）：设计值违反约束 → 「哪个值需修改」——**这是 Openllet 唯一能直接产出的**。

> ⚠️ 更正（v16.5）：上文分工图/文字中的「6 级从后往前匹配、命中→复用」为历史范式；现行流程为**完全正向单链路、无匹配无回退**（BPMN 9 serviceTask + 10 顺序连线、无网关）。

## 八、最终回答

**问：当输入为那两个 Excel 时，能否按 BPMN 流程、经 Openllet 推理后，输出「需要修改的地方」？**

**答：不能「全自动」做到；分三层看——**

| 层 | 职责 | 现状 |
|----|------|------|
| 数据接入（Excel → 本体） | 字段映射 + 解析脚本 | ❌ **映射表未建**；中段字段大部分可承载，门洞/防雷角度等无对应 |
| 流程编排（匹配 + 执行） | 6 级从后往前匹配、提前终止、数值计算 | ❌ **Openllet 做不了**，须 BPMN/脚本；且**历史设计实例库为空（个体数 0）** |
| 推理校验（Openllet） | 检出违反约束公理的个体（现行 19 条数值约束 + 9 条基数约束） | ✅ **能做**，且是「需修改项」的唯一推理来源 |

**要达成目标，需补齐**：① Excel↔本体映射表 + 解析脚本；② 历史设计实例库（ABox）；③ （可选）本体新增「设计环节/匹配结果」概念，让 Openllet 参与推导「需执行哪些环节」。

**当前本体 v16.5 的定位是正确的**：它是一份**质量合格的 TBox（概念层 + 约束层）**（OBDA 留空 ⇒ 纯 TBox），约束公理与流程条款对应，足以支撑 Openllet 做「设计值校验」。**它本就不该承担数据接入与过程控制**——这两者属脚本与 BPMN。
